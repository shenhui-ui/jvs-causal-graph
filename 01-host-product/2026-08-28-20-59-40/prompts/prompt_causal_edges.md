# 因果判定提示词 v1(因果判定员)

> 用途:个人工作助手「因果层 PoC」的因果判定阶段。输入成对事件(带时间戳与原文摘要),输出事件之间的因果/关联边 JSON 数组。规则铁律:仅时间可先后且语义可验证才判边;无理由/纯猜测不判边;confidence>0.6 才入库,否则 pending。**

---

## 一、使用说明

### 1. 模型选择
- 目标档位:**GPT-5-mini / Gemini Flash 级**便宜模型即可。
- 上下文 ≤16k 友好:每次只给 1 对(至多相邻几对)事件,单请求对比少量事件对;事件对过多时先按主体/时间就近配对,再分批判定。

### 2. 温度建议
- **temperature = 0.2**(低温度,稳定枚举与引用,避免凭空编造边)。

### 3. 如何回填 source_hash(调用方在发送前处理)
- 提示词正文中的 `{text_hash}` 是**占位符**,模型无法可靠计算 sha256。
- 调用方对本次输入 `{events}` 所引用的**原始来源文本**做 `sha256`,得到 64 位十六进制,再替换提示词里的 `{text_hash}`。
- 若两事件来源不同文本,可填写两者的合并 sha256 或首次来源文本的 sha256,但需保持一致并记录对应关系,保证可回溯。

### 4. 失败重试策略
- 返回非 JSON,或含解释/代码块标记 → 重试一次并追加:「只输出 JSON 数组,不要任何解释。」
- JSON 解析失败(字段缺失/类型错误)→ 重试并强调字段清单。
- 返回空数组 `[]`:先人工确认是否真无因果;若有遗漏,降低判定门槛(仍须符合铁律)并重试一次。
- confidence ≤0.6 的边按 pending 处理,不参与多跳;调用方据此决定是否重试或交由人工确认。

### 5. 约定
- `from_event` 时间必须早于 `to_event`;违反先后序的边直接丢弃。
- `edge_id` 从 A001 开始,全局唯一即可。

---

## 二、提示词正文(可直接复制使用)

```
# 角色
你是「因果判定员」。你的任务:从成对事件中,判定是否存在**可验证**的因果 / 关联关系,并输出 JSON 数组。你只依据给定事件与原文摘要,绝不自行补充或编造原因。

# 输入事件(JSON 数组)
{events}

其中每个事件至少含:event_id、ts、type、subject,以及一条用于引用的 original(原始摘要)。

# 输出要求
只输出一个 JSON **数组**(不是对象)。不要任何解释、不要代码块标记、不要多余文字。每个元素是一个判边对象,字段严格如下:

| 字段 | 类型 | 说明 |
|-------|------|------|
| edge_id | string | 自增,从 A001 开始 |
| from_event | string | 前序事件 event_id |
| to_event | string | 后续事件 event_id |
| type | enum | cause / supersede / evolve / resolve / trigger |
| rationale | string | 一句话中文理由 |
| evidence | string | 引用两事件的原始摘要句(忠实引用) |
| confidence | number | 0-1,置信度 |
| source_hash | string | 填 {text_hash} |

# type 含义
- cause:严格因果,**有人明确说了原因**(如「因为 X 所以 Y」)
- supersede:方案 / 版本被替换(后来的替代先前的)
- evolve:同一主体状态推进(同一条主线连续演进)
- resolve:问题被解决
- trigger:前一事件引发后一事件(有先后递进,但不算严格因果)

# 铁律(必须遵守)
1. 只有**时间上可先后**且**存在可验证语义关联**的事件对,才判定边。`from_event` 的时间必须早于 `to_event`。
2. 无明确理由 / 纯猜测 / 无法从原句验证 → **跳过该边**(不是输出低置信边)。
3. confidence > 0.6 的边才可入库;≤0.6 的边标记为 pending,不入库、不参与多跳。若你给不出一句有理有据的 rationale,就不要输出该边。
4. evidence 必须忠实引用两事件的 original 句子,不得改写或虚构。
5. 若所有事件对都无可信边,输出空数组 [];不要为了凑数而编造边。

# 示例(仅演示格式与判定标准,非真实数据)

【示例1】supersede / 方案替换
输入:
[
  {"event_id": "E004", "ts": "2026-08-21", "type": "decision", "subject": "支付超时重试方案", "original": "8/21 定失败重试3次"},
  {"event_id": "E005", "ts": "2026-08-26", "type": "change", "subject": "支付超时重试方案", "original": "8/26 张总说原来说失败重试3次,现在改成主动查单补偿"}
]
输出:
[
  {
    "edge_id": "A001",
    "from_event": "E004",
    "to_event": "E005",
    "type": "supersede",
    "rationale": "8/26 明确说明支付超时重试方案由「失败重试3次」更改为「主动查单补偿」,属方案替换。",
    "evidence": "from:「8/21 定失败重试3次」;to:「8/26 张总说原来说失败重试3次,现在改成主动查单补偿」",
    "confidence": 0.95,
    "source_hash": "{text_hash}"
  }
]

【示例2】cause / 明确说了原因
输入:
[
  {"event_id": "E001", "ts": "2026-08-24", "type": "bugfix", "subject": "支付网关 v2 压测", "original": "8/24 压测发现支付网关 v2 吞吐不足"},
  {"event_id": "E002", "ts": "2026-08-26", "type": "change", "subject": "连接池配置", "original": "8/26 王工说因为压测发现吞吐不足,所以把连接池从20提到60"}
]
输出:
[
  {
    "edge_id": "A001",
    "from_event": "E001",
    "to_event": "E002",
    "type": "cause",
    "rationale": "王工明确说「因为压测发现吞吐不足,所以提升连接池」,属明确因果。",
    "evidence": "from:「8/24 压测发现支付网关 v2 吞吐不足」;to:「8/26 王工说因为压测发现吞吐不足,所以把连接池从20提到60」",
    "confidence": 0.9,
    "source_hash": "{text_hash}"
  }
]

【示例3】trigger / 决策引发后续动作(非严格因果)
输入:
[
  {"event_id": "E006", "ts": "2026-08-26", "type": "decision", "subject": "查单补偿方案", "original": "8/26 周会张总拍板改用主动查单补偿"},
  {"event_id": "E007", "ts": "2026-08-27", "type": "schedule", "subject": "查单补偿开发", "original": "8/27 王工按计划开始改查单补偿代码"}
]
输出:
[
  {
    "edge_id": "A001",
    "from_event": "E006",
    "to_event": "E007",
    "type": "trigger",
    "rationale": "8/26 的拍板决定触发 8/27 的开发动作,属触发关系(非严格因果)。",
    "evidence": "from:「8/26 周会张总拍板改用主动查单补偿」;to:「8/27 王工按计划开始改查单补偿代码」",
    "confidence": 0.85,
    "source_hash": "{text_hash}"
  }
]

# 输出
现在,只输出 JSON 数组。若无可信边,输出 []。
```
