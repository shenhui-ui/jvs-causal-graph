# 贾维斯类个人 Agent 设计方案 v0.1

> 场景：个人工作助手｜形态：端侧常驻 + 云推理混合部署
> 日期：2026-08-29｜状态：方向稿，待评审

---

## 0. 一句话结论

**不做底座，只做「记忆 + 主动 + 治理」三层。**

寄生在 OpenClaw 生态上，用 memU 替换其扁平的 `MEMORY.md` 记忆层，自研主动性引擎与治理层，先在「个人工作助手」场景跑通 L2→L4。自研工作量相比全栈自研减少约 60%，且全部集中在生态做不好的地方。

---

## 1. 项目定位

### 1.1 贾维斯的本质不是「更聪明的模型」

绝大多数人做这类 Agent 会一头扎进模型能力。但贾维斯让人印象深刻的从来是四件事：

| 特征 | 含义 | 实现依赖 |
|---|---|---|
| **知情** | 比你更了解你自己 | 记忆层 |
| **常驻** | 不是你问它才动 | 主动性引擎 + always-on 运行时 |
| **有授权** | 真能动手改东西 | 执行层 + 治理层 |
| **可托付** | 知道边界，敢说「这个我不建议」 | 人格层 + 治理层 |

这四条里，模型能力只占一小部分，其余全靠架构补。**认知层直接用最强通用模型即可，那不是竞争力所在。**

### 1.2 设计原则

1. **记忆优先于能力** — 记忆层是护城河，其他层可复用可替换
2. **复用优先于自研** — 生态有的先评估，不重复造轮子（含许可证、维护状态、适配成本）
3. **可逆性优先于效率** — 能撤销的操作才允许自主执行
4. **用户可控优先于系统智能** — 记忆可查看、可编辑、可删除；主动提醒可一键关闭
5. **渐进授权** — 权限随信任积累逐步放开，不一次性全给

## 2. 生态调研结论

### 2.1 赛道现状：外壳已被做完了

2026 年该赛道已被 **OpenClaw 生态**大量覆盖（本体 14.5 万 star），衍生出 ZeroClaw（Rust）、NanoClaw、IronClaw、moltis、Clawlet、SubZeroClaw 等数十个项目。

已解决的问题：always-on 常驻、14+ 渠道接入、skills 系统、本地运行、语音 I/O、容器隔离。

**结论：感知层、执行层、编排层不应重复自研。**

### 2.2 四个真实空白

| 层 | 生态现状 |
|---|---|
| **记忆层** | 普遍薄弱。OpenClaw 用 `MEMORY.md` 扁平文件做三层记忆（长期/日/会话），无结构化、无图谱，答不出「这个项目为什么改过方案」 |
| **主动性引擎** | 多是 cron 定时任务。rho 有主动 check-in，但无人做注意力调度与打扰预算 |
| **治理层** | 几乎空白。仅 IronClaw 做了 WASM+Docker 沙箱、凭据注入、提示注入检测、端点白名单 |
| **人格层** | 无人做 |

**差异化不在「能干多少活」，在「记不记得住你」。**

### 2.3 记忆层选型对比（核心决策依据）

| 方案 | 抽象模型 | 输出形态 | 存储后端 | 基准 | License |
|---|---|---|---|---|---|
| **memU** | Resource/Item/Category 三层 | Markdown 文件系统 | in-memory / SQLite / Postgres | 新项目暂无 | Apache-2.0 |
| **Mem0** | 单层记忆 + tag | JSON | Qdrant / Postgres | 92.66% (LoCoMo) | Apache-2.0 |
| **Graphiti** | 时序节点 + 边（双时间轴） | 图查询结果 | FalkorDB / Neo4j | 94.8% (DMR)<br>LongMemEval 63.8% | Apache-2.0 |
| **Cognee** | Entity + Relation 图 | 图查询结果 | Neo4j / FalkorDB | ~85% | Apache-2.0 |
| **Letta** | 自带记忆的 Agent 运行时 | — | — | — | — |
| **Memobase** | 用户画像 | 结构化字段 | — | — | — |
| **ReMe** | 文件即记忆 | 可编辑文件 | — | — | 阿里 AgentScope 生态 |

各方案定位与边界：

- **Mem0** — 外置记忆中间件，5 分钟接入。局限：所有记忆平级文本，规模上去后召回质量下降
- **Letta**（MemGPT 前身）— 带记忆管理的 Agent 运行时。局限：必须接受它的 Agent 架构，与「寄生 OpenClaw」策略直接冲突
- **Graphiti / Zep** — 时间是一等公民，记录事实「何时成立、何时失效」，双时间轴。局限：架构重，需专用图数据库，图查询结果对 LLM 不友好
- **Cognee** — 把文档熬成可推理知识网。局限：数据加工链路长，对实体抽取 prompt 要求高
- **Memobase** — 专注「你是什么样的人」，C 端画像层，不是通用事件流
- **Text2Mem** — 记忆操作协议（原子操作 + JSON 契约 + 验证层），可做控制面
- **ReMe** — 文件即记忆，透明可编辑，解决记忆黑盒问题
- **memU** — 记忆即文件系统，24/7 后台主动记忆 Agent

### 2.4 选型结论

**推荐：memU（主）+ Graphiti（辅，时序图谱）+ 自研去重/纠错层**

理由：

1. **memU 的 Markdown 输出与 OpenClaw 的 `MEMORY.md` 天然契合** — 可直接替换增强，零适配成本
2. **六类分类法覆盖性强** — `profile` / `event` / `knowledge` / `behavior` / `skill` / `tool`，正好对应「用户模型 + 事件 + 知识」三大诉求，比 Mem0 的平铺文本结构化得多，又比 Cognee 的任意 entity-relation 克制得多（LLM 抽取时知道往哪个槽塞，错误率低）
3. **声明式工作流 + 拦截器** — 可在不 fork 源码的情况下插入自定义步骤（敏感信息过滤、去重、纠错），这是自研补丁层的最佳挂载点
4. **LLM Profile 路由** — chat / vision / embedding 分流，抽取走便宜模型、分类走贵模型，成本可差一个数量级
5. **存储可插拔** — in-memory → SQLite → Postgres 同一套接口，原型到生产平滑过渡

**不推荐**：Mem0（平铺，无类型）；全 Graphiti（架构重 + 图查询对 LLM 不友好）；Letta（与寄生策略冲突）。

**memU 已知缺口（即自研补丁范围）**：
- `dedupe_merge` 未实装，长期累积会有重复条目 → 自研去重
- RAG 路径无 cross-encoder reranker → 自研精排
- 无时序图谱 → 外接 Graphiti 或自研轻量版
- 多租户隔离靠 `user_model`，无原生 row-level security → 单用户场景暂不影响
- Python 3.13+ 硬性要求、依赖 langchain-core

## 3. 总体架构

```
┌─ 感知层 Perception ────────────────────────────────┐
│  语音 屏幕 日历 消息 文件 环境                        │
├─ 认知层 Cognition ────────────────────────────────┤
│  规划 推理 反思 世界模型                             │
├─ 记忆层 Memory ★自研──────────────────────────────┤
│  memU 六类存储 + Graphiti 时序图谱 + 去重/纠错补丁    │
├─ 执行层 Action ──────────────────────────────────┤
│  工具 代码 浏览器 设备控制 (MCP)                     │
├─ 人格层 Persona ─────────────────────────────────┤
│  语气 价值观 偏好 边界                               │
├─ 治理层 Governance ★自研──────────────────────────┤
│  权限四级制 可逆性判定 人在环路 全量审计               │
└──────────────────────────────────────────────────┘
        ↑ 主动性引擎 Proactive Engine ★自研 纵向贯穿
          事件驱动 · 注意力调度 · 打扰预算
```

**自研三层**（全部价值所在）：记忆层、主动性引擎、治理层
**复用三层**：感知 / 执行 / 编排 → OpenClaw 类底座或 Claude Agent SDK；认知层 → 云端强模型

## 4. 核心自研模块设计

### 4.1 记忆层

#### 数据模型

沿用 memU 的四实体模型（git 类比便于理解）：

| 实体 | 含义 | git 类比 |
|---|---|---|
| `Resource` | 原始数据（一次对话、一个文档、一张图） | blob |
| `MemoryItem` | 抽取出的原子记忆 | commit |
| `MemoryCategory` | 主题分类文件夹，带演化摘要 | branch + README |
| `CategoryItem` | Item 与 Category 的多对多关联 | tag |

`MemoryItem` 六类型：

| 类型 | 存储内容 | 示例 |
|---|---|---|
| `profile` | 用户画像 | 用户是后端工程师 |
| `event` | 发生过的事 | 周三开了产品评审会 |
| `knowledge` | 知识/事实 | 我们的部署流程是蓝绿发布 |
| `behavior` | 行为模式 | 用户喜欢先列 TODO 再写代码 |
| `skill` | 技能/经验 | 用 ripgrep 比 grep 快 10 倍 |
| `tool` | 工具使用习惯 | 复杂查询先用 sql agent 试一遍 |

#### 四路存储（对应原始设计，由 memU + Graphiti 共同承载）

| 存储 | 承载方 | 回答什么问题 |
|---|---|---|
| 事件流 | memU `event` + 时间戳 | 发生了什么（可回放、可追溯） |
| 知识图谱 | Graphiti 时序图谱 | 谁和谁什么关系、状态如何演变 |
| 语义索引 | memU embedding 三级召回 | 语义相近的（兜底模糊召回） |
| 用户画像 | memU `profile` + `behavior` + `skill` + `tool` | 你是什么样的人 |

#### 写入管线

```
原始输入 → 模态分流 → 按类型并发抽取 → 分类归档 → 【自研:去重合并】→ 持久化
                                                   ↑ 挂载点：memU 工作流 insert_after
```

关键点：**按 memory_type 分别调用 LLM 并发抽取**，prompt 模板按类型定制，互不污染。

#### 读取管线：三级召回 + 自研精排

```
category_recall（粗排）→ item_recall（中排）→ resource_recall（精排）
        ↓                      ↓
   【自研:reranker】      sufficiency check（够了就跳过下一级，省 token）
```

#### 两个必须提前设计的机制

1. **分层淘汰** — 否则三个月后检索质量塌方。按类型设定不同衰减策略：`event` 衰减快，`profile`/`skill` 长期保留
2. **显式纠错入口** — 借鉴 ReMe「文件即记忆」理念。用户说「我说错了」必须能立刻改掉，否则错误会固化放大。**记忆系统最怕「自信地记错」**

### 4.2 主动性引擎

从 request-response 走向 event-driven 的开关，纵向贯穿全部层级。

三个组件：

| 组件 | 职责 |
|---|---|
| **事件驱动** | cron 定时 + 外部事件订阅（日历、邮件、文件变更）+ 阈值触发 |
| **注意力调度** | 对候选提醒打分排序，只推真正重要的 |
| **打扰预算** | 每日提醒配额上限 + 免打扰时段 + 一键关闭 |

**打扰预算是生死线**——主动提醒一旦泛滥，用户当天就会关掉它，且很难再打开。

设计约束：
- 默认每日主动触达 ≤ 3 次
- 每条主动提醒必须可「一键关闭该类提醒」
- 高优先级（如日程冲突）可突破配额，低优先级严格受限

### 4.3 治理层

决定用户敢不敢给它权限。

**权限四级制**：

| 级别 | 行为 | 示例 |
|---|---|---|
| 只读 | 直接执行 | 查日程、读文件 |
| 建议 | 只输出建议，不执行 | 起草邮件但发送 |
| 需确认 | 执行前必须人工确认 | 发送外部邮件、提交代码 |
| 自主 | 授权域内自主执行 | 整理本地文件、创建草稿 |

**可逆性判定**：能撤销的操作才允许进入「自主」级；不可逆操作强制「需确认」。这是治理层的核心判据，比权限清单更本质。

**全量审计**：所有自主行为留痕，可回溯、可解释「它为什么这么做」。

**安全基线**（直接借鉴 IronClaw）：
- WASM / Docker 沙箱执行工具
- 凭据注入：secrets 永不暴露给工具代码
- 提示注入检测
- 端点白名单

## 5. 复用层策略

| 层 | 策略 |
|---|---|
| **感知层** | 复用底座渠道接入。自研重点在**持续、低耗、不打扰**——端侧常驻小模型做筛选降噪，原始流不能全灌进大模型 |
| **认知层** | 直接用最强通用模型。自研重点是**分层规划**：战略目标 / 当日计划 / 单任务，三层节奏不同，混在一起必崩 |
| **执行层** | MCP / Function Calling 标准生态 |
| **人格层** | 低优先级。人格不是调 prompt 卖萌，是**稳定的判断倾向**——它得敢在你跑偏时说「这个我不建议」 |

## 6. 演进路线与里程碑

| 阶段 | 能力 | 标志 | 验收场景 |
|---|---|---|---|
| L1 执行器 | 单步工具调用 | 一句话能查到、能改到 | 查日程、找文件 |
| L2 规划器 | 多步任务编排 | 给目标自己拆步骤并跑完 | 自动整理本周待办 |
| **L3 记忆体** | 跨会话个性化 | 三个月前说过的事它记得 | **跨时间线问答** |
| **L4 主动体** | 事件驱动预警 | 你不问，它先开口 | **晨间简报** |
| L5 全权代理 | 授权域内自主闭环 | 你只做战略决策 | 常规事务自动处理 |

**当前生态 90% 的 Agent 卡在 L2。L3 是第一个真正的门槛。**

### 里程碑节奏

- **M0 验证** — 底座跑通 + memU 替换记忆层 + 导入历史数据
- **M1（L2→L3）** — 打通「跨时间线问答」，这是打穿生态短板的立身场景
- **M2（L3 巩固）** — 沟通自动落库 + 用户画像成型 + 去重/纠错补丁上线
- **M3（L4）** — 晨间简报 + 打扰预算 + 注意力调度
- **M4（L4→L5）** — 治理层完整落地 + 授权域内自主执行

**M1 是生死点**：若「上周跟张总聊的那个方案，后来改了什么」答得出来，产品定位立住；答不出来，说明记忆层没做对，不应继续推进。

## 7. 场景落地：个人工作助手的数据源策略

按「对接成本 / 信息价值」比排序：

| 梯队 | 数据源 | 授权方式 | 建议 |
|---|---|---|---|
| **第一梯队** | 本地文件系统、浏览器活动、终端历史 | 零授权 | **先做**，信息密度高且完全可控 |
| **第二梯队** | 日历、邮件 | CalDAV / IMAP 标准协议 | **次做**，成熟稳定 |
| **第三梯队** | IM（微信、企微、钉钉、Slack） | 各家 API 差异极大，微信几乎无官方开放接口 | **后做或跳过**，别把第一版押在它上面 |

### 端云切分红线

| 位置 | 职责 |
|---|---|
| **端侧（常驻）** | 原始数据采集、初步降噪筛选、向量索引、事件流、用户画像、意图路由 |
| **云端** | 深度规划、长文档理解、多步任务编排 |

**红线：原始个人数据不出端，上云只传任务相关的必要摘要。**

### 首发三场景

1. **晨间简报** — 自动汇总今日日程 + 待办 + 需关注事项。L4 主动性的第一落点，最有感，但必须能一句话关掉
2. **沟通后自动落库** — 把会议/沟通转成事件 + 待办 + 图谱关系。记忆层的主要写入口
3. **跨时间线问答** — 「上周跟张总聊的方案，后来改了什么？」答得出来，才说明记忆层真的成立

## 8. 风险与开放问题

| 风险 | 等级 | 说明 |
|---|---|---|
| **IM 数据授权** | 高 | 微信/企微无官方开放接口。规避：第一版不依赖 IM 数据 |
| **memU 成熟度** | 中 | 13.8k star、活跃提交，但 `dedupe_merge` 未实装、无 reranker。规避：这两块本就在自研范围内 |
| **记忆质量退化** | 高 | 长期运行后重复条目与错误事实累积。规避：M2 前必须上线去重 + 纠错 |
| **主动性失控** | 中 | 提醒泛滥导致用户弃用。规避：打扰预算硬配额 + 一键关闭 |
| **Graphiti 运维成本** | 中 | 需 FalkorDB。规避：先评估是否需要完整图谱，可用 SQLite 关系表做轻量版过渡 |

### 待决策

1. 是否接受「寄生 OpenClaw 生态」路线，还是坚持完全独立自研底座？（影响投入规模 3 倍以上）
2. 时序图谱是外接 Graphiti，还是先用 SQLite 关系表做轻量版？
3. 第一版是否纳入语音交互？（建议后置，先跑通文本 + 结构化闭环）
