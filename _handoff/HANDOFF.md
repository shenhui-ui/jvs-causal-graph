## 6. 常见坑速查

| 坑 | 表现 | 处置 |
|---|---|---|
| openclaw 内部长时间重试 | 曾挂 **15.7 小时**才放弃 | 所有外部调用加 `timeout -k 15 600` |
| mid-stream 超时 | ~107s 报 `LLM request timed out` | 重试即可过 |
| DNS `ENOTFOUND` | 多为机器休眠/网络瞬断 | 先 `curl -sI https://api.deepseek.com` 探活（401 = 通） |
| 批结果解析 WARN | 回包含日志行 | **预期噪音**，可忽略（`_load_batch_result` 先 JSONL 后 `extract_array` 兜底） |
| `deepseek-v4-flash` | 中转侧 TPM 耗尽 | **勿用** |
| `name_scan --names identities-init.json` | 误报 Z 码 | 严格表有缺陷，用默认表 |
| openclaw vs node | 要求 `>=22.22.3`，托管为 `v22.22.2` | 用系统 node v24，或走 embedded fallback。⚠️ **gateway 常驻服务已于 2026-09-20 安装**（计划任务用系统 node v24），故凡跑 openclaw 命令都需把 PATH 指向系统 node |
| 含花括号的 Glob | 返回空 | 不能据此否定已确认存在的目录 |
| 大文件 Read | 被截断 | 预览 ≠ 完整阅读 |
| **git 分支名含斜杠** | `git branch feat/x` **静默成功但不创建** | 本环境必须用扁平名 `feat-x`，详见 `GIT-POLICY.md` 第四节 |
| **`git gc --prune=now`** | 在暂存区有未提交文件时会**剪掉待提交 blob** | 先 commit 再 gc；若已误剪，`git reset` 后重新 `git add` 即可（磁盘文件未丢） |
| **`git switch` / `git checkout`** | **必被 SIGTERM**（09-18、09-19 各复现一次）；SIGTERM 会把工作区文件**批量移入回收站**：09-18 丢 9,551 个、09-19 丢 6,447 个跟踪文件 | **禁用**。建/切分支用 `git update-ref refs/heads/<b>` + `git symbolic-ref HEAD refs/heads/<b>`；合并用 `commit-tree` + `update-ref`。见 `GIT-POLICY.md` §11 铁律 1 |
| **单条长时 git 命令**（全库 `restore` / `add -A` / `checkout`） | 约 **9,000 个文件**即触顶被 SIGTERM，随后工作区被批量回收 | 切 **≤3,000 文件/命令**的有界批次：`git restore --pathspec-from-file=<chunk.nul> --pathspec-file-nul`。见 §11 铁律 2 |
| **SIGTERM 之后的残留** | `.git/index.lock`（0 字节）阻塞后续所有 git 写操作；`git status` 出现成千上万 ` D` | ① `git cat-file --batch-all-objects --batch-check` 确认对象库完好 → ② `rm -f .git/index.lock` → ③ 分块 `git restore` 还原。见 §11 铁律 3 |
| **`git read-tree HEAD` 对 ` D` 无效** | 它只重置索引、**不动磁盘**；若文件是**真被删**（不是索引残留），文件不会回来 | 先判断：`git status` 只有 ` D` 无 ` M` 且 `ls` 确无此文件 → 走 `git restore`，**不是** `read-tree` |
| **中断 `git merge` / `git gc`** | 可能**破坏 `.git`**（refs 丢失、pack 被移入回收站） | **绝不中断**；无输出不等于卡死。恢复办法见 `GIT-POLICY.md` 第十节事故复盘 |
| **手改 `_index/` 或 `_handoff/PENDING.md`** | 这些文件**由 `_migrate/` 生成**，重跑即被覆盖。09-19 曾把 `PENDING.md` 的整节「git 治理状态」静默抹掉 | 改**生成器**再重跑（索引层四个生成器：`classify.py` / `make_progress_md.py` / `make_scripts_ledger.py` / `make_scripts_md.py` / `make_index_md.py`）。⚠️ **必须先 `git add` 再跑生成器**，且**顺序不可换**（六步，详见技能 `jvs-index-layer-maintenance`） |
| **索引出现「待规划」大类** | 新子类只改了 `classify.py`、没登记 `status_map.py`，木桶口径把整个大类拖下去 | 新子类**必须同步** `_migrate/status_map.py` 的 `STATUS` |

## 7. 工作纪律（来自项目规范）

- 开发类任务收尾时**必须同步** README / 开发规范 / 接口文档 / 状态文档
- 当前执行文档**只写真实现行规则**；历史修订只进归档、migration note、changelog
- 启动较大方案前**先调研同类开源项目**，评估许可证、维护状态、安全风险与适配成本后优先复用
- 多方案应交叉对比、取长补短
- **改动先开分支，合入 `main` 前先过门禁**（`bash scripts/git-gate.sh`），详见 `GIT-POLICY.md`
  ⚠️ **门禁判据 = `FAIL=0` + `WARN=0` + 自报 `OK` 数 == 输出中 `[OK]` 行数；不要照抄 `OK` 数值**

  故**本文件不写该值，一律现测**。本文件 §9 各「补充」块与 §12 交接登记行里的 `OK=16` / `OK=15`
  是**当时为真的历史记录**（`5ca4991` 09-19、`45908cd` 09-20 18:23 均早于 C-4 的 21:53），**勿当现行基线**

### 记录纪律

1. **未知写「未确认」，未验证写「未验证」** —— 不猜、不留空。
2. **已否决的路线必须记「原因 + 重议条件」**（见 §10），不能只写「已否决」。
3. **资料冲突时标明冲突**，不自行宣布哪份更权威。
4. 保留**授权范围**与**待确认动作**，不把建议伪装成授权。

### 授权边界（三动作分离）

> 来源：上游 `project-handoff` 的**方法层**（其机制层不可用，见 §10 R16）。
> 以下三条**不依赖任何宿主能力**，故一并采纳。

**「提醒」「保存交接材料」「新建接续」是三个独立动作，互不授权。**

| 动作 | 触发 | 不得自动扩展为 |
|---|---|---|
| **提醒** | 到检查点且当前工作已安全收拢 | 不自动保存 |
| **保存** | 用户明确要求保存 / 整理交接 | 不自动新建任务 |
| **新建接续** | 用户明确要求「新建并继续」 | —— |

- **笼统的「交接一下」不扩展为新建任务。**
- **同一次明确授权不逐步重问** —— 若授权已含「保存 + 新建 + 核对后继续」，不拆成三次确认。
- 用户未回应时**继续已授权的工作**，不追问、不自动保存或新建任务。

### 提醒展示规范

决定提醒且用户尚未回应时：

1. 放在**最终答复正文最前、单独一段**，以 **`交接建议：`** 开头。
2. 写明**具体原因、接续第一步、确认后覆盖的动作**。
3. **不放进引用块、示例或代码块**，不埋在答复结尾。
4. 进度消息**不替代**最终展示。

### 提醒去重与冷却

- 同阶段、**同一具体混淆只提醒一次**；后续检查点可以得出「暂不提醒」，不因冷却结束就再次催促。
- 用户明确回应「先不交接 / 继续做」后，自回应时起**冷却至少 3 次自动压缩**；重复读取同一回应不延长冷却。
- 普通工作指令里的**「继续」不自动当作回应或交接批准**。
- 「做完 X 再提醒」以**指定节点**为准，不另加次数门槛。
