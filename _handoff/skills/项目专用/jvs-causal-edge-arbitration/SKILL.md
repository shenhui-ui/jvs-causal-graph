# JVS 因果边仲裁入库

## 何时用

- 拿到一批**仲裁裁决**（每条边 → `drop` / `retype` / `keep` / `defer` / `promote`），要落进图谱
- 裁决来自**仲裁界面导出**（`verdict ∈ {ok,no,sk}`）—— 词表与字段双不通，**先过适配器**
- **逐条仲裁**一批非法组合（如 `cause/supersede ∧ weak`、`conf≤0.6`），需要先把机械判据跑掉
- 为一大池边（如 1,379 条）设计**抽样方案**
- **跨快照**引用旧裁决，或怀疑 `edge_id` 与库内对不上
- 图谱边数与裁决记录对不上，要排查
- 需要复核「上次入库到底改了哪些边、有没有漂移」
- 要判「界面 3 键的**粗判层映射**是否与入库词表一致」

⚠️ **这是改库操作**（会改 `.db` + `.jsonl`），**开工前必须先备份**。
⚠️ **只是出结论/方案、不落库时**，只需读「逐条仲裁的机械前置」「抽样方案设计」「第二方独立复核」三节，**不要动库**。

## 一句话

**干跑零写入 → preflight 拒绝 → 备份 → 逐字节保真改写 → 官方入口重建 → 独立校验。**

> 前置版（不动库）：**辨清权威源 → 机械判据全跑 → 逐条人工判读 → 第二方独立复核 → 落交付文档**。

### ⭐⭐ 坑 12：判「映射是不是一一对应」时，**必须先剥离精细层再查**（否则误判为「约定」）

**踩坑经过**：用 `ui_verdict × disposition`（**引用文件的原始字段，5 值**）交叉制表，得到：

| `ui_verdict` | `drop` | `retype` | `keep` | `defer` | `promote` |
|---|---:|---:|---:|---:|---:|
| `no`（103） | 100 | 0 | 0 | 0 | **3** |
| `ok`（42） | 0 | **17** | **25** | 0 | 0 |
| `sk`（1） | 0 | 0 | 0 | 1 | 0 |

于是判「`no`/`ok` 都不是一一对应 ⇒ 该映射是**约定**，须项目方确认」。**这是错的。**

**真相**：`disposition` 是**两层**的合成 —— **粗判层**（界面能表达）+ **精细层**（界面表达不了）。
精细层由 `proposed_*` 字段**独立承载**，**与 `ui_verdict` 无关，可机械剥离**：

| 剥离依据 | 结果 |
|---|---|
| `retype` 17 条 | `proposed_type` **全非空且 ≠ `cur_type`**；`proposed_strength` **未变** ⇒ 纯类型修正 |
| `promote` 3 条 | `proposed_type` **= `cur_type`**；`proposed_strength` **= `strong`** ⇒ 纯强度修正 |
| `keep` 25 条也带 `proposed_*` | **全部等于 `cur_*`** ⇒ 是「**确认不变**」留痕，**不是**第三类处置 |

**剥离后**，粗判层是**严格 3×3 对角（126/126 零例外）**：

| `ui_verdict` | `drop` | `keep` | `defer` |
|---|---:|---:|---:|
| `no` | **100** | 0 | 0 |
| `ok` | 0 | **25** | 0 |
| `sk` | 0 | 0 | **1** |

**再做篡改自证**（只有能拒绝才算校验）：枚举三值 → `{drop,keep,defer}` 的**全部 27 种映射**，
**只有 `{no:drop, ok:keep, sk:defer}` 零反例**（次优解各 1 条 / 25 条反例）
⇒ **唯一解 ⇒ 它是反解结果，不是自由约定项**。

```python
# 核心：先按 proposed_* 是否【改变现值】剥离精细层，再核粗判层
FINE = {"retype", "promote"}
coarse = collections.Counter()
for x in items:
    if x["disposition"] not in FINE:          # ← 关键：不剥离就必然看到非对角项
        coarse[(x["ui_verdict"], x["disposition"])] += 1
# 然后枚举全部 3^3 种映射，数反例 ⇒ 唯一零反例者才是真映射
```

**通则**：**判「两张表是不是一一对应」之前，先问「右边那张表是不是复合的」**。
复合字段（粗判 + 精细）**必然**看起来非一一对应，**不代表映射是自由约定的**。

### 坑 13：⚠️ 界面按钮标签可能**与它实际投的票不一致**（语义可能相反）

实测 220 界面（`_staging/D10-判边人工仲裁-220.html` **第 207 行**）：

```html
<button class="no" onclick="vote('no')">✗ 剔除 / 改判 strong</button>
```

- 标签含「**改判 strong**」，但**只投 `vote('no')`** ⇒ 界面**确实无法表达** `promote`；
- ⚠️ 用户点它是想**升 strong**，实际被记成 `no`（⇒**剔除**）—— **语义可能相反**；
- 全量 `vote()` 只有 3 个值（`ok`/`no`/`sk`），**没有第四种输出**。

⇒ **凡界面导出带「界面表达不了的精细处置」，一律走叠加层**，别指望界面。
适配器做法：`--overlay '{"retype":{id:new_type},"promote":[ids]}'`，
**覆盖粗判并保留 `coarse_disposition` 留痕**（便于事后审计「这条是界面判的还是另定的」）。
**推论**：凡「改型保留」类口径（如 G14 那 9 条）**无法用界面表达**，必须走 overlay。

### 坑 14：核验串会写错 —— **`CLOSED_` 条目的标题常在新旧表述间漂移**

写 `CLOSED_<日期>` 条目时若中途改过标题（如「✅ 已闭合」→「同日自我纠正后闭合」），
之后用**旧串** `grep -cF` 去 HEAD 里核验会返回 **0**，看起来像「没进库」。
⇒ **先 `grep -o` 打印 HEAD 里的真实行再照抄**（同坑 8）；
且 ⚠️ **别用 `grep -F` 配 `^` 锚点** —— 固定串模式下 `^` 是字面量。

> 另：`CLOSED_*` 列表的元组**是 2 元组**（`(标题, 说明)`），不是 3 元组。
> 写成 3 元组会让下游生成器 `make_progress_md.py` 崩在
> `for name, why in items: ValueError: too many values to unpack`。
> **改完 `status_map.py` 必须先 `compile()` + 实跑一次生成器**（本项目已踩 1 次）。

## 第 0 步：先辨清「哪份裁决是权威源」

**同一个目录下常并存多份易混的仲裁文件，口径不同。用错口径 = 整批改错。**

| 文件 | 口径 | 能否用 |
|---|---|---|
| `D10-仲裁结果-独立复核.json` | **B·从严**，含 `proposed_type` | ✅ **权威源** |
| `arbitration-result-doubao.json` | 无目标类型字段 | ❌ 排除 |
| `arbitration-verdicts-146.json` | A 口径 | ❌ 勿混用 |
| `arbitration-result-146.json` | A 口径 | ❌ 勿混用 |

**判据**：权威源必须同时具备 ① 每条边的**当前状态**（`cur_type`/`cur_strength`，
用于 preflight 比对）② **目标状态**（`proposed_type`，用于 retype）。

**从严原则**：`promote`（升 `strong`）误升会污染高置信子集，**宁可不采**。
若裁决中存在「撤回的 promote」，用 `effective_disposition()` 把撤回项一律视为 `keep`：

```python
PROMOTE_ADOPTED = {"A5324"}                  # 实际采纳
PROMOTE_WITHDRAWN = {"A4830", "A711"}        # 撤回 → 视为 keep

def effective_disposition(item):
    if item["disposition"] == "promote" and item["edge_id"] in PROMOTE_WITHDRAWN:
        return "keep"
    return item["disposition"]
```

## 第 2 步：preflight 拒绝机制（不可降级为警告）

```python
def preflight(verdicts, edges_by_id):
    if len(edges_by_id) != EXPECT_EDGES_BEFORE:
        raise SystemExit("边集边数 %d != 期望 %d" % (len(edges_by_id), EXPECT_EDGES_BEFORE))
    missing = [e for e in verdicts if e not in edges_by_id]
    if missing:
        raise SystemExit("裁决中的边不在边集内：%s" % missing)
    bad = [...逐条比对 cur_type / cur_strength 与库内是否一致...]
    if bad:
        raise SystemExit("库内状态与裁决记录不符 %d 条（前 5）：%s" % (len(bad), bad[:5]))
```

**三类都必须 `SystemExit`，不允许「打个警告继续跑」** —— 库与裁决不一致时继续写，
等于在错误前提上批量改数据。

⭐ **还须加第四类：事件对校验**（见坑 4）。**只校验 `edge_id` 在不在边集，挡不住跨快照错配**：

```python
    # 裁决文件须含 (from_event, to_event)；以事件对为跨快照主键
    drift = []
    for eid, it in verdicts.items():
        cur = edges_by_id.get(eid)
        if cur and (cur["from_event"], cur["to_event"]) != (it["from_event"], it["to_event"]):
            drift.append((eid, cur["from_event"], cur["to_event"], it["from_event"], it["to_event"]))
    if drift:
        raise SystemExit("edge_id 指向的事件对与裁决记录不符 %d 条（前 5）：%s" % (len(drift), drift[:5]))
```

⭐ **第五类：范围完备性**（2026-09-22 新增）。**只校验「清单里的边在不在」挡不住漏剔 / 误剔** ——
必须**反向**断言「集合的全集 == 清单」，**两个方向都封死**：

```python
    # 本轮的裁决范围 = 某个可机械判定的集合（如 cause/supersede∧weak∧conf<=0.6）
    actual = {e["edge_id"] for e in edges if in_scope(e)}
    want = set(verdicts)
    if actual != want:
        raise SystemExit("范围不完备：边集内该集合实为 %d 条，与裁决 %d 条不符\n"
                         "  漏剔（在边集不在裁决）：%s\n  误剔（在裁决不在边集）：%s"
                         % (len(actual), len(want), sorted(actual - want), sorted(want - actual)))
```

⭐ **第六类：处置白名单** —— 本轮只允许的处置（如全 `drop`）**逐条**校验：

```python
    bad_disp = [(eid, it.get("disposition")) for eid, it in verdicts.items()
                if it.get("disposition") not in ALLOWED]
    if bad_disp:
        raise SystemExit("裁决中存在非白名单处置：%s" % bad_disp[:5])
```

> ⚠️ **六类守卫必须全部写在 `preflight()` 内**，不得散落在 `load_verdicts()` 等外层函数里 ——
> 否则**单测 `preflight()` 时会被绕过**（见坑 9）。**守卫分层 = 覆盖缺口。**

## 第 2b 步：preflight 反向自证（不可省 —— 只证明「会通过」= 恒真探针）

**「干跑通过」什么都不能证明** —— 一个恒返回 `None` 的 `preflight` 也会「通过」。
必须**逐类篡改输入**，要求**每一类都真的拒绝**：

```python
import copy, importlib.util
spec = importlib.util.spec_from_file_location("arb", TOOL); m = importlib.util.module_from_spec(spec)
spec.loader.exec_module(m)
verdicts = m.load_verdicts(); edges, _ = m.load_edges()
by_id = {e["edge_id"]: e for e in edges}

def expect_reject(name, mutate):
    v, e, b = copy.deepcopy(verdicts), list(edges), dict(by_id)
    mutate(v, e, b)
    try:
        m.preflight(v, b, e)
    except SystemExit as ex:
        print("  ✓ %-24s 已拒绝：%s" % (name, str(ex).splitlines()[0][:70]))
    else:
        print("  ✗ %-24s **未拒绝**（守卫失效！）" % name)   # ← 必须让整体失败

# 逐类篡改：条数+1 / 塞不存在的 id / 改 cur_type / 改事件对 / 删一条(漏剔) / 加一条(误剔) / 改处置
```

**判据**：全部 `✓` 才放行。**本步实测价值**：首轮跑出 **6/7** ——
「处置白名单」没被拒绝（它只写在 `load_verdicts()`，单测 `preflight()` 绕过了它）⇒ 当场收口后 7/7。

## 第 2c 步：判据上线前先量 **基线发生率**（否则会把「图的共同属性」当「本批的缺陷」）

**触发场景**：你为某个**子集**（如待仲裁的 20 条）设计了一条机械判据，
发现子集里有 n 条"违规"，想据此**直接处置**。

**必做前置**：把同一判据**跑在全量**上，量它的**基数**。

**实测教训（2026-09-22，D-②）**：我把「`from_event` 与 `to_event` **同日**」当成
20 条待仲裁边的机械违规，准备直接剔除 3 条（`A2421`/`A3431`/`A5237`）。基数校验推翻：

| 判据 | 全量 8,475 边 | 占比 |
|---|---:|---:|
| `from` 严格早于 `to` | 7,229 | 85.30% |
| **同日** | **1,246** | **14.70%** |
| 倒序（`to` 早于 `from`） | **0** | 0.00% |

⇒ **同日边占全图 14.7%** —— 这是 `ts` **只到「日」粒度**造成的**系统性性质**，
　**不是**这 20 条的特有缺陷；**倒序为 0** 则说明铁律「from 早于 to」在**非严格意义上全图成立**。

⇒ **规则**：**若一条判据的"违规"在全量上普遍存在，它就不是这个子集的缺陷。**
　在子集上"发现"的违规数，必须与全量基数**同尺度比较**后才可解释。
　（**同族**：别把共同属性当个别缺陷；先量基数，再谈处置。）

⚠️ **同一手法还揪出一条更大的真池**（供项目方，不主张处置）：
「同日 ∧ `strong` ∧ `conf>0.6`」= **369 条** —— 这些**是**在参与多跳的，
影响面**远大于**本轮 20 条。⇒ 基数校验不但防误判，还能**发现真正的大池**。

## 第 2d 步：⭐⭐ 声称「判据 X 有效」前，必须给 **准确率 + 盲目基线**（只给召回率一律不算证据）

**触发场景**：你要用某条机械判据（元组可验证的，如 `D1`）**支撑「剔/保」的结论**，
或要**用它的判别力**去压缩人工判读量。

**实测教训（2026-09-23，`D1` 撤回）**：上一轮报告称 `D1`（`subject≠ ∧ object≠`）
「召回 89.5% ｜ 146 条 **+29.0pp**」⇒ 两次独立样本「方向一致 ⇒ 有效」。逐项现测后**全部不成立**：

| 复核项 | 报告值 | **现测值** | 判定 |
|---|---|---|---|
| R 档 20 条召回 | 89.5% | 89.5% | ✓ 一致 |
| **R 档准确率** | *未给* | **85.0%** | ❌ **< 盲目全剔基线 95.0%** |
| 146 条判别力 | **+29.0pp** | **+5.6pp** | ❌ 差 5.2 倍 |
| **146 条准确率** | *未给* | **60.3%** | ❌ **< 盲目全剔基线 68.5%** |

**+29.0pp 的根因 = 分组口径漏项**：报告把「不剔组」**只取 `keep`**（现测恰 **44.0%**），
**漏掉 17 条 `retype`**。而 `retype` 在 `apply_arbitration_146.py` 里**只改 `type`、不删边**（L107-114 / L178-179）
⇒ **属保留侧**；其 `D1` 命中率现测 **17/17 = 100.0%**。
⇒ 把命中率最高的一组排除在「不剔」之外，**必然人为放大差值**（`73.0−44.0=+29.0` vs `73.0−67.4=+5.6`）。

**两条必守规则**：

1. **三件套**：凡称「判据 X 有效」，必须同时给
   ① **准确率** `(tp+tn)/N` ② **盲目基线** `max(全剔, 全保)` ③ **二者之差**。
   **只给召回率 / 判别力 pp 的，一律不得作为有效性证据**（红线 16）。
   ⚠️ **「两次独立样本方向一致」≠ 有效** —— 两次都低于基线 = **一致地无效**。
2. **分组必须完备且互斥**：报「组间判别力」前，先证明「非剔组」= **`retype`+`keep`+`defer`+`promote`**
   （**不得只取 `keep`**）。分母口径漏一项，能把 **5.6pp 放大成 29.0pp**。
   （**同族**：红线 14「先问右边那张表是不是复合的」。）

⚠️ **连带**：若某「严口径」已被证明**逻辑等价于**该无效判据（实测 `¬(同subj∨同obj) ≡ D1`，220 条差 **0**），
则**它同样无效** —— 等价性一旦成立，二者的有效性**必须同生共死**。

⚠️ **自检提示**：当现测值与报告值差 5 倍时，**先怀疑自己也先算一遍另一种口径**
（本次正是把「剔 vs 全部非剔」与「剔 vs 仅 keep」**两种都算了**，才定位到是报告错，
而不是停在「大概是我算错」）。这属**红线 9 家族**，但**「怀疑自己」不等于「认定自己错」**。

### 坑 6：中文实体比对**不能用分词求交集**（会假阴性），但子串法也会**过报**

```python
if plan is not None:
    to_drop, to_retype, to_promote = plan[0], plan[1], plan[2]
else:
    bak = bak or latest_backup()

```

### ⭐⭐⭐ 铁律（2026-09-22 第三轮新增，最重要的一条）：**「机械复现引擎」在用于裁决前，必须先标定「逐条一致率」**

上面那条管的是**单条判据**的判别力；这条管的是**把多条判据拼成的整套裁决引擎**。

**触发场景**：你为一批待裁决边写了规则引擎（`if 自述否定→剔 / elif 同主体→保 / else→剔`），
跑出「剔 95%」这类**看起来很整齐**的结果 —— **此时不可上报，先做本检验**。

**检验方法**：把**同一个引擎原样**跑在**上一轮已裁决样本**上，
算**逐条一致率**（引擎判定 == 上一轮实际裁定的比例），并与**盲目基线**比：

```python
base = 上一轮实际 drop 数 / 样本数        # ← 盲目「全判剔」的一致率
# 引擎一致率 < base ⇒ 引擎比瞎猜还差 ⇒ 输出必须撤回，不得上报
```

**本轮实测（必须记住这个数字）**：

| 口径 | 档 | n | 引擎剔 | 实际剔 | **逐条一致率** |
|---|---|---:|---:|---:|---:|
| 严 | tier S | 92 | 98.9% | 77.2% | 78.3% |
| 严 | **tier A** | 54 | 24.1% | 53.7% | **29.6%** |
| 宽 | **tier A** | 54 | 16.7% | 53.7% | **37.0%** |
| 严 | 合计 | 146 | 71.2% | 68.5% | 60.3% |

**盲目基线 = 68.5%** ⇒ tier A 的 29.6% / 37.0% **都低于基线** ⇒ **引擎无判别力，输出已撤回**。

> ⚠️ **为什么会这样（根因）**：上一轮的剔边主线**不是**任何能从元组机械判定的东西，
> 而是 **`并列个案` / `对象漂移` / `逻辑搭桥`** 等**语义判据** —— 这类判据**必须逐条人工判读**。
> 试图用 `subject/object 字符串比较` 复现它，**方向必然错**。

### ⭐ 阈值型缺陷的**指纹识别**：看 `conf` 的**精确值分布**

若一条铁律要求「`X > 阈值` 才可入库」而**实现没做闸门**，被判为「不合格」的边会
**大量精确落在阈值本身**（因为判边器知道规则、倾向报阈值本想走 pending）。

**判据**：统计不合格集合的 `confidence` **精确值**直方图。本轮实测 `conf≤0.6` 的 1,379 条：

| `confidence` | 条数 | 占比 |
|---|---:|---:|
| **`0.6`（精确等于）** | **1,330** | **96.4%** |
| `0.58` / `0.55` / `0.5` / … | 49 | 3.6% |

⇒ **96.4% 贴在阈值上** = 「**有闸门缺失**」的强指纹（不是「判边质量差」的分布）。
⇒ 这比「有 20 条判错」严重得多：**1,330 条按设计就该被拦下的边落进了库**。

比贴阈值者**更可疑**（判边器给了明确低于阈值的值）⇒ **单独列为 tier S′ 全量审**，成本极低。

```python
# ② 反向核验：各节点的**全图**出入度是否恰为对方集合？
```

## 抽样方案设计（范围大但不想逐条时）

**口径**：先分层，再配额，最后层内抽样。**全程确定性**（不用随机数，任何人重跑同一结果）。

1. **分层**：沿用既有 `tier` 先例（`D10-仲裁结果-独立复核.json` 的 `tier` 字段）：
   - **tier S** = `type∈{cause,supersede} ∧ weak` —— **非法组合**（type 要求 strong）⇒ **全量**
   - **tier A** = `type∈{evolve,trigger,resolve} ∧ weak` —— 合法组合 ⇒ **抽样**
   - **tier R**（新增）= `strength=strong ∧ conf≤0.6` —— **反向矛盾**（先例未覆盖，量小）⇒ **全量**
   - **tier S′**（新增）= `conf < 阈值`（严格小于）—— **贴阈值者之外的「更可疑」子集** ⇒ **全量**
     （实测仅 49 条；其中 `cause/supersede∧weak` 仅 1 条 ⇒ 成本极低）
   > 设计逻辑：S / R / S′ 各仅 ~20–50 条却分别代表 **三类最尖锐的规范矛盾**（全量成本极低）；
   > A 是 1,339 条的合法组合、缺陷率预期低，故抽样。
2. **子层** = `type × corpus 群`（实测得 16 子层）。
3. **配额** = `sqrt` 分层（小池权重高，避免大群淹没小群）—— ⚠️ **上限 = 池大小**（见坑 7）。
4. **层内抽样** = 按 `edge_id` 排序后**等距系统抽样**（起点 `len/(2n)`、步长 `len/n`）。
5. **报精度**：`n=200` 时 p=0.5 的 95% CI ≈ ±6.9%。
6. **报覆盖面**：群数 / 类型数 —— **小层必须被覆盖到**（否则结论不能外推）。

**备选口径对比（须写明）**：直接对全池做随机/等距抽样会**丢失** S/R 两层的**全量**保证
（小层各有 ~1.7% 概率被抽中不足 5 条）⇒ **不建议**。

## 「可疑度 `sus`」评分（已复原，2026-09-22）—— 仲裁界面的排序依据

### ⚠️⚠️ 指标公式有「**适用域**」—— 换池子前必须重验区分度（2026-09-22 实测）

### ⭐ 方法：生成器脚本丢失时，如何重建（回归验证是硬要求）

界面/报表的**生成器脚本丢失**、只剩产物时，可重建 —— **判据是「能否复现原产物」**：

1. 找出产物的**数据注入口**（本项目：模板里的 `const D = window.__ARB__;` 一行）。

### ⭐ 方法：生成器脚本丢失时，如何反解出公式

**可复用的三步**（本轮实测有效）：

1. **找双份数据**：一份是**记录值**（如 `sus` / `span`），一份是**派生标签**（如内联进 HTML 的 `why`）。

2. **交叉制表**：`记录值 × 标签集合`。若每个取值都对应**唯一的标签组合**，权重即浮出水面
   （本例：4 个取值 ↔ 4 种组合，一一对应）。
3. ⭐ **用全量逐条复现作证** —— 把反解出的公式**重算一遍全部样本**，要求**零例外**；
   并单独验证中间量（本例 `span` 的定义也 146/146 复现）。

**实测**：判 `cause ∧ weak` 是否「非法」时，查到 `criteria` 原文含
「**weak 须有可从元组验证的同一具名主体/对象**」⇒ 按它，`A1207`（两端 `subject` / `object` 均不同）**应剔**。
但**更早的同类裁定**（`WEAK-POSITION-RULING-20260923.md`）已把 **weak 定位 = 检索线索层（宽口径）**，
并证明**严口径 ≡ 已被撤回的 `D1`**（220 条上不重合 **0** 条）⇒ 那条要求**不适用**。
⇒ **照 `criteria` 原文判，会得出与既有裁定相反的结论。**

**三条纪律**：

1. **用前先溯源** —— `grep` 该判据是否已被后续文档**取代 / 撤回 / 修订**（本项目已有
   「裁定前先查有没有更早的同类裁定」的既有纪律，本条是它在**判据文本**上的落实）。
2. ⚠️ **文本未同步修订 ⇒ 必须登记「残留不一致」**：实测 `criteria` 字段**文本至今保留**该条，
   而裁定只是「**建议**」、**无正式废止** ⇒ **哪份优先未被书面确认**。
   ⇒ **凡结论依赖该口径，必须把「该条是否废止」写成结论的显式前提**，不得默认成立。
3. **判据强度要分级** —— 同批对象可能「非法」的依据不同：实测 `cause ∧ weak` 有**定义级**矛盾
   （`cause` 要求「有人明确说了原因」 vs `weak` 要求「无明确因果句」⇒ 两处定义互斥），
   而 `supersede ∧ weak` **没有**（其定义「方案/版本被替换」**不排斥** `weak`），
   **只有「不在表内」这一条** ⇒ 两者处置依据**不能混为一谈**（一个可剔、一个判据不足）。

### ⭐ 坑 26（2026-09-23 新增）：「补充表」不得当穷尽表用 —— 判「某组合非法」前先找**规范自身的反例**

**实测**：v2.1 的「判型映射**补充**」表只有 4 行。若当穷尽表用，则
`trigger ∧ strong` / `evolve ∧ strong` / `resolve ∧ weak` / `resolve ∧ strong` 等**全属非法** ——
**全库 1,243 条（14.7%）**。但 v2.1 **自身的示例 3** 就是 `"type": "trigger", "strength": "strong"`
（= 表外组合）⇒ **该表确定非穷尽** ⇒ **「不在表内」不能单独构成「非法」**。

**判据**：凡要按「**不在某表内**」定性非法，**先去规范里找该表之外的合法示例**；
找到 ⇒ 该表非穷尽 ⇒ 必须改用**定义级**判据（如两处定义互斥），或**把它上升为口径裁定**。

### ⭐ 坑 27（2026-09-23 新增）：能把「暴露面」**先验算出**的维度，就先登记**预注册预测**

**实测**：`timeline` 的暴露面**不必跑遍历**即可算出 —— 其实现 = 「取该 subject 的事件 + 列出各事件**全部**关联边」，
且 subject 过滤是**子串匹配**（`subject not in ev["subject"]`）⇒ 用 SQL 就能算出「受影响 subject = **10 / 1,142**」。
⇒ **写在看到任何探针结果之前**（真·预注册），随后被实测证实 ⇒ 比「事后比对」强得多。

**配套**：能**独立算两遍**的量，就用**两条代码路径**各测一次 —— 实测两处**精确相等**
（`why` 的 **103** == 独立探针的 **103**；`chain_recall` rev0 的 **3** == **3**）⇒ 互证探针无系统偏差。
