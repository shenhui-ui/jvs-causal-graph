15. **判边质量不能用启发式自动裁决，也不要拿另一个模型当"更高召回"的证据**：
    实测同一批 60 对：
    - `glm-5.2` 判定率 **35%–67%**（保守）
    - `deepseek-chat` 判定率 **60/60 = 100%**，且理由自陈
      「同属…主线推进，**但原文无明确因果句**，属弱关联」——
      **它承认没有可验证因果却仍判边，违反提示词铁律**，已退化为「时间+话题邻近」基线。
    另外两个坑：**(a)** 交叉核验脚本用 `max_tokens=8192`，长批被截断 → 静默 `[]`
    → 会得出「两模型不一致」的**假结论**（提到 32768 后 glm 边反而是 DeepSeek 的子集）；
    **(b)** 用「事件对是否带 `变更:由「…」→…」差分」当高置信判据**会过度标记** ——
    差分只说明 `to` 是 change，不代表与 `from` 有语义关联（实测标出的对 from/to 毫无关系）。
    **(c)** 这种「自承无因果却仍判边」的违规**不是个例，而是普遍现象** ——
    用正则扫 rationale（`无明确因果|未明示因果|弱关联|同主题|同属.{0,6}主题`）统计：
    **glm 81.4%（3,717/4,568）、flash 65.0%（3,360/5,171）** 的边带有此类自承措辞。
    ⇒ 判边产物**必须人工抽检 + 仲裁**，任何"自动判质量"的尝试都会得出不可信的结论。

15b. **两通道的「补跑清单」可能因判据取自对方而整体漏跑**（2026-09-18）：
    `build_todo.py` 用 **glm 产物**当「已完成」判据，于是 flash 只跑了「glm 缺的部分」，
    **glm 已成功的 482 批从未用 flash 跑过** —— 直接合并会悄悄让这 482 批走 glm 口径
    （异质通道，且恰好全是**低批号＝闸口段优先**的关键批）。
    ⇒ 做双模型对照时，**清单必须按「目标通道自身产物」构建**，
    否则不是"两模型都跑了"，而是"各跑了一半"。

16. **`reasoning_effort` 会被官方封装静默吞掉 —— 这是判边截断的头号根因**（2026-09-17）：
    服务端合法枚举是 **`low / medium / high / xhigh / none`**（传 `minimal` 会 HTTP 400 并
    在报错里列出枚举）。但官方 `relay_call.chat()` 的过滤是：
    ```python
    if reasoning_effort and reasoning_effort not in ("none", "off", "false"):
        body["reasoning_effort"] = reasoning_effort
    ```
    —— 它把**合法的 `"none"`（= 关闭思考）和 `"off"/"false"` 一起滤掉**，
    请求悄悄退化成「默认思考」。长批上推理膨胀到 **9 万字符**、撞 `max_tokens` 截断，
    **永远拿不到 JSON**（实测 `reasoning_effort="none"` 让同一批从 6.1 min 降到
    **0.6 min**，`finish_reason` 从 `length` 变 `stop`，JSON 完整）。
    **凡遇「回包全是推理文字、没有 JSON」，先检查 effort 是否被吞。**
    但注意：`none` 会改变判边尺度 —— 实测同批 `glm(low)` 判出的边，
    `flash-lite(none)` 只认 **14%**，**跨模型/跨档位混用会破坏图谱口径**。

16b. **★ 判边参数完整清单 —— 脚本默认值全是错的，必须显式覆盖**（2026-09-18 实操踩坑）：
    `run_d10_judge.py` 的 argparse 默认值是「通用占位」，**与任何真实基线都不符**：
    ```
    --model   默认 glm-5.2      ← 基线是 sensenova-6.8-flash-lite
    --temperature 默认 0.2      ← 基线是 1.0
    --reasoning-effort 默认 low ← 基线是 none
    --max-tokens 默认 16384     ← 基线是 32768
    --timeout 默认 300          ← 基线是 1800（300 会导致长批 TimeoutError！）
    ```
    基线 flash-lite 判边的**唯一正确调用**（出自 `build_flash_fill.py` 的 `params`，
    并已回写进 `write_plan.py` 注释）：
    ```
    --model sensenova-6.8-flash-lite --reasoning-effort none \
    --temperature 1.0 --max-tokens 32768 --timeout 1800 --workers 4
    ```
    **血泪教训**：本轮先按默认值（temp=0.2/effort=low/timeout=300）跑，
    批 1 直接 `TimeoutError: read operation timed out`（15 min 白烧），
    且批 2 虽成功但**参数异质**，属口径污染，必须整批重跑。
    ⇒ **跑任何判边前，先 `grep -n params` 上游清单文件确认六个参数**，
    不要相信子命令默认值。**参数错的产物不是"差一点"，是会污染整张图谱。**

16c. **★★★ 判边执行器必须用 `run_judge_v2.py`，不能用 `run_d10_judge.py`**（2026-09-18 双重踩坑）：
    两个脚本都能"跑判边"，但**底层通道不同**，结果天差地别：
    | | `run_judge_v2.py`（✓ 基线） | `run_d10_judge.py`（✗ 会吞 effort） |
    |---|---|---|
    | 调用 | 自带 `call()`，`if effort:` **原样透传** | `relay_call.chat()` |
    | effort | `none` 真能关掉思考 | `none` 被过滤 → **退化成默认思考** |
    | 长批 | 0.6–3 min 出 JSON | 推理膨胀撞 32768 顶 → **`empty reply` / 超时** |
    实测同一批（批 1，60 对）：走 `run_d10_judge` 连续两次失败
    （`TimeoutError` → `empty reply`，两次共烧 **38 min**，`reasoning_tokens=32768` 撞顶）；
    换 `run_judge_v2.py` 才正常。
    - `run_d10_judge.py` 的价值仅在 **`--prep`**（生成 prompt，确定性零 API）。
    - **执行一律走** `run_flash_round.py`（内部调 `run_judge_v2.py`）或直接调 `run_judge_v2.py`。
    - 两者**产物命名也不同**：`run_judge_v2` 写 `batch_%04d.result.txt`（4 位），
      `run_d10_judge` 写 `batch_%03d.result.txt`（3 位）—— 混用会导致断点续跑误判「未完成」。

17. **档位阶梯与窗口预算：判得多少随思考强度单调上升**（2026-09-17）：
    同一批 `batch_026` 实测（`probe_flash_params.py`）：

    | 档位 | 推理长度 | 判出边 | 耗时 |
    |---|---|---|---|
    | disable-thinking | 92,871 | **失败**（撞上限无 JSON） | 6.1 min |
    | 默认（无 effort） | 73,526 | 5 | 3.6 min |
    | `none` | 1 | 6 | **0.6 min** |
    | `high` | 81,614 | 11 | ~5 min |
    | `xhigh` | 45,947 | **14** | 3.3 min |

    **思考越充分 → 判出的边越多**。`none` 提速 10 倍但有真实质量损失。
    **注意 `max` 不是合法档位**（实测 400 拒绝）——合法枚举只有
    `low/medium/high/xhigh/none`。

    **窗口预算**：flash-lite 限额 **1500 次/5h**，但瓶颈是速度而非调用数。
    实测 4 并发下 `xhigh` 约 **38 批/h**（含限流重试），故
    **223 批闸口段 ≈ 5.9h、全量 1,175 批 ≈ 31h**。若窗口只有 5 小时，
    **必须按解锁增益排序跑闸口段**，不要顺序跑全量。

18. **别把「与基座模型一致」当成判边质量基准**（2026-09-17 重要）：
    项目既有文档 `docs/M1-LLM判边模型对比-20260831.md` 早有定论 ——
    glm-5.2 偏「**激进**」（几乎全判 strong）、flash-lite 偏「**克制+多样**」
    （有差分才 strong，且**唯一识别出 supersede**），
    文档判断 **flash-lite「更贴 v2.1 设计意图」**、glm「可能 over-strong」。
    实测 glm 全量 strong 占比仅 **9.1%**（偏 weak 一侧，判得多）。
    ⇒ 两模型**口径不同但无绝对优劣**，「Jaccard 低」不等于「差」。
    **正确定版流程是「两模型对照 + 人工仲裁」**，不要用启发式自动裁决，
    也不要为「对齐 glm」而牺牲判得细的模型。
    **产物必须物理隔离**（如 `out_glm/` 与 `out_flash_xhigh/`），保留两套可比结果。

19. **判断「数组是否完整」只能靠括号配对，绝不能看文件结尾形态**（2026-09-17 三次踩坑）：
    推理型模型的回包**常常是「完整 JSON 数组 + 后面继续写推理散文」**。
    实测三个 raw 回包体积 76KB/90KB/100KB，**都不以 `]` 结尾**，
    但数组**个个完整**，`]` 之后还有 4,238–4,851 字符的散文。
    我因此连判三次「截断率 30%」——全错，**真截断 0 批**。
    **唯一正确判据：括号配对闭合（含字符串状态机处理转义）+ `json.loads` 可解析。**

20. **同一回包内模型会反复输出多次数组 —— 必须取「最后一个」**（2026-09-17）：
    推理模型常在「Let me format:」之后重来一遍。实测 `batch_0118` 一份回包里依次
    给出 **4 条 → 4 条 → 3 条**三个完整数组，**最末的 3 条才是最终答案**。
    若解析器取**第一个**数组，就会拿到中间草稿（少判/错判且无任何报错）。
    ```python
    cands = []          # 扫描所有候选起点的完整闭合数组
    ...
    return cands[-1]    # 取最后一个 = 最终答案
    ```

21. **`temperature=1.0` 下不要用单批抽样推断档位规律**（2026-09-17）：
    同一批同一档位实测两次：`xhigh` 一次 14 条、另一次 5 条。
    因此据单次结果得出的「思考越充分判得越多（none 6 → high 11 → xhigh 14）」
    **是抽样噪声，不成立**。要比较档位必须多批重复取样。
    另外注意推理型模型必须 `temperature=1.0`，方差天然很大。

22. **判断「批任务是否还活着」只能看产物增量，绝不能信 `tasklist`**（2026-09-17）：
    我据 `tasklist | grep python` 返回空，判定跑了 9 小时的 glm 批任务已死，
    **实际它一直活着、并在 1.5 小时后正常结束（总时长 9h35m）**。
    → 本沙箱下 `tasklist` 会给出**空结果**（权限/隔离所致），`PowerShell Get-Process`
    也可能静默失败。**唯一可靠判据**：
    ```bash
    find <outdir> -name "*.result.txt" -newermt "-3 minutes" | wc -l   # >0 即存活
    ```
    误判的代价很实在：我据此错误决策、并误以为「通道已死」，
    而真因是**它用 `workers=8` 占满了同一 endpoint 的 `tpm/rpm`**，
    导致我另起的 flash 请求频繁 429 —— **多通道打同一网关时必须错峰或限并发**。

23. **`[]` 是人类可读的合法判定，不是空回包 —— 别把「小文件」当「故障」**（2026-09-18 更正）：
    ⚠ **本条此前写反了，务必按新版执行。** 旧版称「所有 `[]` 都是 2–4 字节空回包，
    该模型从未真实判定过本批无边」——**错误**。逐字节开箱核对（`raw.strip() == "[]"`）
    后事实是：

    | 通道 | 有边 | **真·空数组 `[]`** | 真·空回包（0 字节） | 破损 |
    |---|---|---|---|---|
    | `out_glm` | 605 | **265** | **0** | 75 |
    | `out_flash_none` | 596 | **579** | **0** | 0 |

    `[]` 恰好 2 字节，若用 `size <= 4` 分桶就会**整批误判成故障**（我上一轮即如此，
    凭空多报 265/579 个「空回包」）。**判据必须是内容而不是体积**：
    - `raw.strip() == "[]"` → **合法判定「本批无因果边」**，可入库、**不要重跑**；
    - 文件 0 字节 / HTTP 无 body → 真空回包，**需重跑**；
    - 有内容但括号不闭合 → 破损，**需重跑**。

    推论：**「有效覆盖」应把「有边」与「明确判空」都算上**。实测两通道并集
    = **1,657 / 1,657 = 100%**，**零缺口、无需补跑**；若按旧版只算「有边」，
    会误以为有 535 批缺口而发起大量无效调用。

24. **判边质量要按「双模型交叉对照」评，单看完成率会选错通道**（2026-09-17）：
    同一套 352 批上，glm-5.2 与 flash-lite 的状态交叉：

    | 组合 | 批数 |
    |---|---|
    | (glm 空回包, flash ok) | **112** |
    | (glm 破损, flash ok) | **54** |
    | (glm 空回包, flash 空回包) | 111 |
    | (ok, ok) | 32 |

    **仅 flash 可信 166 批 vs 仅 glm 可信 22 批** —— 看似"慢/弱"的 flash
    在对方失效的批上补回了 **7.5 倍**的量，且**破损率 0**（glm 有 75 批破损）。
    ⇒ **不能只看「谁跑得快/谁判得多」选通道，要用交叉对照看谁在对方失效处补得回。**
    另外：两模型在 **110 批上独立同判空**，说明这些批**数据本身确实无边**
    （60 对语义上无可验证因果），**不要误当成故障去重跑**。

24b. **★「完成率对照」≠「结论一致」：两模型边级 Jaccard 仅 0.27**（2026-09-18）：
    条目 24 只比了「批状态是否 ok」，**没比「判出了哪些边」**。补做全量
    边级集合运算（`_staging/compare_flash_glm_full.py`，**零 LLM 成本**——
    两套产物都已落盘，别对每批重跑 flash），在**双方均 ok 的 406 批**上：

    | 指标 | 值 |
    |---|---|
    | glm 边 / flash 边 | 3,335 / 3,996 |
    | 交集 | 1,558 |
    | **整体 Jaccard** | **0.2699** |
    | 完全一致的批 | **仅 10 / 406** |
    | 零共识批 | 52 |
    | `type` 不一致 | **38.1%** |
    | `strength` 不一致 | **30.6%** |

    **⇒ 两个判边模型在语义层面几乎不重叠。** 互不为子集（覆盖率均 <0.5）。
    - `strength` 分歧**高度不对称**：`glm=weak→flash=strong` **425 条**，
      反向仅 51 条 ⇒ flash 确实更激进。
    - `type` 主要分歧是 `evolve↔trigger` 互相错认（188 + 130 条），
      **说明这两个"最软"的类型边界本身就模糊**。
    - **混用两套产物 = 把 Jaccard 0.27 的两套判断合并**，

    （prompt 末尾明说「填原始事件 id（`|` 前的部分）」）。
    直接拿 prompt 文本与 result id 比对 ⇒ **100% 被误判为"越界"**的假结论。
    **必须先截 `|` 前部分再比**。做完这步，越界率 glm 0.0% / flash 1.4%，
    才证明「两模型在同一候选集上判边」这个**前提成立**。

25. **入库前必须校验 `type` 字段是否在合法枚举内**（2026-09-17）：
    合法枚举仅 **`cause / supersede / evolve / resolve / trigger`**。
    实测 flash 有 **5/5,171（0.1%）** 条边把 `strength` 的值误填进 `type`
    （`weak`×3、`weak_relation_placeholder`×1、`change`×1）。
    量小但会让下游图库出现非法类型，**`merge` 前必须清洗**。
    清洗口径（2026-09-18 定案）：`weak*` 类**丢弃**（其 rationale 自陈"仅弱关联"，
    属违规伪边）；`change` **映射为 `supersede`**（语义即"前者被后者取代"）。
    ⚠ **必须在 `merge` 之前改源文件**：`merge` 按 `(from,to)` 去重且"保留首个批的边"，
    若非法边留在源文件里，它可能先占住某个键，把另一批里同一对的**合法**边挤掉。

26. **批量打同一网关时并发本身就是限流源 —— 必须全局节流 + 429 指数退避**（2026-09-18）：
    实测 `workers=4` 打 flash-lite 时**首个请求即 429**
    `{"message":"inference exceeds tpm/rpm limit"}`，5 分钟只成功 6 批
    （rejected 累积 **132** 个，其中 **96 个是 attempt0**＝从未成功过）。
    关键算式：每批 prompt≈**10.3K tokens**，`workers=4` ⇒ 瞬时 ≈ **41K tpm** 就超限。
    **串行两次同批 prompt 全部成功（31s / 21s）** ⇒ 确认是并发而非长 prompt。
    解药（`run_judge_v2.py` 已有 `--workers 2 --min-interval 3`）：
    - **跨线程全局节流闸**：保证任意两次**实际发起**的请求间隔 ≥ `min_interval`；
    - **429 指数退避** `15 * 2**attempt`（原固定 3s/10s 太短，会连续被拒）；
    - 实测 `workers=2 + min_interval=3` ⇒ **rejected = 0**。
    ⚠ **实现坑**：节流的 `time.sleep` 必须写在**锁外**（锁内只做原子更新）。
    若 sleep 写在锁内，持锁线程会把其他线程全挡住，**多线程退化为单线程**
    （实测 workers=2 时仅 90 批/h），表面上"没有报错"却极慢。
