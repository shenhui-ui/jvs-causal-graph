# 陷阱 11–14、27–28：检索与抽取

> **本页是技能 `jvs-graph-question-compatibility` 的附页**（2026-09-20 从 `SKILL.md` 拆出，**内容逐字未改**）。
> **何时读**：改检索 / 抽取层、评估抽取质量时（27–28 为抽取类，故归此页）。
> 入口、三步核验流程、第 4 步与全部附页索引见 `SKILL.md`。

11. **检索污染：把非题群语料一起录入图谱会毁掉锚点召回**。实测同日：
    D10 全 12 群（3,732 事件）→ 有边锚点题 **5/10**；仅 7 个题群（1,648）→ **10/10**，
    **候选对与批数完全相同（99,388 / 1,657）**。机制：`G01` 1,681 事件（45%）且日期密集，
    题面日期串被 `extract_keywords_v2` 切成 `2026081` 这类 n-gram 后在 G01 大量命中，
    top3 检索被挤占。**结论：事件表只录「题目所在的语料群」**；要通用图谱就另建一份、别混用。
    > 注意区分：`coref`/`semantic` 通道的候选**比较范围**受语料影响，但本次两侧
    > 入选的 99,388 对恰好一致（cap 边界所致），故此语境下「候选集 == 边集」。

    > **根因已定位（2026-09-17）**：真正的杀手是**题面数字碎片**。
    > `_search_text(e)` 含事件 `ts`，而题面日期 `2026-08-12` 会被切成
    > `-0` `02` `08` `20` `26` `6-` `8-`，**能匹配任意事件日期串**，
    > 使无关事件把 2-gram 命中数 `bh` 刷到 6~8，真值（`bh=3`）被压后。
    > 实测 H10：真值 `G14-C02-0023` 确在候选内，属**排序权重**问题而非召回失败。
    > 修法：`_drop_digit_grams`（**只剔纯数字**；去含数字会伤基线，位次0 27/30→25/30）
    > + hybrid 排序键 `(kh,bh)` → `(kh,prox,bh)`。12 群 5/10→**10/10**、基线零损失。

11b. **首位落块 ≠ 评测指标；平局胜负由语料行序决定，无语义依据**（2026-09-18）：
    补抽后（1,648→1,655 事件）复核，D5 定案收益保持（题级命中 10/10），
    但**首位落块仍 9/10**（H10）。真实根因：
    - 现行 hybrid 键是 `(kh, 有日期标志, prox, bh)` —— **不含 `type`**。
      别把 `retrieve_top` 的 `(hits, pref, ts)` 键结构套到 hybrid 上（pref 才是类型偏好）。
    - H10 在 1,655 事件上候选集仅 **10 个 / 8 个不同键**，**top-1 键 `(1,1,0,3)` 恰 2 事件平局**：
      `G11-C02-0031`（G11 群）与 `G14-C02-0023`（G14 群，gold 块）。
      **四分量全等 → 平局由输入顺序（stable sort）决定**，G11 在语料前段故排前。
    - 两事件**不是重复数据**：不同 corpus、不同 `source_hash`，
      是**两份独立来源记录同一件事**。→ 这类冲突无法靠"去重"解决。
    - **平局非孤例**：10 题中 top-1 平局出现 2 次（H04、H10），
      两题本块均只占 1/2，**H04 恰胜、H10 恰败 —— 胜负纯靠行序**。
    - **判断是否有实质后果，回去看判分明细而不是猜**：H10 判分
      `cause=false/effect=true/evidence_hint=true`，其官方 type=「证据定位」（**本身不问原因**），
      cause=false 属题型预期；且**模型答案两侧都引用了**、真值 2 事件**已进 top-3**。
      ⇒ **首位落块是诊断指标，不是评测指标** —— 别把它当失分来汇报。
    - tie-break 干跑 3 方案（尾键追加于 prox 后），**均使 H10 首位修好且基线零退化、零序列变化**：
      `subject` 长度 / `type` 因果优先 / 同群优先。
      ⚠ **「同群优先」不可用** —— 需读 `questions.json` 的 `group` 字段，
      等同把答案位置喂给检索，违反既有泄漏边界。
      方案间差异对基线**毫无影响**（基线 30 题无 top-1 平局），说明修法只作用于极少数退化情形。
    - **经验**：任何排序键变更都属**检索层口径变更**，须同步报告口径说明 + 重跑回归；
      收益仅为「诊断指标 +1」时不值得，如实上报更合规。

12. **改检索层前必须确认真实调用路径**（2026-09-17 踩坑）：
    `prepare_question` 的主路径是 **`retrieve_hybrid`**，不是 `retrieve_top`：
    ```python
    anchors = retrieve_top(events, kws, k=3)
    if os.environ.get("LLM_RETRIEVE_HYBRID", "1") != "0":
        anchors = retrieve_hybrid(events, kws, q.get("question",""), k=3) or anchors
    ```
    `LLM_RETRIEVE_HYBRID` **默认开**且已并入默认管线（见
    `M1-10-总收尾报告-20260903.md`「定版 V1H = EXPERT + 链排序 + 混合检索」）；
    实测基线 30/30 题、D10 10/10 题**全走 hybrid**，`retrieve_top` 仅兜底。
    **原 `retrieve_hybrid` 排序键是 `(kh, bh)`，没有 `ts`** ——
    曾据 `retrieve_top` 的 `(hits, pref, ts)` 降序推断「日期越晚越靠前挤掉真原因」，
    在真实路径上不成立。**诊断对象错了，结论必然错。**

13. **n-gram/关键词抽取要检查数字碎片**：`extract_keywords_v2` 对含日期题面会抽出
    60+ 个 n-gram，其中数字碎片（`2026081` `0260812` `60812前` `-0` `02`）占比极高。
    凡题面含 ISO 日期，先跑一次片段分解（列出纯数字/含数字片段及其命中分布）
    再决定过滤强度。

14. **判边批产物的「完成度」会骗人 —— 必须做质量稽核**（2026-09-17）：
    `s4_pipeline.extract_array` 在解析失败时**静默返回 `[]`**，与「模型判定本批无边」
    **不可区分**。实测 743 批里只有 **482 批（64.9%）**可信：
    - **194 批是 2 字节文件，内容就是 `[]`**（26.1%）
    - **46 批 JSON 被截断**、21 批无数组括号（合计 9%）
    坏产物**根因不是网络**，而是**思维链泄漏进 `content`、真 JSON 未输出完**：
    ```
    " to G14-C02-0017. There's no direct pair"     ← batch_1524 / 69,602 B
    "Let me list them: 1, 2, 3, 4, 7, 8, "         ← batch_0614 / 61,812 B
    ```
    且失效在时间上**均匀分布**（与 `ok` 批次逐 5 分钟交错），说明是**逐次请求随机失败**，
    不是通道劣化。**别用完成批数当进度**：先按 `(可解析非空 / 空数组 / 截断 / 无数组)`
    四分，再谈进度。

14b. **`strength` 字段与 `confidence` 是两套口径 —— 且模型的自我矛盾正好可当抽检排序信号**（2026-09-18）：
    ⚠ 先分清两个**不是同一概念**的东西，混用会得出错误结论：
    - **边自带的 `strength` 字段** = 模型主观标注（实测 weak **6,603** / strong 1,924）；
    - **`s4_pipeline.report` 的 `strength_of(confidence)`** = 由 `confidence` 阈值
      0.6 派生（strong 815 / medium 6,333 / weak 1,379）。
    两者数值差异很大**不是数据错误**，别据此判定脚本有 bug。

    **真正的发现**：交叉两者后暴露模型输出的**自相矛盾** ——
    **61.5%（5,244 / 8,527）的边「自评 `weak`，却给出 `confidence > 0.6`」**，
    其中 **79.7%（4,180 条）** 的 rationale 明确写着「无明确因果句 / 弱关联 / 同主题」。
    样例：
    ```
    A012 evolve conf=0.62 strength=weak
         "…同属采集准备主题，但无明确因果句，判弱关联。"
    A021 evolve conf=0.65 strength=weak
         "…为同主题推进，但无明确因果句。"
    ```
    （反向 `strong ∧ confidence≤0.6` 仅 **20** 条，可忽略。）

    **正确用法**：`strength == "weak"` ∧ `confidence > 0.6` 几乎必然是
    「主题邻近伪装成因果」的伪边，可作为**人工抽检的优先级排序**（优先复核这 5,244 条）。
    ⚠ **但不可据此自动过滤/裁决** —— 见陷阱 15（自动判质量会得出不可信结论），
    且该组合里仍可能混有真实但表达保守的边。

27. **★「丢因保果」：抽取阶段会丢掉根因消息、只留措施，而证据链看起来仍然完整**（2026-09-18）：
    这是**最难发现**的一类缺陷，因为它**不在判边层、也不表现为任何报错**。

    实例（D10-H01「为什么把火山 TOS 带宽从 5G 提到 15G」）：
    原始语料 `G03-chunk01.payload.txt` 明确含根因：
    ```
    [2026-05-26 00:17] G03-P07：以前数据和算力都在火山 走的基本是内网。
                       现在算力往阿里迁移 就会有大量的走外网读取和写入，把外网的带宽占了。
    [2026-05-26 00:18] G03-P07：这两天的网络问题 归结到一起 都是这一个原因
    [2026-05-26 00:19] G03-P07：当前 降低阿里pod数 + 扩充公网带宽 + 拉专线 在同步推进中
    ```
    抽取结果：**只把 `00:19` 的「措施」抽成事件**（`G03-C01-0014`），
    `00:17`/`00:18` 的**根因未抽成任何事件**。

    **验证手法（可直接复用）**：对 gold 的 `cause` 取特征词，在事件集里搜 ——
    实测 `归结`=0、`带宽占了`=0、`内网`=0、`外网`=0、`迁移`=**0 条命中**。
    ⇒ 根因在抽取结果中**完全不存在**。

    **为什么难发现**：
    - `evidence_hint` 指向的事件**全部存在**（9/10 题 4/4、5/5、6/6 全 OK），
      粗看「证据链完整」，实则块内已丢因；
    - 判边层无责（根因事件不存在，自然不可能有指向它的边）；
    - 生成模型会**转而引用时间更晚的事件当原因** ⇒ 产出「因果方向反了」的答案，
      看起来像模型能力问题，实为上游数据缺陷。

    **口径影响**：该题因果准确率被**结构性判死**。若计入分母，会**同时低估
    图谱能力与生成能力** —— 属**评测设计缺陷**，须在报告中单独标注、不可与
    正常题并列解读。

    **排查方式（可复用脚本 `_staging/audit_cause_gap.py`）**：
    对每题 gold 的 `cause` 抽**实义关键词**（扣除 effect 共有词），
    分别回搜**原始语料 payload**（抽取输入）与**事件集**（抽取输出）：
    - 语料命中 ∧ 事件命不中 ⇒ **该信息在抽取阶段丢失**；
    - 逐题统计 `cause_kw_in_payload` vs `cause_kw_in_events`，落差大即为缺口。
    实测：H01 cause 词 14 个，语料命中 10、**事件仅命中 1** ⇒ 缺口确认；
    H07 报疑似但人工核验为**误报**（丢的是通知标题，与处置同句，非独立根因）
    ⇒ **关键词命不中必须人工复核**，避免把同句标题误判成丢因。

    **排除「分块截断」**：核对该消息在 payload 中的行号（H01 为第 **185** 行，
    文件中段非 chunk 边界），且同时间前后的消息均被正常抽取
    ⇒ 是**抽取模型漏抽**，不是输入被截断。

    **抽取比是高危土壤**：7 题群原始消息 **12,874** 条 → 事件 **1,648** 条，
    抽取比仅 **0.128**（各群 0.077–0.211，**G03 最低**，正是 H01 所在群）。
    抽取模型倾向保留**结论性/决策性**消息（措施、变更、安排），
    丢弃**诊断性/解释性**消息（原因、背景、推论）—— 这正是「丢因保果」的成因。
    ⇒ 语料抽取比越低，越要逐题回归核验根因是否入库。

    **★修复手法：定向补抽（不要原样重跑整份 payload）**

    原样重跑必复现同样结果 —— 因为病根在**提示词的 type 枚举**
    （只有 `decision/change/meeting/commit/bugfix/schedule/assign`，
    **没有"原因/诊断"类**），铁律 5 又要求「疑似编造/情绪/祈使/感想类
    直接输出 `[]`」。**必须改变输入条件**才可能抽出根因。

    正确做法（脚本 `_staging/refill_g03_cause.py`，可复用）：
    1. **保留原 payload 的「角色/输出要求/type 含义/铁律/示例」段**
       —— 保住 schema 不变，新增事件才能与既有事件集同构可比；
    2. 把「待抽取文本」**替换成聚焦窗口**（H01 = `05-25 23:44 ~ 05-26 16:19`，
       44 条消息 / 6.2K 字符），而不是喂全量 271 条；
    3. 在「附加说明」里**显式声明**：
       - 「解释某现象为何发生」的陈述属**客观事实**，不得按铁律 5 丢弃
         （判断依据是「是否在陈述成因」，不是「是否带情绪词」）；
       - 此类事件 `type` 一律填 **`change`**（合法枚举里没有 cause 类，
         `change` 是语义最贴的落点），`action` 填「导致」/「变更」；
       - `before`/`after` 必须**值级**（`before`=变化前状态，`after`=变化后状态）；
       - `subject` 写**被影响的对象/系统**（如「外网带宽」），不写发言人。
    4. 模型与参数**完全沿用原抽取**：`deepseek-v4-pro` / T0.2 / `max_tokens=32768`
       / `reasoning_effort=low` —— 换模型会破坏与既有事件集的可比性。

    **合并时必须守的约束**（脚本 `_staging/merge_refill_events.py`）：
    - 新增事件**沿用原块号**（`G03-C01-`）并从块内最大序号顺延
      —— 这样 gold 的 `block` 前缀口径**完全不变**，`evidence_hint` 仍能对上；
    - 新增事件打 `refill: true` 标记 + 保留模型原始编号（`orig_event_id`）便于溯源；
    - 写入**新目录**（`out_refill_g03/` + `graphR2p-refill/`），
      **绝不覆盖**既有 `graphR2p/` 与 1,657 批判边产物。

    **验收判据（脚本 `_staging/verify_refill.py`，三层）**：
    ① 事件层 —— 新事件是否命中成因词（`内网|外网|迁移|阿里|火山` ≥2 个）。
       ⚠ **判据不要过严**：H01 根因是**两条**消息，`00:17` 讲「算力迁移→走外网
       读写」（**object 不含「带宽」**）、`00:18` 讲「都是这一个原因」。
       强制要求命中「带宽」会漏判第一条 ⇒ 实测漏掉 `G03-C01-0022`。
       故用 `≥2 成因词 ∧（命中关键对象 ∨ ≥3 成因词）`。
    ② 语料层 —— 新事件关键词回搜原文，做**反幻觉校验**（对齐「0 编造边」口径）；
    ③ 可达性层 —— 根因事件与锚点事件**两端齐备**（判边能产出 cause 边的必要条件）。

    补抽只产出**事件**，不自动进入已判边图谱。要生效必须走完：
    `补抽 → 并入 d10-events → 重算候选对（stage_d10_graph.py）→ 判边
     → 重建图谱 → 重新生成`。

    **★★★ 最致命的坑：新事件的「插入位置」决定因果方向（写错 = 白补 + 更糟）**

    `s4_pipeline.channel_adjacency` **只按日期排序**：
    ```python
    known = [(e, day(e.get("ts"))) for e in evs]   # day() 只取到「日」
    known.sort(key=lambda x: x[1])                 # 同日事件靠 stable sort
    ```
    即**同日事件的先后完全由文件里的原始顺序决定**，而事件的 `ts`
    **只精确到日**，**无法区分同一天内的先后**。

    H01 恰好踩满这个坑：根因在 `05-26 00:17`、措施在 `00:19`、
    锚点在 `16:15` —— **三者同为 `2026-05-26`**。

    实测三种插入方式（同一份事件，只改位置）：

    | 插入方式 | `根因 → 锚点0015`（需要） | `0015 → 根因`（反向，错的） |
    |---|---|---|
    | 追加到文件末尾 | ❌ 0 条 | ✅ 1 条 |
    | 只按 `ts` 插入 | ❌ 0 条 | ✅ 1 条 |
    | **按「语料原文行号」插入** | ✅ **1 条** | ❌ 0 条 |

    ⇒ **追加末尾或只按 ts 的后果不是「没效果」，而是「产出方向相反的因果边」**
      —— 比不补更糟（会把答案引向因果倒置）。
      **必须回到原始语料的「行号」才能恢复真实先后。**

    **怎么拿到行号**（脚本 `_staging/locate_by_line.py`）：
    - 对每个事件，用它的字段文本**回搜语料消息行**，取匹配分最高、且保持
      **单调递增**（用 `lo` 下界约束）的那一行 —— 单调性是映射可信的必要条件；
    - ⚠ **不能用「分词后整词匹配」**：模型会把原文**改写**后再填字段。实测原文
      「以前数据和算力都在火山 走的基本是内网」被改写成
      `after=「数据与算力均在火山云,走内网」`，分词得到「数据与算力均」
      「在火山云」等**全都不是原文用词**，整词匹配一律落空、定位直接失败
      （实测 2/21 定位失败含目标根因）⇒ 必须改用**字符 4~6-gram 子串命中**，
      这样只要保留连续片段就能命中（实测定位率 19/21 → **20/21**）；
    - 插入时按行号归位：**插到第一个行号更大的既有事件之前**。
      实测目标根因事件能精确定位到语料第 **185** 行（正是 `00:17` 那条消息）。

    **合并时的去重（不能省）**：
    补抽窗口与既有抽取**有重叠**，同一事实会被抽第二遍。实测 10 条新事件里
    有 1 条与既有 `0015`（火山 TOS 带宽 5G→15G）**完全重复**，另有一对
    「外网带宽占用」与「网络问题根因」**彼此重复**（同为根因、同 before/after）。
    ⇒ 用 `(object[:14], after[:14])` 作签名，既要去掉与既有的重复，
      也要去掉本次内部的重复，否则会给图谱灌入重复节点。

    **产物隔离**：写入新目录（`out_refill_g03/` + `graphR2p-refill/`），

28. **★ 抽检排序要用「客观判据」，别用 rationale 文本启发式**（2026-09-18）：
    任务：给 `strength=weak ∧ confidence>0.6` 的 5,311 条边排「送检优先级」。

    **先记录一个分布事实**：D10 图 8,595 边中 `weak` 6,670 条（77.6%），
    `weak ∧ conf>0.6` 5,311 条（61.8%）；**`weak ∧ conf>0.9` 为 0 条**
    —— weak 边的 confidence **上限仅 0.85**，分布密集在 0.70/0.72。
    ⇒ **「weak」与「confidence」在模型自评里是解耦的**，别用 confidence 分桶判质量。

    **❌ 失败的判据**：初版设「rationale 含因果连词（因为/所以/导致）却判 weak」
    为首要可疑信号，结果**假阳性极高**。因为模型写的实际是：
    > 「原文未出现因为…所以…」「同主题推进但无明确因果句」「但原文未写明」

    这些是**在解释为何不判强**，属**守规行为**，不是自相矛盾。
    逐句 + 就近原则加否定词过滤后仍难覆盖（「缺明确」「未直接说明」等变体无穷）。
    ⇒ **文本启发式信噪比不足，只能降级为辅助标注**（实测仅剩 11 条，几无价值）。

    **✅ 改用客观判据**（可复核、无歧义）：

    | 档 | 判据 | 依据 |
    |---|---|---|
    | **S** | `type ∈ {cause, supersede}` 却判 `weak` | 因果/替代本质是**强关系**，判弱属硬矛盾 |
    | **A** | 事件时间跨度 > 30 天 | 「弱关联」跨越 1 个月以上，语义可疑 |
    | **B** | 跨度 > 14 天；或 conf ≥ 0.7 且 type ∈ {evolve, trigger} | 时间疏远 / 弱关系主力且高置信 |
    | **C** | 跨度 > 7 天；或 rationale < 15 字 | 时间稍远 / 可能模板化 |

    实测分层：**S = 92 条（1.7%）**、**A = 54 条（1.0%）**，S+A 仅 **146 条**，
    人工可审，是**收益最高、最省人力**的仲裁切入点。
    另注意：**跨群边 = 0 条**（候选对生成阶段已限同群，符合设计，无需检查）。

    **教训**：给「送检优先级排序」设计判据时，**优先找结构化字段的矛盾**
    （`type` 与 `strength` 语义冲突、时间跨度阈值），
    而不是猜 rationale 的自然语言意图 —— 后者模型可以无限变体地表达。
