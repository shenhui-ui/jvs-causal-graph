### 坑 1：生成器会静默抹掉「只存在于产物里」的手写内容

**2026-09-19 实例**：`_handoff/PENDING.md` 里有一整节「五、git 治理状态」，
但 `make_progress_md.py` 的 `write_pending()` 里**没有这段代码**。
重跑后该节被静默删除（文件从 4,427 → 3,301 字节），**没有任何报错**。

**防护**：
1. 重跑前**先 diff 产物**：`diff <备份> <新产物>`，逐段确认没有内容消失。
2. 发现产物里有生成器没有的内容 → **搬进生成器**，不是搬回产物。
3. 生成物尾部加一行「本文件自动生成，手写修改会被覆盖」。

### 坑 2：新增子类只改 `classify.py` 会拖垮整个大类

`rollup()` 用**木桶口径**：大类进度 = 子类中最未完成者。
未在 `status_map.py` 登记的 (大类, 子类) 会 `get()` 回落为 **「待规划」**（最差态），
于是整个大类从「已开发」被拖成「待规划」。

**防护**：`classify.py` 加子类 → **同一个提交里**必须改 `status_map.py`。

**共同特征**：**断言的是「状态」，而不是「事实」**。状态变了断言不会自己变，
而且**不会报错** —— 它只是持续输出一个错的结论。

**防护（通用）**：
1. 改任何检查脚本 / 生成器时，**逐条验证它写的每个断言当下是否还成立**。
2. 能真跑的就真跑，别硬编码结论。**永久为真的告警会训练人忽略 WARN** ——
   这是最危险的形态，因为它在降低整个门禁的信噪比。
3. 结论类表格（缺陷表 / 验收数字 / 进度表）**尽量由活数据生成**，
   或至少在表头写「截至 <日期>，未复核」。
4. 每次改动收尾时问一句：**这次改动让哪些文档里的哪句话变成假的了？**

   **2026-09-20 已修**：改为**自动发现** `dir(status_map)` 里所有 `CLOSED_*` 列表

8之二. **判「某文件是否可用」必须查版本库，不能查磁盘。** 2026-09-20 实测：`.gitignore` 的
   `env/` 规则（本意忽略 Python venv）匹配**任意层级**的 `env` 目录，把接手包

   2026-09-19 D09 一项收口牵动 **6 份文档 + 索引层**（`PENDING.md` / `README.md` /

11. **本环境会回滚「单次」编辑。** 2026-09-19 实测：`make_progress_md.py` 的**一处**改动被还原，
    **同一文件的另两处却保留**（回滚粒度不是整文件）。
    ⇒ **每次编辑后立即回读验证**（`grep -c` 计数即可）；批量改动收尾做一次全项清单回读。
12. **「环境 / 能力不可用」也要写判定命令，不能写结论。**（2026-09-22，第 34 处）
    它和计数类同属「静默过期」，但**后果更重** —— 会让整类工作被**错误跳过**。
    凡写「跑不了 / 没凭证 / 没装 / 不支持」，**必须附判定命令**，且该命令要落在
    **实际执行该工作的那条代码路径**上。⚠️ **反向也成立**：读完一句「不可用」就想跳过某项工作时，
    **先跑一遍判定命令**再决定跳不跳 —— 别拿上一轮（或别人写的）结论当护身符。

### 坑 4：生成器跑在「新建文件之前」→ 索引静默少计

**2026-09-19 实测**：上一轮生成了索引，但**当轮新建的两个文件没被收录**：

- `01-host-product/.../docs/host_memory_dump/M1-10-待裁定项决策记录-20260919.md`
- `_handoff/skills/项目专用/jvs-index-layer-maintenance/SKILL.md`

**根因**：生成器的执行顺序在「新建文件」**之前**。总数据说「看起来正常」，
**没有任何报错**，也没有任何断言会发现它少计了 2 个。

**这不是分类规则问题** —— 两个文件本就在 `RULES` 覆盖范围内，只是扫描时它们还不存在。

**防护（顺序纪律）**：

> **凡是「新建文件 + 刷新索引」的任务，生成器必须放在最后一步跑。
> 新建 → 改文档 → **最后**跑生成器 → 用集合差校验 → 再提交。**
>
> （这是「生成器 vs 你的改动」的先后；生成器**彼此之间**的先后另见坑 6。）

**校验必须用集合差**（总数会骗人）：

```bash
PY="C:/Users/<user>/.workbuddy-ai/binaries/python/versions/3.13.12/python.exe"
# ⭐ 首选 old 侧 = 「上一次提交里的索引」：无需手工备份，且不受工作区回滚影响。
#    前提：重跑前 _index/文件索引.jsonl 相对 HEAD 是干净的（本轮 git add 过且未手改索引）。
#    不满足时退回手工备份（等价）：
#    mkdir -p "C:/Users/<user>/_staging/_idxbak-$(date +%Y%m%d-%H%M)"
#    cp _index/文件索引.jsonl "C:/Users/<user>/_staging/_idxbak-$(date +%Y%m%d-%H%M)/"
# ...重跑生成器...
# 求集合差（注意：两边排序口径要一致，用 Python 不要用 comm）
"$PY" -c "
import json,io,subprocess
def load_text(t):
    d={}
    for ln in t.splitlines():
        ln=ln.strip()
        if ln: o=json.loads(ln); d[o['p']]=o
    return d
old=load_text(subprocess.run(['git','show','HEAD:_index/文件索引.jsonl'],
        capture_output=True,text=True,encoding='utf-8').stdout)
new=load_text(io.open('_index/文件索引.jsonl',encoding='utf-8').read())
add=sorted(set(new)-set(old)); rem=sorted(set(old)-set(new))
chg=sorted(p for p in set(old)&set(new) if old[p]!=new[p])
print('新增',len(add))
for k in add: print('  +',k)
print('消失',len(rem))
for k in rem: print('  -',k)
print('字段变化',len(chg))
for p in chg:
    d={k:(old[p].get(k),new[p].get(k)) for k in set(old[p])|set(new[p]) if old[p].get(k)!=new[p].get(k)}
    print('  ~',p,d)
"
```

**判据**：
- **`消失` 必须为 0** —— 不为 0 说明有文件被删或规则被改坏，**立即停手查因**；
- **`新增` 必须逐个对得上**「本轮真正新建的文件」—— 多出来的通常是**上轮漏计的**（坑 4 本身）；
- 两个清单都打印出来人工过一眼，**不要只看总数**；
- ⭐ **`字段变化` 必须逐条能解释 —— 只看 `新增/消失` 会漏掉「陈旧索引追平」**（2026-09-23 现测）。
  这类形态：某文件的 `s` 变了，但 `新增` 与 `消失` **都是 0** ⇒ 该文件**早已被改并提交**，
  只是**上一轮索引没跟上**，本轮才追平 —— **不是本轮改动、更不是漂移**。
  （判据：拿该路径 `git log -1 --format=%h -- <path>` 对一下是否早于本轮即可；
  若把它当成本轮改动去追查，会白查一轮。）
  ⚠️ **这一栏才是有信息量的**：本轮 4 条字段变化里，3 条是本轮被改文档的 `s` 增长，
  1 条是上述追平 —— 而 `新增` 只有 3 条（= 本轮真正新建的文件）。**只打印总数会两者都看不出来。**

### 坑 12：生成物含「是否入库」标记 ⇒ 必须先 `git add` 再跑生成器

**2026-09-20 实测**：`make_scripts_ledger.py`（→ `_index/一次性脚本登记表.md`）与
`make_scripts_md.py`（→ `_handoff/scripts/SCRIPTS.md`）都会给每个脚本打一个
**入库标记**（`✅` = 已在 `git ls-files` 里 / `⚠️未入库`）。判据来自 `git ls-files`。

当时的操作顺序是「**新建文件 → 跑生成器 → `git add`**」，于是产物把**当轮新建的两个文件**
写成了 `⚠️未入库`；`git add` 之后这两个标记**静默变成假话**，且**不会再自动纠正**
（要等下一次重跑）。实测两个产物各错 1 行。

**根因**：生成器的输入里有 `git ls-files` ⇒ **生成物的正确性依赖「跑生成器那一刻的暂存/跟踪状态」**。

**防护（顺序纪律）**：

> **先 `git add -A`，再跑生成器；生成物落地后再 `git add -A` 一次，然后提交。**
> 即：`改/新建文件 → git add -A → 跑六步生成器 → git add -A → 提交`。

**判据（怎么发现它）**：提交前 grep 一遍产物里的未入库标记 —— 若本轮新增的文件已被 `git add`，
却仍显示未入库，就是踩了本坑：

```bash
cd /c/Users/<user>/jvs-src
grep -rn "未入库" _index/ _handoff/ | head
```

**与坑 4 的区别**：坑 4 是「生成器跑在文件**存在**之前」（少计条目）；
本坑是「生成器跑在文件**入库**之前」（条目在，但标记为假）。两者都是**顺序**问题，
**都不报错**，都只能靠固定流程 + 收尾 grep 发现。

### 坑 13：**编辑存活核验必须排在跑生成器之前**（否则要整轮重跑）

**2026-09-20 实测**：本轮改了 16 个文件，跑完六步生成器、做完集合差校验之后才发现
`_handoff/HANDOFF.md` 的**第 74 行被环境回滚成旧值**（`265`），而**同一文件的第 85 行改动保留**（`266`）——
正是 `MEMORY-detail.md` §四 第 2 条那个「**回滚粒度不是整文件**」的老毛病。

后果不是「漏改一处」那么简单：**生成器已经跑过了** ⇒ 产物里的 `HANDOFF.md` 尺寸是**回滚后**的值
（43,918），补上编辑后文件变成 43,936 ⇒ **整个六步序列必须重跑一遍**，
否则提交进去的索引尺寸与实际文件不符（静默过期，第 27 处的同族）。

**防护（顺序纪律，加在坑 12 之前）**：

> `改/新建文件 → **逐项核验编辑存活** → git add -A → 跑六步生成器 → git add -A → 提交`

**核验手法**（批量、可照抄 —— 用 `grep -cF` 逐条断言，输出必须全是 `1`）：

```bash
cd /c/Users/<user>/jvs-src
for s in "<改动1的关键串>" "<改动2的关键串>" ...; do printf '%s => ' "$s"; grep -rcF "$s" <对应文件>; done
```

⚠️ 两个要点：
1. **核验必须在跑生成器之前**。跑完再核验 = 发现问题就得整轮重跑（生成器的输入含文件尺寸）。
2. **`grep -cF` 命中 0 不等于编辑丢了** —— 先确认**是不是自己的引号/转义写错了**
   （本轮就因 `grep -F 'grep -rnF \"四步\"'` 里的转义写法自造了一次假阴性）。
   **不要凭印象断言「没改上」**，直接 `sed -n '<行号>p'` 打印真实行看一眼。


### 坑 14：同一文件的多处改动**同批下发** ⇒ 后一次写入被覆盖，**静默丢改动**（编辑工具仍报「成功」）

**2026-09-21 实测五次**（P1b 接线那一轮 3 次 + C-2 收尾轮 2 次，**全部发生在「同一文件的多处改动」上**）：

| # | 文件 | 同批下发 | 实际存活 | 丢掉的是 |
|---|---|---|---|---|
| 1 | `_migrate/status_map.py` | 2 处 | **1 处** | **后**一次（`尚未接线进 git-gate.sh` → `同日已接线…`） |
| 2 | `DEV-STANDARDS-ALIGNMENT-PLAN.md` | 3 处 | **1 处** | `§3.3 9 步`、`§5 P1 对齐动作` |
| 3 | `DEV-STANDARDS-ALIGNMENT-PLAN.md` | 2 处 | **1 处** | `§9 两道门禁都硬编码本机解释器…` 行 |
| 4 | `REFACTOR-PLAN.md` | 2 处 | **1 处** | **先**一次（「冻结面核对」整块；后下发的「再添 2 条」那行存活） |
| 5 | `REFACTOR-PLAN.md` | 2 处 | **1 处** | **先**一次（「9 条里 6 条」那行；后下发的「解析口径」块存活） |

⚠️ **丢掉的不一定是「后一次」** —— 第 4/5 行丢的是**先**下发的那一处
⇒ 更坐实「**竞态**」定性：**连方向都不确定**，故不能靠观察「哪一次容易丢」来偷懒，
只能**每处改完立即 `grep -cF` 逐串核验**（命中 0 时**先查是不是自己转义写错**）。

**共同形态**：编辑工具**逐次返回「成功」**，但同一文件**只有一次改动最终落盘** ——
**不报错、不提示、不留痕迹**。

**⚠️ 这是竞态，不是确定性回归** —— 反例：同一轮里 `GIT-POLICY.md` 同批下发 **2 处，两处都活了**。
⇒ **不能靠「这一次没事」推断下一次安全**，只能靠纪律。

**与坑 13 的分工**（两条必须同时守）：

- 坑 13 管「**什么时候**核验」—— 必须排在**跑生成器之前**；
- 本坑管「**怎么下发**改动」—— 同文件**不要同批并发**；
- **两条都踩 ⇒ 生成器带着旧尺寸跑完 ⇒ 整轮六步必须重跑。**

**防护（二选一，首选 ②）**：

① **同文件改动一律串行** —— 一次只改一处，回读确认后再改下一处。
   代价是 N 处要 N 轮往返，但**每轮都可核验**（适合少量改动）。

② **单次读-改-写 + 逐条断言「替换数 == 1」**（推荐；原子手法，适合多处改动）：
   一次运行内完成「读全文 → 逐条 `str.replace` → **断言每条替换数恰为 1** → 写回」，
   任何一条 ≠ 1 就**整批中止、不写盘**。

```bash
PY="C:/Users/<user>/.workbuddy-ai/binaries/python/versions/3.13.12/python.exe"
"$PY" -B - <<'EOF'
import io, sys
P = r"<目标文件绝对路径，正斜杠>"
SUBS = [("<旧串1>", "<新串1>"), ("<旧串2>", "<新串2>")]     # 每条都必须唯一
b = io.open(P, "rb").read().decode("utf-8")
for old, new in SUBS:
    n = b.count(old)
    if n != 1:
        sys.exit("整批中止：替换数 %d != 1" % n)
    b = b.replace(old, new, 1)
io.open(P, "wb").write(b.encode("utf-8"))
print("写入完成，%d 处" % len(SUBS))
EOF
```

**⚠️ 防护 ② 本身有两个实现陷阱**（2026-09-21 实测踩到第 1 条）：

- **① 插入会让后续行号整体后移** —— 若同一脚本里既「按行号替换」又「按行号插入」
  （如 `lines[73:73] = NOTE` 一次插 3 行），**插入之后的所有行号全部失效**。
  本轮实测：先插入 3 行，再用 `lines[91]` 去取目标行 ⇒ 取到的是 `def cn2int(s):`
  （真正的目标行已后移到 94），断言当场失败。
  ⇒ **把所有「替换」做完，最后再「插入」**；或先取出目标行对象、插入后再写回。
- **② 多行字面量匹配易被不可见字符坑** —— 把「两行拼起来」当匹配串
  （`行1 + "\n" + 行2`）时，破折号（`——` = U+2014 × 2）、全角标点、行尾空格等
  **肉眼不可分辨**的差异会让 `count()` **静默返回 0**。
  本轮实测：一个两行匹配串在文件里**明明存在**却命中 0（断言报「替换数 0 != 1」），
  改用行号定位后一次通过。
  ⇒ 改文件优先「**按行号 + `startswith` 断言**」定位，或**只替换短安全串**
  （如 `十三个` → `十四个`）；**不要把整行、更不要把多行写进匹配串**。

> ⚠️ 两条都**不报错**、只让脚本「看起来跑了」—— 与坑 14 主体同族。
> **判据必须是「替换数 == 1」这种可断言的量，而不是「脚本没抛异常」。**

**判据（改完立刻核验，不要只看编辑工具的回显）**：

```bash
cd /c/Users/<user>/jvs-src
for s in "<新串1>" "<新串2>"; do printf '%s => ' "$s"; grep -cF "$s" <目标文件>; done   # 必须全是 1
```

> ⚠️ **三个同源陷阱**（本轮都踩过或差点踩）：
> 1. **回读要读「全文件」，不能只读同批中已生效的那一处** —— 本轮第 1 次丢失，
>    正是因为只核验了「先下发、已生效」的那一处，就以为整批成功。
> 2. **检查串一律用「新串」**（命中 1 = 成功）；拿「旧串」当检查串时**命中 0 才算成功**，
>    搞反就自造假阴性（与坑 9 同源）。
> 3. **`grep -cF` 命中 0 ≠ 编辑丢了** —— 先查自己的引号 / 转义写法（坑 13 要点 2）。

**归属「静默过期」家族**：本坑丢的是**你刚写下的那处改动**，不是「早就写下的断言」，
但**表现完全一致** —— 不报错、只输出错结论。
⇒ 凡出现「**改了却查不到**」的现象，**先怀疑本坑，再怀疑转义**。

### 坑 15：**执行层三条实现陷阱** —— 引号提前终止 ⇒ 重定向污染；行尾检测误报（2026-09-21 新增，**已造成真实污染**）

#### 症状 A：`python -c "..."` 里用双引号 ⇒ `>` 变重定向 ⇒ 生成杂散文件并**污染索引**

```bash
# ❌ 错：Python 字符串里的 " 提前终止了外层双引号 ⇒ 后面的 > 成了重定向
python -c "
old = '"> **共 6 份**（...）'.replace('\n', eol)
"
```

后果链（本轮**实测走完**）：

bash 把 `> **共 6 份**（...` 当**重定向** ⇒ 生成文件 `**共`
（Windows 上 `*` 是非法字符 ⇒ 实际落成 `\uf02a\uf02a共`）
⇒ 同批的 `git add -A` 把它**纳入索引**
⇒ 生成器又把它写进 `_index/文件索引.jsonl`（索引条数 **+1**）。

**清理三步（缺一不可）**：

1. `git rm --cached -- <name>`（从索引移除）
2. 删磁盘文件
3. ⭐ **重跑六步生成器** —— 只做前两步，**索引产物里仍留条目**

**判据**：`grep -c $'\uf02a' _index/文件索引.jsonl` → **0**；索引条数回到改动前。

**正确写法**：用 **`<<'PY'` heredoc**（bash 不做替换），或改走**脚本文件**。

⚠️ **同一根因还会吞掉 Windows 路径里的反斜杠**（`python -c "r'C://x'"` ⇒ 变成 `C:/x`）
⇒ 同样改用 heredoc。

#### 症状 B：`grep -qU $'\r' <file>` 在 Git Bash 下**误报 CRLF**

实测：对一个 `CR = 0` 的**纯 LF** 文件报「CRLF」。

⇒ **行尾检测一律用 Python**：

```python
open(path, "rb").read().count(b"\r")     # 0 = 纯 LF
```

**改动后必查的旁证**：`git diff --stat` 的**改动行数**应与实际改的行数相当；
若接近**文件总行数** ⇒ 行尾被整体改写，**立即回退**。

⭐ **根因补记（2026-09-23，本坑的第二种成因 —— 上面那句是「检测」，这里是「写入」）**：

本轮踩到的不是 `grep` 误报，而是**写入手段本身**：用 Python 批量改文件时，若
**以默认模式读**（universal newlines 把 `\r\n` 折成 `\n`）再 **`io.open(..., "w", newline="")` 写**，
则**整文件行尾被静默改成 LF**。实测 `_migrate/status_map.py`：原 **CRLF 263 / LF 0（68,064 B）**
⇒ 改后 **CRLF 0 / LF 280（67,346 B）**，`git diff --stat` 报 **543 行**（≈ 文件总行数）。
⚠️ 后果不止 diff 难看：本仓库 `.gitattributes` 是 `* -text`（**字节冻结**），
且 `classify.py` 记录**文件字节数** ⇒ 行尾一改，**索引层尺寸字段全部连带失真**。

**判据（改文件前先定行尾）**：

```python
n_crlf = open(p, "rb").read().count(b"\r\n")     # 非 0 ⇒ 该文件是 CRLF
```

- **非 0 ⇒ 全程二进制读写**：`rb` 读 → 只对目标子串做 **bytes** 替换 → `wb` 写。
  **不要**用文本模式往返（读→改→写），`newline=""` 并不能把 CRLF 变回来。
- **已误改的修法**（先归一再统一，幂等）：

```python
t = open(p, "rb").read().replace(b"\r\n", b"\n").replace(b"\n", b"\r\n")
open(p, "wb").write(t)
```

- **收尾两步缺一不可**：① `py_compile` 核语法；② **重跑六步生成器**
  （尺寸字段已随行尾变化 ⇒ 不重跑就是「索引与磁盘对不上」）。

> 同族：与坑 3（静默过期家族）、坑 13（编辑存活）一样，**不报错、只让结论/产物错**。
> 本次是靠 `git diff --stat` 的旁证当场发现（**该旁证确实有效**），但发现时提交已产生
> ⇒ 修法走 `--amend`（未合并前）而非新提交。

> 同批复核（10 个技能）：仅 `d10-review-overlay-closeout` 为 CRLF，且
> worktree `CR` == HEAD `CR` == 88 ⇒ **本就如此**，无混合行尾。

#### 症状 C：把 MSYS 风格路径（`/c/...`）交给 **Windows 原生 git**

`git` 是 Windows 原生程序，**不认** Git Bash 的 `/c/Users/...`，会把它当成相对路径：

```text
fatal: could not read log file '/c/Users/<user>/_staging/.../commit-msg.txt':
No such file or directory
```

实测 2026-09-21 落库坑 15 时**真实失败一次**：首次 `git commit -F /c/...` 直接 fatal，
改 `C:/...` 后成功（提交 `ff14f50`）。

⇒ **接文件路径的 git 参数（`-F` / `--file` / `--output`）一律用 `C:/...`**；
只有**传给 bash 自己**的变量（如 `STAGE=/c/Users/...`）才用 `/c/...`。

**判据**：命令报 `fatal:` 而**路径明明存在** ⇒ 先怀疑路径风格。

**归属**：症状 A / B 属「**静默过期**」家族（不报错、结论错）；
症状 C 是**硬报错**，好定位，但会把治理流程的第一步直接卡住。
