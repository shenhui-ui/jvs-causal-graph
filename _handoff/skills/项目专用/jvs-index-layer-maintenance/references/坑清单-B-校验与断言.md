### 坑 5：校验脚本自己取错字段名 → 假阴性（`None == None` 恒真）

**2026-09-19 实测**：集合差校验脚本里写 `old[k].get("size")` / `new[k].get("size")`，
但索引条目的尺寸字段实际是 **`s`**（不是 `size`）：

```json
{"p": "_handoff\\HANDOFF.md", "l1": "09 工程与运维", "l2": "接手包与技能", "s": 28042}
```

两边都取到 `None` → `None != None` 为假 → **「尺寸变化 = 0」**。

**这个错误不报错、不抛异常，只是输出一个「看起来很正常的 0」**。
暴露它的唯一途径是：**结果与已知事实矛盾** —— 当轮明明改了 3 个文档，尺寸变化不可能是 0。

**防护**：

> **校验脚本本身也是代码，必须先用「已知答案」自证。**
> 跑之前先问一句：「如果我的改动生效了，这个数**应该是多少**？」
> 数字对不上预期时，**先怀疑校验脚本，再怀疑数据**。

字段名速查（`文件索引.jsonl` 每行 5 个键）：

| 键 | 含义 |
|---|---|
| `p` | 相对路径（反斜杠分隔） |
| `l1` | 大类，如 `09 工程与运维` |
| `l2` | 子类，如 `接手包与技能` |
| `s` | **尺寸（字节）** ← 易误写成 `size` |

**完整校验脚本**（六段全过才算通过）：

```bash
PY="C:/Users/<user>/.workbuddy-ai/binaries/python/versions/3.13.12/python.exe"
cd /c/Users/<user>/jvs-src
"$PY" -B "C:/Users/<user>/_staging/tools/verify_index.py"      # 旧索引自动从 git HEAD 导出
```

| 段 | 检查 | 判据 |
|---|---|---|
| 1 | 内部自洽 | `total == 子类求和`、未归类「无」 |
| 2 | 陈旧条目 | 索引有磁盘无 = **0** |
| 3 | 集合差 | **消失 = 0**；新增逐个对得上 |
| 4 | 尺寸变化 | 与「本轮改了几个文档」一致 |
| 5 | 本轮新建条目 | `MUST_NEW` 列表全 `OK` |
| 6 | **交叉验证** | git 侧变更 vs 索引侧变化，两侧一致 |

**段 6 是「用独立口径互相印证」**：文件若在索引口径内且被 git 改了，
索引侧就必须有对应变化。改了文件却忘记重跑生成器，会在这里被抓出来：

```
[6] 交叉验证（git 侧变更 vs 索引侧变化）
    git 侧：改动 2 / 未跟踪 0 / 删除 0
    ? 已改动且在索引口径内，但索引尺寸未变: README.md
警告: 交叉验证有 1 处不一致（见上，需人工判断）
结果: 通过（含 1 条警告，需人工确认后再提交）
```

⚠️ 注意 `.workbuddy-ai/memory/*.md` **是被 git 跟踪的**，但**不在索引口径内**，
故它改动时段 6 会显示「改动 1」且**正确地不报不一致**。

**脚本自证方法**（新脚本/改脚本后必做一次）：
临时往一个已索引文件追加一行（如 `printf '\n<!-- selftest -->\n' >> README.md`），
跑脚本应报出「已改动…索引尺寸未变」；再用事先 `cp` 的备份还原，核对字节数一致。

⚠️ **自证段的条件必须随「本轮预期」参数化，不能写死。**
**2026-09-20 实测**：集合差脚本的自证段写死了 `EXPECTED_NEW = ["PHASE-C-PLAN.md"]`
（「该文件必须 before 无、after 有」）。第二轮收尾时本轮**无新增文件**
⇒ 自证段正确地拦下并报「`PHASE-C-PLAN.md` 本来就在 before 中（未发生新增）」。
这是**正确行为**，但它会诱发一个错误反应：**「那我把自证段删掉就好了」** ——
**绝不能这么做**，那等于把唯一的安全网拆了。
正确做法是**把预期条件做成参数**，例如加 `EXPECT_SAME_COUNT = True`
并在自证段里断言「条目数须相等」，让同一份脚本在「有新增」与「无新增」两种轮次下
都保留自证能力。⇒ 判据：**自证段应当能表达「本轮不该有新增」这件事**，
而不是只能表达「本轮必有新增」。

### 坑 6：生成器之间有**顺序依赖** —— `PENDING.md` 尺寸恒滞后一轮

**2026-09-19 确证**。依赖关系（实测自源码）：

```
classify.py ──写──> 分类统计.json ──读──> make_progress_md.py ──写──> _handoff/PENDING.md
   │                    └───────────读──> make_index_md.py
   └──写──> 文件索引.jsonl ──────────读──> make_index_md.py
```

`classify.py` 要**索引** `_handoff/PENDING.md`，但 `PENDING.md` 是
`make_progress_md.py` 的**产物** ⇒ 若 `classify.py` 先跑，它记录的是**上一轮的**
`PENDING.md` 尺寸，**每轮滞后一拍**。

**实测证据链**（三个时间点，完全吻合「滞后一拍」）：

| 轮次 | 磁盘实际 | 索引记录 | 一致 |
|---|---|---|---|
| 第一轮 | 6,582 | 6,503 | ✗（滞后） |
| 第二轮 | 6,457 | 6,582 | ✗（滞后） |
| 第三轮 | 6,457 | 6,457 | ✓（内容不再变，自动追平） |

**决定性对照实验**（往 `status_map.PENDING` 插一个临时项制造变化）：

```
旧顺序 classify -> make_index_md -> make_progress_md
    磁盘 = 6558 | 索引 = 6457 | 一致: False     ← 滞后

修正顺序：在 make_progress_md 之后再跑一次 classify
    磁盘 = 6558 | 索引 = 6558 | 一致: True      ← 追平
```

**防护**（2026-09-20 修订为**通用判据 + 六步**）：

> **判据：凡产物落在「会被 `classify.py` 索引」的路径（`_handoff/`、`03-`…）的生成器，
> 都必须排在最后一次 `classify.py` 之前。** 产物落在 `_index/` 的（`classify.py` 显式排除）位置自由。
> 标准六步（**先 `git add` 再跑** —— 产物内嵌「是否入库」标记，见坑 12）：
> `git add -A → classify → make_progress_md → make_scripts_ledger → make_scripts_md → classify → make_index_md → git add -A`
>
> 已建成的仓库里 `分类统计.json` 已存在，故可简化为：
> `git add -A → make_progress_md → make_scripts_ledger → make_scripts_md → classify → make_index_md → git add -A`

**为什么这个坑特别隐蔽**：**同时满足「被 `classify.py` 索引」且「是某个生成器的产物」的文件，
尺寸会恒滞后一拍**。2026-09-19 时这类文件**只有一个**（`_handoff/PENDING.md`），
所以症状只出现在一个文件上、很容易被当成「偶发尺寸陈旧」放过去；
**2026-09-20 起变成两个**（新增 `_handoff/scripts/SCRIPTS.md` ← `make_scripts_md.py`），
`_index/` 自身仍被 `classify.py` 显式跳过、无此问题。
⚠️ 该数字会继续增长 —— **新增生成器时先问一句：它的产物落在会被索引的路径吗？**

**识别信号**：段 4 报出 `_handoff\PENDING.md` 或 `_handoff\scripts\SCRIPTS.md`
`<旧值> -> <新值>`，且新值 == 磁盘实际值、旧值 == 上一轮的磁盘值 → 就是这个坑。

### 坑 7：「历史快照」被误判为「过期文本」—— 坑 3 的**反面**

**2026-09-19 实例**：D09 复核后列了一条待办「`review-summary.md` 补记
（仍写『33 行 pending』，已过期）」。**这条待办本身是错的。**

该文件位于 `02-m1-evaluation/outputs/m1-10-d09-pilot-20260907/`，与
`execution.json` / `verification.json` **同目录、同生成时间（2026-09-07 21:40:52）、同性质** ——
它记录的是**生成时**状态，**不是**需要刷新的活文档。

**决定性判据**：它的 SHA256 **被 `delivery-receipt.json` 冻结**，
且当前哈希与冻结值**一致**（已实测 9/9 中 8 项一致）。
⇒ 一旦「补记」，冻结哈希立刻失效，**审计轨迹被破坏**。

**动手前必查 —— 它是活文档还是历史快照？**

| 判据 | 活文档 | 历史快照 |
|---|---|---|
| 在冻结指纹表 / 交付回执里有哈希吗？ | 无 | **有** |
| 正文有「生成于 / 创建于 <过去时间>」吗？ | 不一定 | **有** |
| 同目录有 `verification.json` / `execution.json` 等固化产物吗？ | 无 | **有** |

```bash
# 查某文件是否被冻结
grep -rl "<文件名>" --include=* . | grep -iE "receipt|verification|frozen"
```

⇒ **有哈希冻结 ⇒ 登记缺口，不要「修正」。** 无法重建原版时，改冻结产物只会更糟。

**防护**：把「过期」这个判定**也当作一个断言来验证** ——
声称某文本「过期」之前，先证明**它本来就应该反映当前状态**。
坑 3 是「该变的没变」，坑 7 是「不该变的被改了」，两者都会毁掉审计轨迹。

### 坑 8：**概括句**是最危险的断言形态（2026-09-19 新增，**连错两次**）

**实例**：`ORGANIZATION-AUDIT.md` §一某行与 `HANDOFF.md` §10 R16 都断言
「上游 `project-handoff` **方法层已全部移植**」。**它错了，而且错了两次**：

| 轮次 | 写法 | 实际 |
|---|---|---|
| 第一次 | 「部分移植」 | 易被误读为「方法层也只移植了一部分」 |
| 第二次 | 「**方法层已全部移植**」 | ❌ **仍不实** —— 上游 `references/handoff.md`（**9.7 KB 纯方法层、零宿主依赖**）**从未移植** |

**为什么概括句特别危险**：

- 它**不可验证** —— 读的人无法从这句话知道「全覆盖」的边界在哪，**也就无法发现它错了**
- 它**看起来像结论**，于是被 `HANDOFF` / `README` / 技能**多处引用**，一处错、处处错
- 它**不会随事实变化** —— 上游新增文件、本方漏移植，这句话都不会变

**防护**：

> **覆盖面类断言一律用「逐文件核对清单」，不用概括句。**
> 清单要含：文件名 / 体积 / 状态 / 处置。**能逐行核对，才叫断言。**

```bash
# 上游文件清单（对本项目相关目录）
curl -sSL "https://api.github.com/repos/<owner>/<repo>/git/trees/main?recursive=1" \
  | python -c "import json,sys;[print(e['type'],e.get('size',''),e['path']) for e in json.load(sys.stdin)['tree']]"
```

**相关**：核对覆盖面时**不能只核「数量」与「路径」**。
本轮开读时曾判断技能清单「已对齐、无需补」（11 份、双副本一致、路径全对），
**逐文件核对上游后**才发现 9.7 KB 附页缺失。
⇒ **「清单一致」≠「内容完整」。**

### 坑 9：「检查串凭印象写」→ 假阴性（2026-09-19 一日内**连中九次**）

**本轮实例（三个，都发生在写下本条的过程中）**：

1. 用 `grep -cF "三动作分离，用户未要求保存"` 回读 HEAD，报 **✗ 0** ——
   而 HEAD 里的真实文本是「故按 §11 三动作分离**不登记**」（第 452 行），**内容完全正确**。
   按字面结论本应「改文件」，实际该改的是**检查串**。
2. 用 `grep -cF "坑 8：\*\*概括句\*\*"` 得 **0** —— 因为 `grep -F` 是**固定串匹配**，
   不解释转义 ⇒ `\*` 被当成「反斜杠 + 星号」两个字面字符，而文件里**没有反斜杠**。
   ⇒ **用 `-F` 就不要加任何转义**；含特殊字符的定位改用 `grep -n` 先找行号。
3. **第 3 类失效（本条最隐蔽）：检查串漏抄「加粗标记」**。
   用 `grep -cF "寻址的是 DSH 会话，不是 WorkBuddy 会话"` 报 **✗ 0**，
   而文件里真实写的是「寻址的是 \*\*DSH 会话，不是 WorkBuddy 会话\*\*」——
   **`**` 也是正文字符**，漏掉即失配。
   ⇒ 抄检查串时必须**连同 Markdown 标记一起抄**，**不要「顺手去掉格式」**。

4. **第 4 类失效（不是「假阴性」而是「整条命令不执行」）：检查串含反引号会炸 shell。**
   用 `grep -cF "session/fork\` 未在能力声明中"` 这类**含反引号**的串，
   在 bash 里直接 `unexpected EOF while looking for matching backtick` ——
   **命令根本没跑**，比假阴性更危险（会以为没输出=没命中）。
   ⇒ 检查串**含反引号时**：改用 Python 读文件比对，或换一段**不含反引号**的片段。
   同族的还有 `!`（历史展开）、`$(`（子命令）—— 检查串尽量选**纯文字片段**。

**为什么归在这里**：它与坑 5（字段名错配）、坑 3 防护⑥（数字断言）**同源** ——
**校验动作本身也需要被校验**，而「凭印象写的串」是最常见的失效点。

**防护**：

> **出现 FAIL，先怀疑检查串，再怀疑文件。**
> 先 `grep -n` / `sed -n` **打印真实行**，**照抄**它（**含 `**` 等标记**），再重新比对。
> 一律用 `grep -F`（固定串），**不要用正则** —— `\*`、全角括号、星号都易失配。
> 检查串**优先选纯文字**：避开反引号 / `!` / `$(` —— 它们会在 shell 层先炸。
> ⚠️ **反向陷阱**：同样是「✗ 0」，也可能是**刻意保留的历史对照**（如 `~~旧断言~~ → 新结论`），
> 或**本轮刚新增的正确内容**。报 FAIL 后除了核对检查串，还要问一句：
> **这里是不是本来就该留有旧串？这个串是不是我刚刚才加进去的？**

同源历史三例（均已记入 `MEMORY.md` 第 17 条）：检查串多字 / 少字 / 措辞不同，
三次都报 FAIL 而**文本完全正确**。

**第 5 类失效：检查串「写得太精确」也会失配。**
`grep -cF "PATHEXT 修复接续侧 git"` 报 0，而文件里真实写的是
「已注入 \`PATHEXT\` 修复接续侧 git 不可用」—— 中间**隔了反引号和 `已注入`**。
⇒ 检查串取**连续的一段**，不要**跳过**中间的字符拼成一个「看起来该有」的串。

### 坑 10：**用截断的输出当全集**（2026-09-19 新增）

**实例**：更正「ACP 会话内 git 不可执行」这条失效断言时，用

```bash
grep -rn "..." --include=*.md --include=*.py . | head -20
```

数出命中，**据此认为「只需改 5 处」**并全部改完。收尾复查时把 `head -20` 去掉，
发现**另有 3 处**（`NEXT-交接提醒自动化.md` 卡点 7、`make_scripts_md.py`、
`status_map.py`）**从未显示** —— 它们正好被截在 20 行之外。

**危害**：与坑 8（概括句）**同族** —— 都是**把「不完整的观察」当成「完整的结论」**。
区别在于坑 8 是「自己写了一句概括」，坑 10 是「工具替自己截断了，而我没注意」。
且 `head` 这类截断**不报错、不警告**，与坑 3「静默过期」同源。

**防护**：

> **凡用于「确定覆盖面/穷举清单」的检索，不得配 `head` 截断。**
> 要么**不截断**，要么**同时输出总数并核对**（例如先 `grep -rc ... | wc -l` 拿总数，
> 再决定要不要分段读）。看到 `head -N` 就要问一句：**「被截掉的那部分会不会正好有我要找的？」**
> 改完收尾复查时，**用不带截断的命令再跑一遍** —— 这是唯一能发现漏改的方法。

**⭐ 2026-09-20 复发一次（同一坑第二次）**：做「四步 → 六步」全库搜旧表述时，
命令是 `grep -rnE "..." . | head -20`，输出**被 `544`/`5444` 这类无关数字的假阳性挤满**，
于是**没看到** `make_index_md.py` 的 `ANCHORS`、`ORGANIZATION-AUDIT.md`（5 处）、
`_handoff/env/RUN-CONTRACT.md`、`HANDOFF.md` §1/R06 —— 收尾用**精确 `grep -F`** 复查才发现，
合计又补改 **10 处**。

> ⇒ **两条加强**：① 假阳性会**挤占 `head` 配额**，比单纯截断更隐蔽；
> ② **收尾复查必须换成「精确串 `grep -F`」**（不要复用粗正则 + `head`），
> 且**逐条打印命中**，不要只看数量。

### 坑 11：生成器**硬编码主工作树路径** ⇒ 在 linked worktree 里跑会写到主工作树（2026-09-20 新增）

`_migrate/*.py` 普遍把根路径写死成常量 `JVS`（值 = 本机主工作树的绝对路径）。现测：

```bash
grep -rn 'JVS = ' _migrate/*.py | wc -l     # 命中 10+ 处
```

⇒ 在 linked worktree（如 `C:/Users/<user>/WorkBuddy/Worktrees/JVS/<name>`）里跑生成器，
**产物会写进主工作树**，而你以为改的是 worktree ⇒ **两边都不对，且全程不报错**。

**防护**：

1. 索引层六步序列（`classify → make_progress_md → make_scripts_ledger → make_scripts_md → classify → make_index_md`）**只在主工作树跑**；
2. worktree 只用来**改代码 + 提交**，改完用 plumbing 合并回 `main`，再由主工作树重新生成；
3. 收尾核对**产物时间戳 + `pwd`**，不要只看命令「跑成功了」。
