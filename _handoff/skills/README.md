> 📄 **正文已拆到附页**（2026-09-20 细分）：坑 1–4、12–15 在 `references/坑清单-A-生成器与产物.md`，
> 坑 5–11 在 `references/坑清单-B-校验与断言.md`。**下面只是摘要，判据与命令一律以附页为准。**

1. 生成器会**静默抹掉**「只存在于产物里」的手写内容 → 重跑前必须先 diff 产物
2. 新子类只改 `classify.py` 不登记 `status_map.py` → 木桶口径把整个大类拖成「待规划」
3. **「静默过期」是一个家族**（⚠️ **别引用数量** —— 本行原写死「十六处」，早已过期；权威清单在技能内「坑 3」表格，现数命令也在那里）—— 断言「状态」而非「事实」的文本不会自己变，
   也不报错，只是持续输出错结论。**硬防护 11 条**（技能内逐条列出，下面只列最易漏的 4 条）：
   ① `CLOSED_*` 类留档列表**必须真被渲染**（定义了却不渲染 = 收口项静默消失）；
   ② 一项裁定会**同时让多份文档失效** ⇒ 落档后**全库 grep 关键词**，别只改「我知道的那几份」；
   ③ 产物里出现的文本，**改产物无效，必须改生成器**（`grep -n "<那句话>" _migrate/*.py` 一测便知）；
   ④ **本环境会回滚「单次」编辑**（同文件其他改动可能保留）⇒ 每次编辑后**立即回读验证**
4. **集合差校验**：总数相同 ≠ 内容相同，`comm` 因排序口径失效，必须用 Python 求差
5. **校验脚本要先用已知答案自证**（曾因字段名 `size` vs `s` 导致 `None == None` 恒真、假阴性）
6. **生成器之间有顺序依赖**：`classify → make_progress_md → make_scripts_ledger → make_scripts_md → classify → make_index_md`；
   少跑一次 `classify` 会让 `PENDING.md` / `SCRIPTS.md` 尺寸**恒滞后一拍**；
   且生成器必须跑在 `git add` **之后**（产物含「是否入库」标记，见坑 12）
7. **「历史快照」被误判为「过期文本」**（坑 3 的反面）—— 动手「补记」前先查该文件
   是否被 `delivery-receipt.json` / 冻结指纹表**冻结了哈希**；有冻结 ⇒ **只登记缺口，不得修改**
8. **概括句**是最危险的断言形态（2026-09-19 **连错两次**）—— 覆盖面类断言一律用**逐文件核对清单**
9. **检查串凭印象写** ⇒ 假阴性（一日内**连中九次**）—— 检查串必须**从文件里抄**，一律 `grep -F` 不用正则
10. **用截断的输出当全集** —— 穷举类检索**不得配 `head`**；收尾必须用**不带截断**的命令再跑一遍
11. **生成器硬编码主工作树路径** ⇒ 在 linked worktree 里跑，**产物会写进主工作树**且不报错；
    索引层六步序列**只在主工作树跑**
12. **生成物含「是否入库」标记** ⇒ 生成器必须跑在 `git add` **之后**，否则产物把新文件记成
    `⚠️未入库`，`git add` 后该标记**静默变假**（2026-09-20 新增）
13. **核验编辑存活必须排在跑生成器之前** —— 本环境会**按行回滚**编辑（同文件一处还原、另两处保留）；
    生成器输入含**文件尺寸**，跑完才发现被回滚 ⇒ 产物记的是旧尺寸 ⇒ **整轮六步必须重跑**
    （2026-09-20 第三次实测后新增）。核验 = 对每条改动的关键串 `grep -cF`，输出必须全是 `1`；
    ⚠️ **命中 0 ≠ 编辑丢了** —— 先查自己的转义写法，`sed -n '<行号>p'` 打印真实行再判断
14. **同一文件的多处改动「同批下发」⇒ 后一次写入被覆盖，静默丢改动**（2026-09-21 新增）——
    编辑工具**逐次报「成功」**，但同文件**只有一次改动落盘**；⚠️ 是**竞态**（同轮 `GIT-POLICY.md`
    同批 2 处全活）⇒ **不能靠「这一次没事」推断安全**。对策：同文件**串行**，或
    **单次读-改-写 + 逐条断言「替换数 == 1」**（任一 ≠ 1 整批中止、不写盘）
15. **执行层三条实现陷阱**（2026-09-21 新增，**已造成真实污染**）—— ① `python -c "..."` 里用双引号
    ⇒ 外层引号被提前终止 ⇒ `>` 变**重定向**、生成杂散文件并被 `git add -A` **纳入索引**
    （清理必须**重跑六步**，只删文件不够）；② `grep -qU $'\r'` 在 Git Bash 下**误报 CRLF**
    ⇒ 行尾检测一律用 Python 的 `count(b"\r")`；③ 把 `/c/...`（MSYS 风格）交给 **Windows 原生 git**
    ⇒ `fatal: could not read log file`（实测失败一次）⇒ 接文件路径的 git 参数一律用 `C:/...`

另含三个**活数字**口径（索引覆盖 / `git ls-files` / `find` 全盘）的精确分解与**重测命令**。

**本技能沉淀的两个非显然坑**

| 坑 | 现象 | 修法 |
|---|---|---|
| 隐私闸门 vs 断网上下文 | `offline()` 把 `socket.socket` 换成普通函数 ⇒ 闸门惰性 `import ssl` 时 `class SSLSocket(socket)` 报 `TypeError` | 闸门**模块级缓存**，并在 `with offline()` **之前**预热 |
| `build` 与测试循环依赖 | `verification.json` 要在测试计数之后写，而测试又要读它 | 三段式 `build` / `verify` / `validate`；**任何测试都不得要求 `verification.json` 必须存在** |

首次落版实例：`m1-10-evidence-governance-20260907-v4`（2026-09-20，裁定 #6 / E6，21 项测试全过，

### `script-family-merge-verification`

**把「同源脚本族」合并成「单脚本 + 子命令」，并做机械等价性验证（A/B）。**

触发场景：「这些脚本重复度很高，能不能合并」「命名族收敛」「多份快照合成一份」
「合并后怎么证明行为没变」「A/B 验证脚本族」「合并完输出对不上」。

**第 0 步是先判「真同构 / 重写 / 同源非逐字」三态** —— 2026-09-20 在 JVS 实测**推翻了
「命名族 = 近同构」的直觉假设**：`_migrate/` 11 份里**只有 `append_ws_memory{,2,3}`
是真正同构**（骨架相同、只差目标/哨兵/载荷），其余三族都是「同一个问题问了三遍」或整段重写
（182 / 218 / 167 行，扫描范围、样本上限、扩展名集各不相同）⇒ **只能按「能力」重组成子命令，
不能参数化**。

⭐ **三条实测坑（都会导致 A/B 假失败或真漏改）**

| 坑 | 现象 | 修法 |
|---|---|---|
| `PYTHONHASHSEED` 未固定 | 「按计数取 Top N」在并列处按集合迭代序截断 ⇒ **原脚本自己两次运行都不同**，A/B 报几十行「越界」 | A/B 两侧子进程统一注入 `PYTHONHASHSEED=0` |
| 行号漂移 | 自己改了被扫的 md ⇒ `file:line` 行号整体平移，被误判为「新增行」 | `norm()` 把 `file:line` 归一成 `file:<N>` 并**打印归一计数** |
| 归档后再验证 | 原脚本已 `git mv` 走，验证脚本仍指旧路径 ⇒ 原侧输出变成「文件不存在」错误文本 ⇒ 集合近空 | 常量 `ARCH` 指向归档目录 **+ 加「自证段」**（要求原侧输出含预期标记，缺则直接中止） |

另含：按能力拆子命令的原则、A/B 骨架（含 `LIVE_STATE` 状态行白名单）、
「**先归档，再验证**」顺序、收尾自检清单、常见误判速查表。

⭐ **合并后加「加速器」（缓存 / 记忆化）的六条硬性手法**（2026-09-20 item 3 补充）：
**opt-in 默认关闭**（旧行为逐字可复现）、**诊断走 `stderr`**（`stdout` 两模式逐字相同，
A/B 无需白名单）、**只有「报告 / 盘点」语义可接缓存**（「校验」语义是禁区 ——
缓存会把它退化成「证明缓存没变」）、**已知过期面写进模块头**、
**自证判据 = 抽样重算不符 0 条**、**冷 / 热各比一次 + 命中率 ≥ 99%**。

⚠️ **状态行（`git status` / 密钥扫描 / 尺寸）天然会漂移** —— 这类子命令必须在 A/B 里
**白名单放行**，只校验「格式与条数」，不要逐字比。

### `repo-refactor-perf-survey`

**大型仓库（多 GB / 上万文件）「重构 + 性能」候选的只读盘点** —— 产出方案文档，不写代码。
**本项目的 `REFACTOR-PLAN.md`（阶段 A 产出）就是用它做出来的。**

触发场景：「代码重构」「性能优化」「重复代码太多」「仓库太大 / 太慢」「全树扫描很慢」
「哪些脚本可以合并」「盘点技术债」。

⭐ **核心产出是「两个独立瓶颈轴」** —— 这是本技能最容易被忽略、也最容易错的地方：

| 轴 | 判据 | 有效手段 | 无效手段 |
|---|---|---|---|
| **字节瓶颈** | 体积大、文件数相对少；吞吐接近磁盘上限 | 内容去重 | — |
| **文件数瓶颈** | **体积小但文件极多、单文件极小**；吞吐几十 MB/s | 合并小文件、**哈希缓存** | ❌ **去重完全无效** |

JVS 实测：`03-d10-workspace` 只占全库体积 **5%**，却吃掉 13.8 s 中的 7.6 s
（13,043 个文件、中位数 0.9 KB、吞吐 25 MB/s）⇒ **凭 `du` 直觉去重会得到「假成功」**。

另含：六刀盘点流程（重复族量化 / 整文件副本 + 循环内 I/O / 骨架 vs 数据切分 /
全库内容级重复 / 全树操作只读实测 / 尺寸分布）、报告必写八节、
「先查 `ORGANIZATION-AUDIT.md` + `repo_size_plan.py` 有没有人已经做过」的第一铁律、
以及本项目红线清单（不改版本目录 / 不碰受限素材 / 不为减文件数牺牲逐文件可寻址性）。

⭐ **第三条铁律：盘点结论也要能被证伪** —— 候选清单每一项都要判**证据强度档位**
（✅ 可执行 / ⚠️ 成立但有但书 / ⚠️ **证据不足** / ❌ **被证伪**），
靠三个追问筛：「收益是**上限**还是一次观测」「引用面是**词法信号**还是**依赖审计**」
「**测法本身**能不能发现被保性质被破坏」。

⚠️ **本技能实证：四项候选里三项的原始判断不成立**（不是过期，是**方法测不出它想测的东西**）：
- 把单次热态读数当收益上限（0.70 s 只是同一轮观测，不可外推）；
- 把 `grep` 后缀命中 94.8% 当依赖审计（词法命中 ≠ 运行时按该路径解析）；
- 「索引与 HEAD 一致 ⇒ 可替代 `find`」**不成立**（先删盘再刷新索引 ⇒ 路径已从索引消失 ⇒ 静默漏报）
  ⇒ 修法是用**只增不减的独立基线**当真值源。

⭐ **顺带捡到的更值钱一条**：改测法时检查**旧阈值是不是「弱」的** ——
本项目实测门禁写 `-ge 2000` 却提示「基线 2363」⇒ **丢 363 个文件仍全绿**。
**阈值型判据要问「假绿窗口有多宽」**。

⚠️ **第 2 刀有刻意例外**：校验脚本「重复读同一文件」**有时是刻意的**（读两次确认未被并发修改）
⇒ 报告必须标注该可能性，**不得建议一律缓存**（与 `script-family-merge-verification` 同源约束）。

⚠️ **「❌ 被证伪」的经典错因：只看字节、没看职责**。
实例：18 份「重复」交付脚本实为**交付契约一等公民**（被 `required` 强制要求）+ **包内自证**
（打包时复制进 stage 并断言「活跃证据 == 包内证据」）⇒ 方法论：**数副本前先问它有没有职责**。

⭐ **判完「证据强度」还要判「覆盖面」**（第四问：这条结论覆盖多少对象？）——
用一个脚本代表 18 份副本是**过度概括**。补做全量核验后结论反而更强：
**26 个落点 = 23 个交付包（清单收录 .py 且 sha 全符，缺口 0）+ 3 个源目录（本就无清单，非缺口）**。
⚠️ **B 类源目录不是覆盖缺口**；⚠️ 探测脚本必须先证明**有鉴别力**——
本技能连着写坏两版（L1 递归 ⇒ 恒真；L2 漏改 ⇒ 覆盖率 24/23 自相矛盾），
**一个恒真的探测等于没有探测**，坏版本留档作反例。

⭐ **数字要有来源独立性**（第五问）：拿被测系统自己打印的数字当标准是**循环论证**。
本项目用**四路互不依赖口径**交叉验证（索引解析 / `find` / `git ls-files` / `os.walk` 自算）
⇒ 全为 2363 / 43。但交叉验证只解决「此刻一致」，
**不解决**「脚本里那个 `2363` 是写死字符串、不会自更新」⇒ 仍需**基线驱动**。

⚠️ 另有四条引用纪律（均来自实测翻车）：
① **引代码证据必须绑哈希**（同一文件可有 4 个哈希代，行号 186↔188 漂移，
且**原引路径根本不存在**）；② **冻结清单要用它自己声明的解析规则**（直拼 `base` 会得「9/9 缺失」假结论）；
③ **状态逐条表述，不整体宣告「已过期」**（9 条里 7 条仍一致）；
④ **隔离夹具的基线必须 `--root` 参数化**（否则夹具全判缺），并由此得一条
**廉价反假绿判据**：错误 root 下解析**必须全部判缺**。

⚠️ **独立复核失败后的正确动作**：按**四问自查提纲**（路径真的存在吗 / 覆盖多少对象 /
措辞与自己列的数字矛盾吗 / 判据真跑过吗）逐条自问，并把查出的东西写进文档。
本技能实证：两次复核失败（限流 + 额度耗尽）后自查，**四问里查出三条实质缺陷**。
但仍须写明「**自查不能替代第二方复核**」——判据由作者本人编写时，
它只能证明「文档与作者声称一致」，**证明不了判断对不对**。

### `characterization-regression-harness`

**为「即将被重构 / 拆分的巨函数或大脚本」补特征化回归件** —— 拆分前的「行为等价」底座。

触发场景：「拆完怎么证明行为没变」「回归件写了却恒绿、从不失败」
「怎么证明测试不是恒真探针」「夹具越跑越脏、报错是上一轮的」
「端到端基线该用真实包还是合成包」「基线缺失时该 skip 还是 fail」。

**来源**：本项目 C-2 / R4 巨函数拆分的前置工序（2026-09-21 首次落地两件，
见 `PHASE-C-PLAN.md` §3.2 与 `REFACTOR-PLAN.md` §三 R4）。

⭐ **核心判据：恒绿的回归件 = 没有回归件** ⇒ 写完必须做**负向自检**
（生产路径写桩 → 必须 FAIL 且**命中预期用例名** → **单次运行内**还原 + `sha256` 逐字节一致 → 复跑 PASS）。

⭐ **三条实测坑**（第一版 27 处失败**全部**源于夹具缺陷，被测对象一行没错）：

| # | 现象 | 修法 |
|---|---|---|
| 1 | 报错内容是**上一轮**的 | 固定基线 `self.x0` + `reset()`，**每个 `subTest` 迭代先调**（变异辅助函数会 `save()` 落盘 ⇒ 变异跨轮累积） |
| 2 | 负向断言**永不命中**，报错文本还误导 | `assertIn(needle, list)` 是**精确成员**判断 ⇒ 先 `"\n".join(errors)` |
| 3 | 「全过」但被测代码其实是坏的 | 真实包缺失时一律 `fail`（fail-closed），**绝不 `skip`** |

另含：三件套范式（自建可复位夹具 / 逐条钉错误文本 / 真实包端到端基线 + 只读证明）、
与拆分验收判据（R4-a 先存在先绿 / R4-b 钉文本不钉增量）的接口、
以及「**特征化 ≠ 正确性**」的口径提示（怪癖也应被钉住，将来改了回归件就该改）。

### `giant-function-split-and-verify`

**把巨型函数按阶段抽成私有函数，并证明行为逐字节没变。**

触发场景：「巨函数拆分」「抽私有函数 / 降低圈复杂度」「拆完怎么证明行为等价」
「没有回归件能不能拆」「拆完文件反而变长算不算失败」「目标函数的行数与圈复杂度怎么判据」
「A/B 对比跑不完被超时杀掉」「抽出的函数要原地 append 到调用方传入的列表」
「拆分脚本报锚点不唯一」「变异用例要覆盖哪些错误分支」。

**来源**：本项目 C-2 / R4 巨函数拆分的**执行工序**（2026-09-21 首次完整走通一个目标，
见 `PHASE-C-PLAN.md` §3.6 与 `REFACTOR-PLAN.md` §三 R4）。
与 `characterization-regression-harness` 是**上下游**关系：后者负责「先有回归件」，本件负责「动刀 + 验收」。

⭐ **四层判据**（缺一不可）：**回归件拆前已绿** → **目标函数行数与圈复杂度严格小于基线** →
**冻结指纹仍逐条一致** → **变更说明列出新增的过期条目**。

⭐ **三层 A/B（强度递增）**：① CLI 的 stdout + 退出码 + 产物 sha256 **逐字节**；
② **in-process** 比大量真实样本的返回值（**不能 spawn 成进程**，会超时被杀）；
③ **定向变异**覆盖**互不相同**的错误分支（真实样本多半只走 happy path）。

⭐ **三条实测坑**：

| # | 现象 | 修法 |
|---|---|---|
| 1 | 变换脚本报「锚点不唯一」 | 拼接顺序是**承重**的：**先改调用方、后插被调函数**（被调函数体里逐字包含调用方那几行） |
| 2 | 抽完后调用方拿到空列表 | 要**原地 append** 的 list 必须传**对象本身**，不能在函数内 rebind |
| 3 | 抽完后真值语义变了 | 原用 `if x:` 判真值的，传入前先归一化（`x = x if isinstance(x, list) else []`） |

⚠️ **文件总行数变大是正常的**（抽函数必然加行）；**不得**用「全库行数下降」当判据。
⚠️ 落库的分支 / 合并**只用安全写法**（见 `git-sigterm-safe-recovery`），提交后**回读 `HEAD`**。

**来源与许可证**：改写自 `obra/superpowers` 的同名技能（**MIT**，上游 v6.4.1，摘取 2026-09-21）。
采纳四阶段根因流程、多组件**逐层加仪器**、追数据流到源头、3+ 次修复失败 ⇒ **质疑架构**。

④ 结果**「全 0 / 全不相符 / 极端齐整」先怀疑比较口径**（跨 shell 传参的绝对路径会被改写分隔符 ⇒ 前缀比较静默全假）。

### `llm-judge-drift-verification`

**判断「LLM 判分 / 评测指标的变化，到底是模型变了、数据变了、还是判分器变了」。**

触发场景：「新旧 `scores.json` 直接对比」「换模型重判」「同一模型名却给出相反结论」
「评测指标突然下降 / 翻转」「判分结果不可复现」「跨时间对照」「重判自证」「`input_fingerprint`」。

⭐ **核心判据：跨时间的 LLM 判分结果默认不可比** ——
必须先证明「**同输入 ⇒ 同判定**」，才允许谈归因。**五步**：
① 枚举变动源（数据 / 生成模型 / 判分模型 / 判分代码 / prompt / gold / 端点），每项都要有证明手段；
② **用旧产物的原样输入重判**（不要重新生成 —— 否则同时改了答案文本，变量不分离）；
③ 比对 **`input_fingerprint`**：指纹**相同**而判定**不同** ⇒ **服务端漂移**（同名不同物）；
④ 先查**结构性假阳性** —— gold 是占位符时「命中」在结构上不可能 ⇒ 指标「下降」实为**修正**，
**合法分母 = 有实质 gold 的题数**（不是总题数）；
⑤ **效应量只认零 LLM 的对照**（prompt 字节 diff / 检索链集合 diff），
LLM 判分差**只能**用来说明「判分侧不可比」。

含 6 条实测坑（同模型名 ≠ 同模型 / `bool("0")` 造成的**假门控** / 「判分失败」不是「判定为假」/
答案与 gold 必须裁到同一题集 / 端点共享限流且可用性同日翻转 / 采样噪声识别），
以及抗理性化对照表与红旗清单（**对照结果全 0 差异或极端齐整 ⇒ 先怀疑自己的检查代码**）。

### ⚠️ 完整性三关的**判据**（机械部分已入脚本；此处只留判据与修法）

`diff` 一致**不代表**文件可用 —— 实测发现环境会**破坏技能文件**：

> **实例（2026-09-19）**：新建的 `capability-recon-before-build` 在用户级副本上
> **frontmatter 被整段剥掉**（⇒ 技能**无法被发现/加载**），且正文出现**编码乱码**
> `&#x4F46;`（应为「但」）；**而项目级副本与 git HEAD 是完好的**。
> 若只跑 `diff`，会得出「两份不一致」却**不知道是哪份坏了** —— 险些把坏的那份当权威拷过去。

**三关判据**（由 `python scripts/skills-gate.py` 的 `[3]` 段**逐份**执行）：

| 关 | 判据 | 为什么 |
|---|---|---|
| frontmatter | `SKILL.md` 以 `---` 块开头**且**块内含 `name` / `description` | 这是**技能可被加载的前提**，缺了等于技能不存在 |
| 乱码实体 | `&#x[0-9A-Fa-f]{2,6};` 命中 **0** | **实体 + hex + 分号**三要素才算真乱码 |
| 双副本 | **递归**逐文件比较（含 `references/`） | 「两份一致」也可能是「**两份都坏**」，故必须与前两关同时过 |

**发现不一致时的修法**（⚠️ **先判断哪份是好的**）：

```bash
# 权威判定顺序：git HEAD（被跟踪且已提交）> 项目级工作区 > 用户级
cd /c/Users/<user>/jvs-src
git show "HEAD:_handoff/skills/通用/<名字>/SKILL.md" | head -3   # 看 frontmatter 是否完整
# 若 HEAD 完好 ⇒ 从 HEAD 恢复用户级
git show "HEAD:_handoff/skills/通用/<名字>/SKILL.md" > "C:/Users/<user>/.workbuddy-ai/skills/<名字>/SKILL.md"
diff -r "C:/Users/<user>/.workbuddy-ai/skills/<名字>" "_handoff/skills/通用/<名字>" && echo "✓ 已修复"
```

> **判据**：frontmatter（`---` 开头 3 行）是**技能可被加载的前提**，缺了等于技能不存在；
> `&#x....;` 形式的 HTML 实体是**编码损坏**的特征串。这两项**必须逐份检查**，
> 不能只看 `diff` —— 「两份一致」也可能是「**两份都坏**」。
> ⇒ 这是「**覆盖面类断言一律用逐文件核对清单**」纪律在技能层的落地。

> ⚠️ **2026-09-21 判据收窄**：原第 4 关用**裸 `grep -c '&#x'`**，
> 会对**记录该乱码形态的技能**误报 —— 实测 `skill-authoring-and-verification` 正文里
> **描述该乱码的那句话**与**检查命令本身**都会命中，判「乱码 = 2」而文件完好。
> ⇒ 判据改为**实体 + hex + 分号**三要素（`&#x[0-9A-Fa-f]{2,6};`）。
> 这是本项目「**子串假阳性**」家族在技能层的复现：**检查串必须排除「描述它的文本」**。
