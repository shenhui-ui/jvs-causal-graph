## 一句话

**技能是「会被实际执行的那段文本」** —— 触发靠 description 定，写法按失败形态选，发布前过三关复检。

---

## 一、description 只写「何时用」，不写「怎么做」（SDO）

上游做过对照实测：当 description **概括了工作流**，Agent 会**照着 description 做而不读正文** ——
一份写着「任务间做代码评审」的描述，让 Agent 只做了**一次**评审，
而正文流程图明写**两次**（先规格符合性、再代码质量）。改成只写触发条件后，Agent 才去读流程图、按两次做。

⇒ 规则：

- description = **触发条件 + 症状 + 关键词**；**绝不概括流程**
- 第三人称；技能本身与技术无关时，不要在描述里点名具体技术
- 把「错误串 / 症状词 / 同义词 / 工具名」都塞进去（检索全靠它）
- 上限：frontmatter 合计 ≤ 1024 字符；描述尽量 ≤ 500 字符

```
❌ 先查三层，再决定自研或移植            ← 概括了流程
✅ 当出现「GitHub 上有吗」「要不要自己写」时使用   ← 只有触发
```

⚠️ **但本项目有一条反向经验，不可丢**：

> **速查块与正文不一致时，速查块才是被实际执行的那个。**
> （2026-09-21 实测：切分支速查块只抄了正确写法的后半句 ⇒ 照着做产生**未出生分支**）

⇒ SDO 约束的是 **description**，**不是正文里的速查块**。
正文速查块必须**完整且与正文一致** —— 它是唯一会被照抄执行的部分。

## 二、按「失败形态」选写法（上游最锋利的一条）

先给基线失败分类，再决定用什么写法。**形态用错会反向恶化**：

| 基线失败 | 正确形态 | 错误形态 |
|---|---|---|
| 知道规则、但在压力下违反 | 禁令 + 理性化对照表 + 红旗清单 | 软性建议（「建议…」「可以考虑…」） |
| 遵守了，但输出**形状**不对 | **正向配方 / 契约**：写清输出「是什么」、有哪几部分、什么顺序 | 禁令清单（「不要复述」「别啰嗦」） |
| 该产出的东西里**漏了必填元素** | **结构性**：在它要填的模板里设 REQUIRED 字段 | 模板旁边的散文提醒 |
| 行为应随条件变化 | **条件式**，挂在**可观测谓词**上 | 无条件规则 + 例外条款 |

两条硬规则：

- **不写「细微例外」子句** —— 「不要 X，除非确实需要」会把已生效的配方重新变成可协商
- **例外条款没有作用域** —— 「此限制不适用于代码块」仍会压制代码块；
  要豁免就**重构结构让规则够不到**，不要靠加例外

## 三、纪律型技能要「抗理性化」

适用范围：**知道规则、在压力下跳过**这类失败。
对「输出形状不对」用禁令会**反噬**（见 §二），别乱用。

三件套：

1. **堵死每个绕法**，不只写规则 ——
   `写代码前先写测试？删掉，重来。` 后面紧跟
   `不要留作参考 / 不要在写测试时「顺手改」/ 不要看它 / 删就是删`
2. **提前切断「精神 vs 字面」** —— 正文靠前写：`违反字面即违反精神。`
3. **理性化对照表 + 红旗清单** —— 把基线测试里 Agent 真实说过的借口**逐条照抄**入表

## 四、RED-GREEN-REFACTOR（技能版）

| TDD | 技能 |
|---|---|
| 测试用例 | 一个会诱发该失败的任务场景 |
| 生产代码 | `SKILL.md` |
| RED | **先不装技能**跑一遍，**逐字记录**它怎么错的 |
| GREEN | 写最小技能，专治那些借口；再跑，应变合规 |
| REFACTOR | 找新借口 → 补反制 → 再跑 |

**措辞可先做微测**（比全场景跑便宜）：

- 每次调用用**全新上下文**；system prompt 用**它真实会待的那个上下文**（整份技能，不是孤立的这一句）
- **必须带「无指导」对照组** —— 对照组不复现该失败，就**没有要修的问题，停手**，不要写这段指导
- **每个变体 ≥ 5 次** —— 单次会骗人
- **每条命中都要人眼读** —— 模板回显、被引用的反例都会伪装成命中；只靠自动计数会同时高估失败与成功
- **方差本身是指标** —— 生效时多次会收敛到同一形状；5 次 5 个理解 = 措辞没有约束力，**先收紧形态再加字**

⚠️ 本项目**没有稳定的子代理压测设施**（子代理可用，但成本高且曾经间歇失败），
⇒ 微测优先；全场景压测只在纪律型技能上做，且**不要一次批量建多个技能**。

## 五、token 效率（会被反复加载的技能尤其）

- 细节**移出**：不要罗列所有参数，写「运行 `--help`」
- **交叉引用**而不是复述别的技能
- 压缩示例：**一个能跑的好例子 > 多个平庸例子**
- 自检：`wc -w <SKILL.md>`

## 六、命名与结构

- 只用字母/数字/连字符；**动词优先**（`creating-skills` 而非 `skill-creation`）；`-ing` 适合表示过程
- 扁平命名空间；重参考（100+ 行）与可复用工具**拆文件**，原则与短代码留内联
- 反模式：**叙事化举例**（「某次会话里我们发现…」）／**多语言稀释**（同一个例子写 5 种语言）／**把代码塞进流程图**／**无意义标签**（helper1、step2）

### 6.1 正文段位表（**推荐，非强制**）

> 来源：对齐方案 **P6**（上游机制 **M05**：frontmatter `name` + `description`（≤1024 字符）
> + 六段正文）。判定见 `DEV-STANDARDS-ALIGNMENT-PLAN.md` §3.1（M05 🟡 需改造）。
>
> ⚠️ **本项目标为「推荐」而非「强制」** —— JVS 技能多为**「坑清单」型**
> （用编号坑 + 实测证据承载知识），**强制段位会削掉实测证据**。
> 段位表是**写作检查表**，**不是准入门槛**；机械门禁**不检查**它。

| 段位 | 作用 | JVS 对应写法（有则写，无则省） |
|---|---|---|
| **Overview** | 一句话说清这个技能解决什么 | 已有惯例：`## 一句话` / `## 这个技能解决什么` |
| **When to Use** | 触发条件（= description 的正文展开） | `## 何时用`；**必须与 description 一致**（SDO，见 §一） |
| **Process** | 怎么做（步骤 / 判据 / 命令） | 主体：`## 标准流程` / `## 第 N 步` / **坑清单** |
| **Rationalizations** | 提前堵死「精神 vs 字面」的绕法 | 已有：`## 抗理性化` / 借口对照表 |
| **Red Flags** | 出现这些信号 ⇒ 停手查因 | 已有：`## 红旗` / `## 常见误判速查` |
| **Verification** | 怎么证明做对了（可复跑） | 已有：`## 校验` / `## 收尾`（指向 `_handoff/DEFINITION-OF-DONE.md`） |

**自评口径（推荐级，不进机械门禁）**：

- 六段**全有** ⇒ 最完整；
- 六段**有 3 段以上** ⇒ 可接受；
- **只有 1–2 段** ⇒ 重点查是否漏了 **Verification** —— 这是最容易漏、也最致命的一段
  （漏了它，技能就只剩「主张」而没有「怎么验」）。

## 七、⚠️ 本项目专属纪律（上游没有，必须遵守）

### 7.1 技能文件会被环境破坏 —— 发布前「三关复检」

实测：某技能**用户级副本 frontmatter 被整段剥掉**（⇒ 无法加载），
正文还出现 **HTML 实体乱码 `&#x....;`**，而同技能的 git HEAD 完好。

```bash
head -1  <技能>/SKILL.md | grep -c '^---$'    # ① 必须 = 1
grep -cE '&#x[0-9A-Fa-f]{2,6};' <技能>/SKILL.md       # ② 必须 = 0
diff -r <用户级>/<技能> <仓库内>/<技能>                # ③ 必须无差异
```

⚠️ **第②关的判据必须带「实体 + hex + 分号」三要素** ——
**裸 `grep -c '&#x'` 会对「记录该乱码形态的技能」误报**：
实测（2026-09-21）：某技能正文里**描述该乱码的那句话**与**检查命令本身**都会命中 `&#x`，
于是判据报「乱码 = 2」而文件其实完好（三处副本 sha 完全一致）。
⇒ 这是本项目「**子串假阳性**」家族在技能层的一次复现：
**检查串必须排除「描述它的文本」**。

**权威顺序：`git HEAD` > 项目级工作区 > 用户级。** 三处不一致时**以 HEAD 为准**回写另两处。

### 7.2 双副本字节一致

技能同时装两处：`~/.workbuddy-ai/skills/<技能>/`（新会话自动可用）
与 `<仓库>/_handoff/skills/{通用,项目专用}/<技能>/`（随项目走，可拷走）。

改完**必须 `cp` 同步 + `diff -r` 验字节一致**（可一次跑完全部技能的逐文件总检）。

⚠️ **「同时装在两处」必须实测** —— 曾发现 3 份技能只在用户级，而清单声称「同时装在两处」。

### 7.3 技能里不得埋本环境的「丢文件触发器」

本环境 `git switch` / `git checkout` **必发 SIGTERM**，
而 SIGTERM 会把工作区文件**批量移入回收站**（09-18 丢 9,551 / 09-19 丢 6,447 个跟踪文件）。

⇒ 技能正文里**不要出现可被照抄执行的**分支切换或合并命令。
必须提及时，只写**替代写法**（切分支用 `git update-ref` + `git symbolic-ref` 两行；
合并用 `git commit-tree` + `git update-ref`），并显式标注**禁止使用原命令**。

### 7.4 别在技能里写「会变的数字」和「本项目专属清单」

- ❌ 「本项目共 N 个技能」——**判据 > 枚举**：写「见 `ls -1 <目录>` 现测」
- ❌ 通用技能里硬编码某项目的文件清单 —— **清单本身就是过期源**；
  写成「清单随项目而定（以 X 为例）」+ 通则
- ❌ **格式示例里嵌真实值** —— 示例本意是讲**形式**，读者却会把它当**内容**引用，
  且真实值一变示例**立刻失效**。
  ⚠️ **实测（2026-09-21）**：项目文档 `_handoff/skills/README.md` 讲「加粗与量词位置」的示例里
  **写死了技能份数与通用份数**；同轮新增一个技能后该示例即失效。
  ⇒ **示例一律用占位符**（`N` / `<中文数字>`），真实值只留在**唯一权威处**，且那里应写**现数命令**。
- ❌ **在长文本字段上「追加新句 + 保留旧句」** ⇒ **同义重复**（不是丢改动，是留冗余）。
  ⚠️ **实测（2026-09-21）**：改 `_migrate/status_map.py` 的 `依据` 列（整段数百字）时，
  新写的「① 已接入门禁 `[8]`」与旧的「✅ 两件已于同日接入门禁 `[8]`」并存 ⇒ 同一件事讲了两遍。
  ⇒ 改这类字段后必须**通读整段**；只 `grep -cF` 新串**不足以**判定 —— 新串命中 1 **不代表**旧串已删。
- 改一条纪律后**必须全库搜旧表述**：用**分词搜**（`grep -rnF "四步"`）**不用长串**
  （长串只匹配连写、漏掉变体），再逐条判定；判定时**区分同名不同物**

### 7.5 合规边界

涉及受限素材（`04-restricted-materials/`）的技能，**不得**指导 AI 代替人工签字或作独立语义裁决；
台账 `human_reviewer` / `human_reviewed_at` / `human_review_state` / `source_identity_authenticated`
**不得由 AI 自行填值**。

## 八、什么时候该建技能 / 不该建

**建**：技巧不显然／跨项目会再用／模式通用／别人也能受益

**不建**：

- 一次性方案
- 别处已有标准做法
- 纯项目约定（写进项目文档）
- **能用正则或校验脚本强制的机械约束** —— 那就去**自动化**，文档留给**判断题**
