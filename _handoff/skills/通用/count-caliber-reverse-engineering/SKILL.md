# 计数口径反解（数字不符时的正确姿势）

## 一句话

**「两个数字不符」这个判断本身，多数时候是错的。**
多数时候它们是「**两种口径 × 两个时点**」——各自在其自述条件下都准确。
**先反解口径与时点，再比大小**；直接把两数相减当「差异」是错的方向（本项目第 5 次同族）。

## 0. 何时用 / 不用

**用**：某计数在文档 A 与文档 B（或文档与现测）不一致；或某已登记计数需刷新到时点 T。
**不用**：只有一个出处、且未过期 —— 那就只是「读一下」。

## 1. 铁律：数字不符时的四步固定顺序

> ⛔ **禁止**第一步就去数。第一步永远是**反解**。

1. **找口径出处** —— 别信文档的**文字描述**，去找**产生该数字的脚本行**（`grep` 那个数字本身，
   往往能在生成器里 grep 到**硬编码**）。
   ⚠️ 但**「描述与数字不符」这个结论本身也要先自证** —— 本项目就曾因**抄错判据**
   （把 `C:[\/]…` 看成 `C:[\\/]+…`）而**制造了一个不存在的不符**。判据与自证手法见 **§1.5**。
   ⇒ **以数字反解为准，不以描述为准**（并记「反解」而非「原文确认」）。
2. **定范围（分母）** —— 被跟踪文件？含/不含独立子仓库？读**工作区**还是读 **HEAD**？
   ⚠️ 分母不一致（21,208 / 21,283 / 21,288）本身就是**时点信号**，可直接当锚点用。
3. **建时点矩阵** —— 在**历史提交**上复算，不必 checkout（`git grep <rev>` 直接读历史树）：
   ```
   for C in <候选提交们>; do echo "$C $(git grep -l -F -f <pats> $C | wc -l) $(git ls-tree -r --name-only $C | wc -l)"; done
   ```
   找到**哪个时点的分母与被质疑的载数逐字吻合** ⇒ 该载数的时点即被锁定。
4. **集合运算对齐** —— 口径候选的**并集/交集**往往精确等于另一文档的数：
   ```
   bs1 单反斜杠 → 318   fs1 单正斜杠 → 213   bs1|fs1 → 525（@HEAD） / 524（@09-28）
   ```
   ⇒ **525 恰是另一个文档的「524 + 时点增量」** —— 这就是口径被反解的**裁决性证据**。
5. ⭐ **把文档原文的判据「逐字节抄进判据文件」再重跑** ——
   **不要凭阅读印象复述那个正则**。本项目实测教训：把 `C:[\/]…`（**无 `+`**）看成 `C:[\\/]+…`
   （**多一层转义 + 多写 `+`**）⇒ 算出 4,082 ⇒ 据此断言「原文描述与数字不符」——**制造了一个不存在的不符**。
   按原文逐字重跑：`524@d7663a4`、`525@HEAD` ⇒ **原文本来就自洽**。
   ⇒ 判据：**在断言「某文档的描述与数字不符」之前，必须先逐字节抽取该描述并重跑**。
   ⭐ 这是红线 10（不一致时先怀疑自己的检查代码）**最难自查的形态** ——
   因为错的那一方（宽正则 4,082）**看起来更像「正确的宽口径」**。

## 2. 字节形态必须逐档测（本项目的重灾区）

「路径前缀计数」在不同**写法形态**下差 1 个数量级。
⭐ **最关键的一条：正则里 `[\\/]`、`[\/]`、`[\\/]+` 是三个不同口径，且肉眼极易看混**。
写文档时**必须截图式给原文**，并单独说明「**有没有 `+`**」。

| 形态 | 本项目实测 | 备注 |
|---|---|---|
| 单反斜杠 `C:\Users\…` | 318 | 最常见**真路径** |
| 双反斜杠 `C:\\Users\\…` | 3,555 | **转义写法**（JSON / 源码 / SSE） |
| 三/五/六反斜杠 | **0** | |
| 四反斜杠 | 4 | **与双反斜杠档交叠 4 件**（多档并存 ⇒ **相加 ≠ 并集**：3+3,555+4=3,877 vs 并集 3,873） |
| 单正斜杠 `C:/Users/…` | 213 | ⚠️ **同属真实路径引用**（JSON `"answers": "C:/…"`、206/213 带尾分隔符），**不是叙述、不是「少见的兼容写法」** |
| 单分隔符正则 `C:[\/]…`（**无 `+`**，= 上两档并集） | **525** | ✅ **NEXT 原文口径** |
| 任意分隔符正则 `C:[\\/]+…`（**带 `+`**） | **4,082** | ⚠️ 多算全部 ≥2 分隔符形态，**不是** NEXT 口径 |

⚠️ **各档互不相交**（唯四/双反斜杠交叠 4 件）⇒ 可用作**交叉验证**：若改坏关键词后某档仍非零，说明判据越界。
⚠️ **`-F` 必须显式写**：`git grep -f <file>` 漏 `-F` 则默认走 **BRE**，反斜杠形态**静默算错**
（本项目实测踩到：A 列显示 0、B 列显示 213 —— 看起来像「该口径不存在」，实际是命令用错）。
⚠️ **shell 会吃掉反斜杠**：`printf 'C:\\Users\\…'`、`python -c "...\\..."` 出形态与预期不同
（本项目**两名独立执行者各踩一次**；旧探针用 `chr(92)` 构造即为规避此坑）
⇒ **须在独立 .py 文件里用 `chr(92)` 构造形态**，不要塞进 `-c`，也不要用 `printf`。

## 3. 统计入口与执行纪律（本环境专用）

| 目的 | 入口 | 说明 |
|---|---|---|
| **批量按 rev 统计** | `git grep -l -F -f <pats> <rev>` | **首选**。读历史树、不碰工作区（工作区可能被回滚）。**必须显式 `-F`** |
| 精确形态 | 同上 + **每行一个字面量**的 pattern 文件 | 文件须用 `chr(92)` 风格生成，**不要用 `printf`** |
| 逐对象读内容 | `git cat-file blob <sha>` | ✅ 可用 |
| 批量流式读 | `git cat-file --batch` | ⚠️ **取决于调用形态**：**交互式 stdin 管道 ⇒ SIGTERM**；**stdin 文件重定向 ⇒ rc=0 正常**（实测读回 9.32 MB） |
| `powershell` 中查找文件 | 本环境 git 在子 shell 里**可能整体失效**（`PATHEXT` 问题） | 只用 Bash |

> ⚠️ **写环境限制必须带触发条件**。本项目初版笼统写「`--batch` 必发 SIGTERM」，
> 导致另一位执行者在自己环境**无法复现**并质疑该结论 —— 正解是「**限交互式 stdin 管道**」。

**逐对象读 blob 的可复跑骨架**：
```python
sha_of = dict( 路径→sha from `git ls-tree -r -z <rev>` )
data   = subprocess.run(["git","cat-file","blob",sha_of[p]], stdout=PIPE).stdout
hit    = KEY in data          # 纯字节判定，不经任何模式引擎
```

## 4. 必做自证（四条，缺一不可）

1. **能拒绝（红线 10）**：把关键词改坏 3 例（用户名 / 目录名 / 盘符各错一处）⇒**必须全部归零**。
   若仍非零 ⇒ 是恒真探针，结论作废。
2. **独立第二实现**：不复用同一模式引擎（`git grep` vs 逐对象 `blob` + `in`）。
   双侧：**正侧候选全体逐条确含** + **负侧随机抽样（如 600）逐条确不含**。
3. **锚点复现**：先复现**文档已登记的数字**，对不上立即中止（不是「改口径重算」，是「先证明能复现」）。
4. ⭐ **时点矩阵必须全格实测，禁止外推填充** —— 不得因「两提交的 tracked 数相同」就假定其命中数相同。
   本项目实测教训：因 `a1dd6ff` 与 `93d2908` 的 tracked 同为 21,208，报告把 `93d2908` 的 A 值
   直接填成 `a1dd6ff` 的 313，**实测为 315**；同批 3 格错、**全部源于外推**。
   ⇒ 判据：**宁可留 `—`（未测）也不填推断值**；若确需推断，必须在表内**显式标注为推断**。
   ⚠️ 单点错误会连带整行：`a1dd6ff` 的 B/C 两格也因此错（520→522、4,076→4,078）。

## 5. 反解成功后，还要查两件事（否则数字会再过期）

1. **数字是否被硬编码在生成器里** —— `grep <数字> <生成器>.py`。本项目 `313 / 21,208` 连**8 组明细**
   一起写死在 `_migrate/make_progress_md.py:247`，而目标文档正是该生成器产物 ⇒ **永不自动更新**。
   ⚠️ 更糟：该行**同时写着指向自身的文件名** ⇒ 每次跑生成器都把自己重新计入（**自指**）。
2. **差异必须逐条列出** —— 报「+5」不够，要给「**新增 N 条 / 消失 M 条，净 = N−M**」，
   并逐条说明归因。本项目实测 +5 = **新增 6 / 消失 1**（阅读「+5」为「少了 5 个」会推错方向）。
   ⚠️ **归因日期要去查「该串首次入库的提交」**，不要凭印象写「某次改动同步引入」。
   本项目实测：`PROJECT-OVERVIEW.md` 被判为「09-28 口径同步引入」，实为 **09-23 首版即含**。

## 6.1 ⭐ 最后一步判据：**口径锚 ≠ 处置面全集**

推荐某一口径作「权威值」前，必须**分开回答两问**：

| 问 | 答什么 |
|---|---|
| **对外引用用哪个数？**（口径锚） | 取**血缘最清晰、与既有文档可对账**的那个口径 |
| **要处置的对象一共多少？**（处置面） | 取**所有形态的并集** —— 口径锚往往**小于**处置面 |

⛔ **不要用「小众 / 兼容写法 / 少见」把某些形态排除出处置面**。
本项目实测反例：曾以「正斜杠形态只是兼容写法」为由把 213 件排除，
抽样发现**207 件 FS-only 全部是真实路径引用**（JSON 字段 `"answers": "C:/…"`，206/207 带尾分隔符）
⇒ 按本项目自己的判据（「是否被当作文件系统路径使用」）它们**同样应进处置面**。
⇒ 正确表述：**「A 是口径锚，但处置面应取 B（或更大）」**，两者并列，不给单一「权威数」。

## 6.2 ⭐ 判据跨轴失效：同一判据在**别的轴**上可以无效甚至反向

> 与 §6.1 同族：都是「把一个**局部成立**的东西当成**普适**的」—— §6.1 讲**口径锚**，本条讲**判据效力**。

**一句话**：某判据在池 P₁ 上「有效」，**不能**推出它在池 P₂ 上有效 ——
尤其当 P₁ 与 P₂ 是**按不同轴**选出来的（本项目实测：池 146 按「可疑」选、池 220 按 `conf≤0.6` 选）。

**三例实证（本项目，均可复跑）**：

| # | 判据 | 在轴 A 的表现 | 在轴 B 的表现 | 性质 |
|---|---|---|---|---|
| 1 | `sus` 复原公式（`span>30` / `conf≥0.7`） | 池 146：146/146 命中 | 池 220：**命中 0** | **算术不可达**（220 的 `span∈[0,7]`、`conf∈[0.35,0.60]`，两阈值都在取值域外） |
| 2 | `m10_self_neg`（判边器自述否定） | 池 220：**+56.4 pt**（85.9% vs 29.5%） | 池 146 标定：**反向 −5 pt**（52% vs 57%） | **效力符号相反** |
| 3 | 口径 C 规则引擎 | 同轴样本：~95% | 跨轴：**25%**（低于盲目基线） | **低于基线** |

**三条推论**：

1. **「在本池有效」可能只是因为「与本池的裁决口径同源」** —— 例 2 的 `m10_self_neg` 与口径 C 的剔理由
   **是同一个谓词** ⇒ 高一致率**近乎同义反复**（红线 12）。**去共享谓词后 +0.0 pt** 才是真效力。
2. **判据的「适用轴」必须显式声明** —— 与 §1.2「定范围（分母）」是同一动作的两个面：
   分母定的是**统计范围**，轴定的是**判据定义域**。
3. **迁移前必须先做同轴标定** —— 换池（尤其换选样轴）后**重跑**该判据的
   ① 准确率 ② 盲目基线 ③ 二者之差；**差值 ≤ 0 ⇒ 该判据在新池无效**（红线 15/16）。

## 8. 与既有技能的关系

- `threshold-single-source-and-env-flag`：管**代码/文档两处阈值取值**不一致 ⇒ 本技能管**两个统计数字**不一致。
- `metric-backfill-anchor-verification`：管**从未算过**的指标怎么补 ⇒ 本技能管**已算过但过期/口径不明**的计数。
- `script-family-merge-verification`：管**改代码后行为不变**的 A/B ⇒ 本技能管**改口径后计数怎么对齐**。
- `characterization-regression-harness` / `systematic-debugging`：本技能 §4.4（矩阵禁外推）与其「不能证明等价就不算等价」同族。
