# 仓库「公开层 / 私有层」拆分与发布条件判定

> ⚠️ **三件事要分开答**：**保密**（有没有敏感信息）｜**可用**（公开层自己跑得起来吗）
> ｜**发布**（LICENSE / README 齐备吗）。
> 只答「保密」就说「可以公开了」是**过度断言** —— 本项目实测踩过（见「结论怎么说」）。

## 为什么需要这个技能

在 JVS（21,255 跟踪文件 / 538 提交 / 含真实语料衍生品）上做这件事时，
**最容易犯的错是「按目录划边界」**：判断某目录「是语料」或「是代码」，然后整目录 accept / exclude。

实测证明这会两头错。`01-host-product/` 这一层内部**必须分割** ——
`docs/`（558 个）是语料，`tools/`（82 个）是代码；
而 `02-m1-evaluation/` 里有 4,864 个干净文件与 2,513 个含真名文件**混在一起**。
**按目录切，无论切哪边都会错。**

⭐ 通则：**「某个目录已隔离」≠「该类风险已隔离」。**
只要同一类内容**也在别的目录出现**，按目录写的禁令就只是**纸面结论**。
判定必须按**内容特征**，逐个文件做。

## 核心流程（七步，含 3.5）

### 第 0 步：先确认「有没有已经泄漏出去」

**这一步最先做**，因为它决定后续是「止损」还是「预防」。

```bash
git remote -v                       # 空 = 从未推送
git log --all --diff-filter=A -- '<受限目录>/*'   # 空 = 从未入库
git log --all -p --pickaxe-regex -S 'sk-[A-Za-z0-9]{20,}' --oneline
```

- **远端为空** ⇒ 好消息，成本最低，只是「预防」。
- **已有远端** ⇒ 立刻评估是否已推送敏感内容；**历史不会因删除而消失**。

### 第 1 步：识别「敏感载体」的真实形态

不要凭文件名猜。**打开一个样本看**。语料衍生品往往长得很像普通产物：

| 看似无害 | 实际是 |
|---|---|
| `*.payload.txt` | LLM 调用**入参**，含原始群聊/文档正文 |
| `*.sse` | 模型推理流（**通常不含原文**，需实测确认） |
| `*.json`（事件库） | `after` 字段常残留**未脱敏的原文片段** |
| `*.db`（图谱） | 可能已代号化，需实测 |
| 索引层 `*索引*.jsonl` | 可能含**数万条私有路径**，暴露结构与规模 |

⭐ **务必区分「提示词模板的示例段」与「真实语料正文」**：
前者的姓名是**模板文本**（常自声明「非真实数据」），后者才是真泄露。
按标记切分后分段统计，否则会得出错误的严重程度。

### 第 2 步：建 8 维度核验器 + 负向自证

维度（任一命中即不可公开）：

| 维度 | 判据 |
|---|---|
| 1 真实姓名 | 全名 **+ 昵称/别名**（见下方坑 1） |
| 2 业务标识 | 客户名 / 项目代号 / **真实群名** |
| 3 凭证 | `sk-` **任意形式含省略式** / openid / 私钥 |
| 4 本机标识 | 本机用户名（**任意盘符、任意写法**） |
| 5 语料痕迹 | 消息时间线 / 代号发送者 / invited 名单等**强特征** |
| 6 大文件 | > 50 MB（GitHub 硬限 100 MB） |
| **7 私有层结构** ⭐ | **逐条列举**私有分区**文件路径**的清单/索引/指纹文件 |
| **8 git 元数据** ⭐⭐ | **author / committer / 提交消息 / 对象库**（见坑 13；⚠️ 不在文件内容里） |

⭐⭐ **第 7 维度必须单列 —— 前 6 个都是「内容」维度**：

它们只问「这段文本里有没有敏感**内容**」。而有一类文件对此**如实回答「没有」**，
却泄露**另一件事：私有层长什么样**。典型载体：语料基线清单、文件索引、
冻结指纹表、SHA256 台账 —— 它们可以**完全不含**真名 / 语料正文，
却逐条列出私有层的**完整地图**（实测：一份 `corpus-baseline.jsonl` = **2406 条**
路径 + 字节数 + SHA256，而 6 维度**全部判 0**）。

⇒ 口诀：**维度表若只覆盖「内容」，就必须单独问一句「结构呢」。**

⭐⭐ **第 8 维度同样必须单列 —— 它连「文本」都不是**：

前 7 个维度都在**文件里**找东西（内容或结构），而 git 元数据
**不在工作树里** —— 它在 `.git/` 的 commit object 里，`grep` 工作树**永远看不见**。
实测：7 维度**全部 0 命中**，而 `git log --format='%an <%ae>'` 显示
`真名 <手机号@163.com>` ⇒ push 后**永久公开**。

⇒ 口诀：**「工作树干净」≠「仓库干净」**——还要问一句「**元数据呢**」。
⇒ 且元数据内**还要再分**：`author` 字段 / `committer` 字段 / **提交消息** / 对象库，
**四处各自独立验证**（见坑 14：本项目查了字段、漏了消息）。

⚠️ **两级判据，且界线必须做口径分析后定**（见下方坑 6）：
「**行文提及**私有分区」（README 说明「私有层不发布」，必要且正常）
与「**逐条列举**」（清单文件）是两种东西，**不能用同一个阈值**。

⭐⭐ **必须带负向自证**（本项目的「校验要能拒绝才算校验」）：

```
--selftest  → 逐类篡改输入，确认每类「能拒绝」；再加「行文提及不误报」+「干净输入不误报」
```

只有「会通过」的检查是**恒真探针**，零信息量。
自证要**同时**证明两件事：**能拒绝** 且 **不误报**（后者防「一律拒绝」的另一种恒真）。

### 第 3 步：逐文件判定 + 四分类

```
A. 全维度干净          → 直接公开
B. 含敏感但是「代码」  → 脱敏改写后公开（词表/示例/映射 → 中性占位）
C. 含敏感且是「数据」  → 不公开
D. 私有层结构清单      → 不公开 ⭐（新增；与 C 类同性质，泄露的是「结构」不是「内容」）
```

**C 类的判据**（重要，别硬救）：
若脱敏会**破坏语义**（如题面文本里的姓名、身份映射表），即属 C 类。
把 B 类硬当 C 类删掉会丢功能；把 C 类硬当 B 类改写会产出**读不通的假文档**。

⭐ **D 类的判据**：文件的作用是「列出私有层的文件清单」。
⚠️ 注意**同族一致性**：若项目里已有「索引类因暴露私有结构而被排除」的先例
（如 `_index/`），那么**同性质的清单文件必须一并排除** ——
本项目实测的漏报根因正是「**同类判据未一致适用**」。

⚠️ **额外检查：这类文件往往还是「死重」**。
实测 `corpus-baseline.jsonl` 在公开层跑自查 **2406/2406 全部 MISS**
（它天然只列私有分区的语料产物），门禁永久红灯 ⇒ **既泄露、又失效**。

### 第 3.5 步 ⭐ 排除项必须**主动清理**（`allowed()` 只管「拷入」）

**踩过**：排除逻辑写在「是否拷入」的判定里 ⇒ 对**上一轮已经拷入**的文件无能为力。
加上 D 类排除后重跑，文件**仍在**公开集里（本轮不再拷它，但也没人删它）。

⇒ 必须**两步都做**：① 判定时不拷入；② **主动删除**已存在的排除项。
⇒ 并加一道**构建后自检**：排除项若仍存在 ⇒ **报错退出，不得静默放过**。

⭐ 这道自检的价值当场兑现：**首跑就报错**，抓出了上面这个缺陷。
**如果自检只会说 PASS，这个缺陷会一路带进公开仓库。**

### 第 4 步：脱敏改写

| 项 | 做法 |
|---|---|
| 姓名 | 优先用**项目自有的代号体系**替换（非随意编造），保持与代号化语料一致 |
| 昵称/别名 | 映射到**与全名相同的代号** |
| 本机用户名 | → `<user>`，**只替换用户名本身、保留路径前缀** ⇒ 对任意盘符一次覆盖 |
| 关键：**顺序** | 全局替换必须在「直拷 + 脱敏写盘」**全部完成之后**跑，否则新写入的文件不被处理 |

### 第 5 步：独立交叉核验（不信自研工具）

⭐ 自研核验器与「被它判定为干净」的东西不能互证。必须用**独立手段**：

```bash
# ⭐ 必须读 HEAD，不要读工作区 —— 工作区文件可能被环境回滚/被构建过程污染
git grep -lF "<人名>" HEAD --            # 逐个姓名，期望全 0
git grep -lE '<业务词1>|<业务词2>' HEAD --  # 期望全 0
git grep -lF "<本机用户名>" HEAD --        # 期望全 0
# 项目自带扫描器
python <项目自带 name_scan.py> --check <目录>
# 语法核验（改写过的代码必须 compile）
python -m py_compile <每个 .py>
```

⚠️ **两个口径细节**：
- **抽查 vs 全量**：逐次 `git grep` 全量名单会显著变慢。**报数时必须写清是抽查还是全量**
  （本项目实测：抽查 30 个；旧文档误写成「全量 107」⇒ 属红线 5「计数类断言静默过期」）。
- **`__pycache__` 污染**：跑 `py_compile` 会在候选集内**生成 `__pycache__`**，
  导致「文件数从 177 涨到 183」这类失真 ⇒ 统计/提交前必须清理，并把清理固化进构建脚本。

### 第 6 步：发布条件检查（技术干净 ≠ 可发布）

⭐ **最大的一类遗漏：只验了「内容是否敏感」，没验「公开层是否自洽可用」。**
技术核验（前 5 步）全绿**不等于**可以发布。公开前至少要查这 5 类：

| # | 条件 | 症状 |
|---|---|---|
| 1 | **LICENSE** | 缺失 ⇒ 法律上「保留所有权利」，他人不可合法使用 |
| 2 | **README 适配** | 原 README 面向私有 monorepo，**大量引用私有分区** ⇒ 克隆后断链 |
| 3 | ⭐ **门禁/CI 可运行性** | 见下方 —— **最易漏，也最危险** |
| 4 | **脚本的运行时引用** | 文档里的引用只是「断链」，脚本里的 `os.path.join(私有分区, ...)` 是**运行时直接报错** |
| 5 | 第三方来源内容 | 技能/文档若含第三方内容，需确认许可证兼容性 |

#### ⭐ 第 3 项：门禁/CI 可运行性（本项目实测整类漏掉）

**做法**：把项目**自带的门禁/CI 脚本**在公开层里跑一遍，看它是否还能工作。

**实测结果**：公开层跑自家门禁 ⇒ **FAIL=4**，且**全部是结构性失效**
（公开层天然不含私有产物），例如：

- 指纹/基线类步骤：判据源里含私有分区路径 ⇒ 大量 MISS
- 「首次 `git init`」的新仓库：某些针对「事故后 main」的治理守卫**不适用**
- 依赖**仓库外目录**（如用户级技能目录）的步骤：**作用域错位**

⇒ **判据**：**门禁若在公开层永久红灯，结果是「要么忽略它、要么绕过它」——
两种都比没有门禁更坏。** 必须在公开前适配（声明适用域 / 分公开-私有两套 / 改为可选）。

#### ⭐ 第 4 项：区分「文档断链」与「运行时断链」

统计「引用私有分区的文件数」时，**不要只报总数** —— 要分层：

| 类型 | 影响 |
|---|---|
| `.md` 里的引用 | 只是**文档断链**，改为「（私有层，不随本仓库发布）」即可 |
| `.py` / `.sh` 里的 `os.path.join(...)` | **运行时直接报错**，必须真改 |

**实测**：本项目 40 个文件引用私有分区，其中 **16 个是脚本的运行时引用**
（11 个 `.py` + 1 个 `.sh` 的路径拼接）⇒ 只报「40 个断链」**掩盖了更严重的那一半**。

## ⭐ 十八类实测坑（前 5 类同族：**词表/判据不全 ⇒ 假阴性**；6–8 类是**判据「形态」与「作用域」错配**；9–12 类是**「构建后」与「产物上」才暴露的**；13–14 类是**「元数据」形态**；15–16 类是**「校验器自身」的失真** —— 一个恒假、一个漏覆盖；17 类是**判据选错载体**；18 类是**「清洗表」不是安全边界**）

| # | 坑 | 症状 |
|---|---|---|
| 1 | 姓名词表**只有全名** | 昵称 / 简称（如「小×」「阿×」这类**只写名不写姓**的称呼）**静默漏过** |
| 2 | 密钥正则要求长度下限 | 漏掉**省略式**（只露前缀、后接省略号的写法，如 `sk-…`） |
| 3 | 漏掉「本机标识」维度 | 上百文件含本机用户名 `C:\Users\XXX` |
| 4 | 替换顺序错 | 后写入的文件未被全局替换 |
| 5 | 业务词表缺**真实群名** | 群名残留在脚本字符串里 |
| 6 ⭐ | **维度只覆盖「内容」** | 私有层**结构清单**（2406 条路径+SHA256）被 6 维度全票放行 |
| 7 ⭐ | **阈值随手取，未做口径分析** | 把 README 的**行文提及**与清单的**逐条列举**混为一谈 ⇒ 6 个假阳性 |
| 8 ⭐ | **排除只做「不拷入」，未做「删除已存在」** | 加排除后重跑，文件**仍在**公开集里 |
| 9 ⭐⭐ | **脱敏把「硬编码路径」打成占位符 ⇒ 工具静默失效** | 见下，**最严重** |
| 10 ⭐ | **同根因分布于多个入口，只修了一个** | 修好门禁，`scan-secrets.sh` 仍是恒真探针 |
| 11 ⭐ | **对生成物的手工修改，被下次重建静默覆盖** | 重构过的 `name_scan.py` 退化成 Z 码骨架 |
| 12 ⭐ | **`-B` 抑制不了 `py_compile`** | 检查脚本自己产出 `.pyc`，文件计数 179→185 |
| 13 ⭐⭐ | **只查「文件内容」，没查「git 元数据」** | 7 维度全 0，而 `git log` 里是 `真名 <手机号@163.com>` |
| 14 ⭐ | **查了 author 却没查 commit message** | 字段干净了，**提交消息**里留着真名（同族第三次） |
| 15 ⭐⭐ | **安全网把「正确答案」判成「泄漏」** | 用 noreply（**默认含用户名**）⇒ 反被判「残留泄漏」拒绝上传 |
| 16 ⭐ | **修复动作只覆盖「主判据」，没覆盖「安全网」** | 安全网发现消息含邮箱，而 `msg-filter` 只洗名字 ⇒ **半完成状态** |
| 17 ⭐ | **用「关键词命中」判断语料是否入库** | 必然误报：源码/文档**引用** `events.jsonl`、题集路径是**设计**，不是数据 |
| 18 ⭐⭐ | **把「清洗表」当成安全边界：新增文件不在它的覆盖面内** | 见下 —— **同一份清单，昨天干净不代表今天干净** |

### ⭐⭐ 坑 18 的判据：**清洗表（`GLOBAL_REWRITE`）是「按已知形态枚举」的，不是边界**

**症状**（2026-09-24 实测，本轮自己的技能中招）：把一个**新写的技能**同步进公开层
（`_handoff/skills/通用/` —— 该路径**在公开层清单内**），
而技能正文**用真实身份举例**（本机用户名 + **手机号邮箱**）。

清洗表只覆盖 **用户名 / 内部目录名** 四个串，**不覆盖手机号邮箱**
⇒ 若直接同步并重建，`13800138000@163.com`（真实值形态为「手机号邮箱」）会**原样发布到公开仓库**。

**根因**：清洗表是**按「已知形态」枚举**出来的（历史上踩过什么坑就补什么串），
它对**未枚举到的形态**（手机号邮箱 / `ou_` openid / 真实群名）**天然无覆盖**。
⇒ **「上次扫描干净」是「上次那批文件」的结论，不是「这批文件」的保证。**

**判据（三条，缺一不可）**：

1. **清洗表 ≠ 安全边界** —— 凡**新增**进公开层的文件，必须**单独跑一次内容扫描**，
   **不得**引用既有扫描结论（哪怕只隔了一天）。
2. **扫描词表要按「值形态」而不是「词表形态」**：
   人名是**词表**（枚举），而手机号 / 邮箱 / openid / 群名是**形态**（正则）。
   只查前者 ⇒ 后者必然漏（同族：坑 1/2/5）。
3. **发现后**：**先净化、再同步**（两个副本必须一起改，否则 `diff -r` 不过关）——
   且净化要**保留教学语义**：把真实值换成**中性占位**
   （`<user>` / `13800138000@example.com` / `placeholder@local`），
   **不要**把示例整段删掉 —— 删掉就丢了「这个坑长什么样」的证据。

⚠️ **同族**：坑 6（维度只覆盖内容，漏了结构）与坑 13（漏了元数据）都是
「**以为覆盖面 = 全部**」。本条是第三种形态：**覆盖面按「时间」漏** ——
昨天扫描过的清单，今天新增了文件，**扫描结论自动失效**。

### ⭐ 坑 13 的判据：**第 8 维度 —— git 元数据**

**症状**：7 个内容维度**全部 0 命中**，但 `git log` 显示：

```
84c65af | <user> | 13800138000@163.com   ← 本机用户名 + 手机号邮箱
c5855af | <user> | placeholder@local
0ca5e05 | JVS     | jvs@local             ← 只有首个提交是匿名的
```

⇒ 一旦 push，这些**永久公开**（GitHub 提交列表 / REST API / 任何人 `git log`）。

**根因**：**信息有三种形态 —— 内容 / 结构 / 元数据**。
前 7 个维度覆盖了「内容」和「结构」，**唯独漏了「元数据」**。
⚠️ 且**最容易漏的恰恰是它**，因为「工作树干净」的直觉会让人觉得「已经处理完了」。

**判据（上传前必查，四条各自独立）**：

```bash
# ① 全部提交的身份字段
git log --format='%H|%an|%ae|%cn|%ce' --all
# ② 全部提交的**消息正文**（⚠️ 独立一条，不要以为①干净它就没问题）
git log --all --format=%B | grep -nE "<真名>|<邮箱>|C:/Users|/home/"
# ③ 对象级扫描（⚠️ 不信 ref —— 未被 gc 的旧对象仍可能被 push）
git cat-file --batch-all-objects --batch-check='%(objectname) %(objecttype)'
# ④ 本地身份配置（下次提交会不会**重新引入**）
git config --global user.name; git config --global user.email
```

**修法**（`filter-branch` 只动元数据、**不动 tree**）：

```bash
git filter-branch -f \
  --env-filter 'export GIT_AUTHOR_NAME="<中性名>"; export GIT_AUTHOR_EMAIL="<中性邮箱>";
                export GIT_COMMITTER_NAME="<中性名>"; export GIT_COMMITTER_EMAIL="<中性邮箱>";' \
  --msg-filter "sed 's/<真名>/<user>/g'" \
  -- --all
git update-ref -d refs/original/refs/heads/main
git reflog expire --expire=now --expire-unreachable=now --all
git gc --prune=now
```

**三条自证（都要「能拒绝」）**：

| # | 判据 | 为什么 |
|---|---|---|
| 1 | 重写后身份取值集合**只有一个**且不含泄漏字面量 | 证「替换干净」 |
| 1b | 重写后**提交消息**不含泄漏字面量 | ⚠️ 独立一条（见坑 14） |
| 2 | ⭐ **逐提交 `^{tree}` 逐字节不变** | 若有「按字节冻结的产物指纹」治理，**tree 变了指纹全废** |

⚠️ **防回归**：改**仓库级** `user.name/user.email`（`git config`，不加 `--global`）——
不要动用户的全局配置。`git var GIT_AUTHOR_IDENT` 可验证生效。
⚠️ 若要关联 GitHub 账号，用 **noreply 邮箱** `<id>+<user>@users.noreply.github.com`，
**不要**用真实邮箱。且**必须在首次 push 前**改好。
⚠️ **改写历史的前提**：`git remote -v` 为空。已有远端时改写会让远端不一致 ⇒ 脚本应**拒绝执行**。

#### ⭐⭐ 坑 13 的**直接反例**：`git grep` 查「是否含身份信息」——**单用它必错**（2026-09-24 实测）

我在处置备份目录时，用 `git grep "<user>"` 扫某备份，**得 0 个文件**，
差点据此判定「这个备份不含实名，可以放心留着」。实际该备份的提交身份正是
`<user> <13800138000@163.com>` / `<user> <placeholder@local>`。

**根因**：`git grep` **只覆盖「内容」维度**，覆盖不到「元数据」维度。
⇒ 同一份仓库可以「文件内容 0 命中」而「提交身份就是真名+手机号」。

**正确判据（两个维度必须各查一次，缺一不可）**：

```bash
# ① 内容维度（会漏掉元数据！）
git grep -l "<敏感串>" $(git rev-list --all)

# ② 元数据维度（git grep 完全覆盖不到）
git log --format='%an|%ae|%cn|%ce' --all | sort -u
# ⚠️ %an/%ae（作者）与 %cn/%ce（提交者）都要看 —— 见坑 14「查了一个字段≠查了全部」
```

⭐ **一句话记法**：**`git grep` 干净 ≠ 仓库干净**。
凡判「是否含身份信息」，**必须同时出「内容 + 元数据」两栏结果**。
⚠️ 这也解释了为什么坑 13 会把「7 个内容维度全 0」当成「已经处理完了」——
**内容维度全绿，恰恰是元数据维度最容易被跳过的时刻**。

### ⭐ 坑 14 的判据：查了一个字段 ≠ 查了全部字段

**症状**：修完 `author/committer` 后以为干净了，**对象级扫描**却抓出
**新 HEAD 的提交消息里含真名**（我在消息里举例说明某个路径缺陷时写进去的）。

**判据**：**凡「公开可见」的字段，各列一条判据，逐个独立验证** ——
不能因为「另一处干净了」就假定它也干净。
本项目**同族第三次**：修订 2 的 D 类漏报（按目录划 vs 按内容划）、
修订 3 的「4 个入口只修 1 个」、本坑（author 干净 ≠ message 干净）。

⚠️ **对象级扫描是必需的，不是可选的**：
`git log` 只看 **ref 可达**的提交；而**未被 gc 清掉的旧对象**仍可能被 push
（部分客户端与 `--mirror` 会带全部对象）。本项目正是**这一步**抓出了消息泄漏。

```python
# 批量取全部 commit 对象内容（比逐个 git 调用快一个数量级，避免 SIGTERM）
git cat-file --batch-all-objects --batch-check='%(objectname) %(objecttype)'
# 过滤 commit，再 `git cat-file --batch` 一次性取内容
```

### ⭐ 坑 17 的判据：判「语料是否入库」要看**文件类型分布**，不是**关键词命中**

**症状**（2026-09-24 推送前最后核查）：
`git grep -l "events.jsonl"` → **30 个文件**、`"gold"` → **44 个**、`"语料"` → **40 个** ——
看着像「语料大面积入库」。实际全部是**源码里的路径常量**与**文档里的设计说明**：

```python
BASE = r"C:\Users\<user>\host-workspace\...\docs\host_memory_dump"   # ← 引用，不是数据
```

**决定性判据**（一条命令，无需人工翻文件）：
```bash
git ls-tree -r --name-only HEAD | sed 's/.*\.//' | sort | uniq -c | sort -rn
```
本项目结果：`96 py / 39+33 md / 4 sh / 2 json / 1 txt / LICENSE` ——
**0 个 `.jsonl` / `.sse` / `.csv`** ⇒ 语料确实未入库。
再补一条硬断言：
```bash
git ls-tree -r --name-only HEAD | grep -E "\.(jsonl|sse|csv|tsv|xlsx?|parquet|db|sqlite)$"
# 必须为空
```

⚠️ **为什么关键词判据必然误报**：一个「代码公开 / 语料私有」的仓库，
其**设计意图**就是「代码知道语料在哪、但语料不在仓库里」——
所以**引用语料的代码越多，关键词命中越多，而语料一件都没进来**。
⇒ 命中数与结论**方向相反**。

⭐ 判据选择通则：**判「某类内容是否存在」，要扫「载体」而不是扫「名字」**。
同族见坑 6（维度只覆盖内容 / 结构 / 元数据）、坑 13（文件内容 vs git 元数据）。

### ⭐ 坑 15 的判据：**安全网不得把「目标结果」当「泄漏」**

**症状**（2026-09-24 预演实测，且**必然**会遇到）：
用 GitHub 私密转发地址（`<id>+<username>@users.noreply.github.com`）重写身份后，
「已知敏感字面量」安全网 **3/3 提交全命中**、脚本 **exit 6 拒绝上传** ——
原因是 **noreply 地址默认就含用户名**，而 `LEAK_NAME` 通常就等于该用户名。
⇒ **用户越是正确使用 noreply，越被判泄漏。**

**判据**：安全网扫描前，**先把「目标身份的完整呈现」从文本里剥掉**，
再查裸字面量：

```python
IDENT_STR = "%s <%s>" % (NEW_NAME, NEW_EMAIL)     # e.g. "<user> <123+<user>@users.noreply.github.com>"
def residual_text(t):
    return t.replace(IDENT_STR, "")               # 只豁免「完整字段」，不豁免裸字面量
```

⚠️ **必须只豁免「完整字段呈现」，不得放宽到「豁免该子串」** ——
否则提交消息里的裸实名也一并放过，**安全网直接失效**。
⚠️ 负向自证（**必备**）：往提交消息注入 `裸实名 + 真实邮箱`，
**必须仍被 1b 抓到**；否则说明豁免范围开太大。

⭐ **推广**：这是「**校验器要能拒绝，但拒绝对象必须是真问题**」的另一面 ——
红线 10 讲「不能恒真」，本坑讲「**也不能恒假**」。
**阴性对照与阳性对照都要做**：① 注入真泄漏 ⇒ 必被抓；② 换成正确目标值 ⇒ 必须放行。

### ⭐ 坑 16 的判据：修复要覆盖**判据所依据的全部字段**

**症状**：安全网报「提交消息含真名」⇒ 于是加了 `--msg-filter` 洗名字；
但注入的**邮箱仍在** ⇒ 自证 1b 报残留、exit 4。
⇒ 根因：**修复动作只对齐了「主判据」（身份字段），没对齐「安全网」（全部字面量）**。

**判据**：改完过滤规则后，**按「安全网词表」逐项注入并逐项验证** ——
不能只测第一个词。本项目实测：`msg-filter` 需遍历 `EXTRA_PATTERNS` 生成
sed 表达式，且**必须做正则转义**（不改的话 `13800138000@163.com` 里的
`.` 会变成「任意字符」匹配，既漏又误伤）。

⚠️ **顺带暴露的第二个问题：失败发生在写入之后 ⇒ 半完成状态**。
`filter-branch` 成功但自证失败时，**历史已被重写、`refs/original` 残留**。
⇒ 脚本应当**可重入**：从半完成状态重跑必须能**自愈**（本项目实测可自愈 ✓）。
判据：**故意制造半完成状态，再跑一次，须收敛到通过**。

⭐ **坑 1–5 的判据**：每补完词表重跑，**若不再抓出新漏报才可信**。
第一次「全 0」几乎总是**词表不全**造成的，不是真的干净。

⭐ **坑 6 的判据**：建完维度表后，逐个问自己 ——
**「这份文件回答的是我问的那个问题吗？」**
内容维度回答的是「有没有敏感内容」，而清单文件回答的是「私有层长什么样」。
⇒ **同类信息可能有多种「形态」（内容 / 结构 / 元数据），维度表要覆盖到形态层。**

⭐ **坑 7 的判据（红线 17：口径未定 ⇒ 先做口径敏感性分析）**：
**动手定阈值前，先打印「候选文件 × 各口径计数」的分布表。**
本项目实测分布：`{2406, 18, 15, 10, 10, ...}` —— **2406 与次高值相差 133 倍**，
这是**口径无关的断层**（阈值落在 [20, 2000] 结论都一样）。
⇒ 把界线划在**断层**上，而不是随手取「5」。
⇒ 并做**两级**：`≥100` = 硬阻断、`≥5` = 仅提示（行文提及属正常）。
⚠️ 若分布**没有断层**（连续渐变），说明这批文件**同质** ⇒ 需要换判据，而不是挑阈值。

⭐ **坑 8 的判据**：排除逻辑写完，**必须验证「上一轮的产物已被清除」**，
并把它做成**构建后自检**（排除项仍在 ⇒ 报错退出）。
「只判定、不清理」的排除在**增量重建**场景下**完全失效**。

### ⭐⭐ 坑 9 的判据（最严重 —— 脱敏本身让工具失效）

**症状**：脱敏规则把本机用户名替换成 `<user>` 占位符，于是
`PY="C:/Users/XXX/.workbuddy-ai/.../python.exe"` 变成
`PY="C:/Users/<user>/..."` ⇒ **该路径必然不存在**。

**两种后果，第二种更坏**：

| 形态 | 表现 | 危险度 |
|---|---|---|
| `[ -x "$PY" ]` → 假 + 走 `else` 打印「跳过」**并计为通过** | `scan-secrets.sh` **完全不扫内容却报「扫描通过」exit 0**；注入真凭证也不报错 | ⭐⭐⭐ **恒真探针** |
| 同上但**报 FAIL** | 门禁 [2][3][4][7][10] **五步共 11 个假 FAIL**（级联，同一根因） | ⭐⭐ 永久红灯 ⇒ 人会忽略门禁 |

**判据（三条，缺一不可）**：

1. **必须在「构建产物」上验证工具，不能在源仓库上验证** ——
   源仓库里用户名**未脱敏**，工具那时**是工作的**；脱敏是**构建后事件**
   ⇒ 源侧验证**天然看不见**这个问题。（本项目为此漏了一整轮）
2. **凡「探测不到就跳过」的分支，逐个问：跳过之后还报通过吗？**
   报通过 = 恒真探针。⇒ 一律改 **fail-closed**（探测失败即判 FAIL）。
3. **脱敏规则命中「可执行路径」时，要同时检查该路径的所有消费方** ——
   同一个 `$PY` 变量可能被 4 个入口读（门禁 / 凭证扫描 / 环境自检 / git 钩子）。

**修法**：解释器改为**候选链探测**（不依赖任何硬编码用户名），
用**实测 `--version` 能否跑通**作判据（而非 `[ -x ]`，后者不区分「文件在」与「跑不动」）：

```bash
probe_py(){ local c; for c in "$@"; do
  [ -n "$c" ] || continue
  if "$c" --version >/dev/null 2>&1; then printf '%s' "$c"; return 0; fi
done; return 1; }
PY="$(probe_py "${JVS_PY:-}" "$HOME/.../python.exe" "python3" "python")" || PY=""
```

⚠️ **不是所有入口都该 fail-closed**：`git-gate.sh` 是**人工步骤** ⇒ 可 fail-closed；
`pre-commit` 在**每次提交**时强制调用 ⇒ 若因环境问题一律拒提交，
会让「环境故障」与「真有问题」无法区分（人只会开始用 `--no-verify`）
⇒ 该处保留**降级 + 显式告警**。**这是有意的口径差异，要写进注释。**

### ⭐ 坑 10 的判据：修完一个入口，立刻枚举「还有几个入口」

**症状**：把 `$PY` 探测只写进 `git-gate.sh`，而**同一根因还有 3 处**
（`scan-secrets.sh` / `check_env.sh` / `.githooks/pre-commit`）。

**判据**：**修任何「跨文件共性缺陷」时，第一件事是枚举全部命中点**：

```bash
grep -rn "Users/<user>" . --include="*.sh" --include="*.py"   # 全部硬编码解释器
grep -rn 'if \[ -x "\$PY" \]' . --include="*.sh"              # 全部「探测不到就跳过」
```

⚠️ 本项目**同一族错误犯过两次**：上一轮是「`_index/` 已排除、
`corpus-baseline.jsonl` 同性质却漏排」（坑 6 的邻域）；
本轮是「门禁修了、其余入口没修」。
⇒ 共性：**把「复合/间接的东西」（一个入口 → 全部入口）当成「直接可读的结论」。**

### ⭐ 坑 11 的判据：对生成物的手工修改**必须回写成生成规则**（overlay）

**症状**：构建脚本的脱敏阶段是**纯机械替换**（从源仓库读 → `re.sub`）。
你对公开集文件的**手工重构**（如把扫描器词表外置）**在下次重建时被全部覆盖** ——
实测公开集的 `name_scan.py` 退化成 `BASE_NAMES = {"Z01": ["Z01","Z-ALIAS"], ...}`
（真名全变 Z 码骨架，`--names-dir` 不存在、空词表无守卫）。

**修法**：**overlay 目录** —— `overlays/<与公开集相同的相对路径>` 若存在，
则用该**成品文件整体替换**构建产物（同时覆盖「替换」与「新增」两种用途）。

**必须配套的三道自检**（都要「能拒绝」）：

| 自检 | 判据 |
|---|---|
| 排除项不残留 | 被排除的文件不得出现在产物里 |
| overlay **源**齐全 | 声明走 overlay 的路径，其 overlay 文件必须真存在 |
| overlay **产物**逐字节等于源 | 证明**没被二次改写**（否则跳过逻辑被改坏时**静默失真**） |

⚠️ **关键副作用（易踩）**：全局中性化阶段（`用户X → <user>`）**必须跳过 overlay 产物**。
overlay 是**已脱敏成品**，再扫一次会产出**自相矛盾**的文本
（实测：注释变成「`.../Users/<user>/...` 变成 `.../Users/<user>/...`」）。
⇒ 由此推出硬约束：**overlay 文件内不得出现任何真实用户名**（它不会再被替换）。
⚠️ 顺带：overlay 产物**没被替换**这件事，会让「新增文件」的计数
在「上轮残留」时显示为 0 —— 测 overlay 新增能力要**先删掉产物再重建**。

⭐ **通用化**：这是「环境会回滚编辑」的**机制性同族** ——
**改产物 = 迟早被覆盖；改「源」（overlay / 生成规则）= 持久**。
同族判据：**凡有「生成器 + 生成物」的组合，一切修改都必须落在生成器侧。**

### ⭐ 坑 12 的判据：检查脚本不得弄脏工作区

**症状**：门禁用 `"$PY" -B -m py_compile "$f"` 做语法检查 ——
**`-B` 抑制不了 `py_compile`**（`-B` 只管 **import 时**的字节码缓存，
而 `py_compile` 是**显式写 `.pyc`**）⇒ **每跑一次门禁产出 6 个 `.pyc`**。

**后果**（两条都是老问题）：
1. 门禁**自己弄脏**它下一步正要检查的工作区（随即 WARN「有未跟踪项」）；
2. **计数失真**：构建报 179 文件，核验器扫到 **185**（差 6）。

**修法**：改用**内建 `compile()`** —— 与 `py_compile` 做**同一件事**
（`py_compile.compile()` 内部就是调 `compile()`），都抛 `SyntaxError`，
但**完全不落盘** ⇒ **强度不变、副作用归零**：

```bash
"$PY" -B -c 'import sys; compile(open(sys.argv[1],encoding="utf-8").read(), sys.argv[1], "exec")' "$f"
```

⭐ **判据**：**根因修法是「不产生」，不是「产生后再清理」** ——
清理只能覆盖**自己知道的入口**，而入口会增多（构建清了，门禁又产生）。
**回归件**：跑完检查脚本后，`__pycache__` 目录数**必须仍为 0**。

## 关键设计决定：扫描器的词表必须外置

若项目自带的隐私扫描器把真名**硬编码在源码**里（常见），那么：

- 公开代码 = **直接泄露姓名**；
- 必须在公开版中改为**从外部文件读词表**，附**虚构**示例词表；
- ⭐ **未提供词表时必须主动报错退出**，而不是返回空模式 ——
  因为「空词表 ⇒ 扫描通过」会输出**虚假的干净结论**。
  这是扫描器最重要的防线。
- 词表接口一改，**必须同步项目的隐私 README**（属接口变更）。

## 交付物布局

**公开层单独新建目录并 `git init`**（不要 `filter-repo` 过滤旧库）：

| 做法 | 收益 |
|---|---|
| 新建仓库 | **无历史包袱** —— 不存在「删了文件但历史里还在」的问题 |
| `filter-repo` 旧库 | 需重写全部历史，且会**推翻按字节冻结的产物指纹**治理 |

**核验器与审计报告放在工作区之外**（它们自身含真名，属涉密件，不得入库）。

### ⭐ overlay 目录（生成式构建的必备件）

若构建是「**机械替换 + 成品改写**」两段式，则**任何手工修改都必须放进 overlay**：

```
<工作区之外>/overlays/<与公开集相同的相对路径>   ← 存在即整体替换构建产物
```

| 用途 | 说明 |
|---|---|
| **替换** | 路径同构建产物（语义重构，如扫描器词表外置） |
| **新增** | 路径在源仓库中不存在（如 LICENSE、虚构示例词表） |

⚠️ **overlay 文件内不得出现任何真实用户名/真名** —— 它们是全局中性化阶段的
**跳过对象**，写进去就**直接进公开仓库**（本项目踩到 2 处注释示例路径）。
⚠️ 构建脚本的**全局中性化阶段必须跳过 overlay 产物**，否则会产出矛盾文本。

## 门禁适配怎么做（不是放宽，是按层分支）

⭐ 原门禁为**私有 monorepo** 编写，相当一部分判据**天然以私有层存在为前提**。
在公开层跑会**永久红灯** ⇒ 结果是「要么忽略、要么绕过」，**两种都比没有门禁更坏**。

**正确做法**（本项目实测）：

| 设计点 | 做法 |
|---|---|
| 第三种计分 | `skip()` **独立计数**，既不进 PASS 也不进 FAIL |
| 层次判据 | 取「**私有分区目录是否存在**」——不是「某文件在不在」（会被单点缺失误判） |
| 跳过条件 | `公开层` **且** `私有标识不在场`；⚠️ **不是** `[ -f 判据源 ]`（那会把「判据源被删」也变成放行） |
| 汇总行 | **单列 `SKIP=N`** + 一行说明（只报 OK/WARN/FAIL 会让「几项没跑」不可见） |
| 反假绿 | 公开层却 `SKIP=0` ⇒ **判 FAIL**（防跳过逻辑失灵后静默变全跑） |

⚠️ **三条反模式（都不要做）**：
1. **把跳过写成 `ok()`** ⇒ 假绿；
2. **放宽阈值让公开层变绿**（如把父数判据 `!=3` 改成 `>=2`）
   ⇒ **同时放行私有层的真违规**，比红灯更坏；
3. **给跳过的项也计 `ok()`** ⇒ 同一项既 SKIP 又 OK，自相矛盾（本项目踩到）。

⚠️ 自证要**自包含**（红线 10：守卫必须自包含在被测的那个函数里）——
`--selftest` 的夹具**不得借用真实目录**（在公开层那个目录必然不存在 ⇒ 假失败）。
用 `mktemp -d` 造与 cwd 无关的真实目录，并在**多个 cwd** 下跑一遍。

## 结论怎么说

⭐ **先分清「三件事」，再给结论** —— 本项目实测：只答前一件会得出**过度断言**。

| 层 | 问题 | 验证方式 |
|---|---|---|
| **保密** | 公开集里**有没有**敏感信息？ | 7 维度 + 独立交叉核验 |
| **可用** | 公开集**自己跑得起来**吗？ | 跑自带门禁/CI、跑关键脚本、查运行时引用 |
| **发布** | **法律与文档**上齐备吗？ | LICENSE + README 适配 + 第三方许可兼容 |

⚠️ **措辞纪律**：**不要**因为「保密层全绿」就说「可以公开了」。
本项目就踩过 —— 第一版结论「技术条件已具备」，补验「可用层」后发现门禁 **FAIL=4**。
⇒ 正确表述：**「保密条件已具备；发布条件差 N 项」**，并**逐项列出** N 项。

⚠️ 最后一条建议：**不要因为「功能阶段没走完」而推迟拆库**。
推进阶段**不会**让已入库的真名消失，而私有层体积在持续膨胀 ⇒ **拆库越早越便宜**。
可以「先推私有仓库拿异地备份」与「转公开前补 LICENSE」分两步走。

## 推送执行与推送后核验（最后一公里，2026-09-24 实推踩坑）

> 前面所有章节都是「推之前」。这一节是**真正 push 的那一刻**会遇到的，
> 以及**推完必须回头验什么**。

### 步骤

```bash
cd <公开集目录>
git remote add origin https://github.com/<user>/<repo>.git   # ⚠️ HTTPS，不用 SSH（除非已配 key）
git push -u origin main
```

⚠️ **先在 GitHub 建空仓库，且三个开关全关**
（Add README / .gitignore / License 全部 **Off/No**）——
否则 GitHub 会产生一个**无关的初始提交**，与本地历史分叉，push 时要先
`--allow-unrelated-histories` 合并，白折腾一轮。

⚠️ **建仓库页面的默认标签可能是 SSH**（`git@github.com:...`）。
**照抄那条命令前先确认本机有没有 SSH key**（`ls ~/.ssh/id_*`）——
没有就走 HTTPS + 凭证管理器。

### ⭐ 坑 A：`Repository not found` 有**两种**含义，必须消歧

```
remote: Repository not found.
fatal: repository 'https://github.com/...' not found
```
可能是 **①仓库还没创建**，也可能是 **②没权限 / 认证没生效**。
**不要靠猜**，用 API 二分（无需 token 即可查公开信息）：

```bash
curl -s -o /dev/null -w "%{http_code}\n" https://api.github.com/users/<user>
# 200 = 账号存在      → 排除「用户名写错」
curl -s -o /dev/null -w "%{http_code}\n" https://api.github.com/repos/<user>/<repo>
# 404 = 仓库不存在    → 判定为「尚未创建」，让用户去点 Create repository
```
⭐ **`200 + 404` ⇒ 尚未创建**（最常见，用户填完表单但没点绿色按钮）。
若两个都 200 却仍 not found ⇒ 才去查权限 / 认证。

### ⭐ 坑 B：noreply 地址要做 **ID 交叉验证**（幽灵提交**不报错**）

用 `<id>+<user>@users.noreply.github.com` 时，**务必验一次**：
```bash
curl -s https://api.github.com/users/<user> | grep '"id"'
# 必须等于 noreply 地址里的 <id>
```
⚠️ **ID 写错不会报任何错** —— 提交照样推上去，只是**不归属任何人**
（头像不显示、贡献图不计），事后才发现很难查。

### ⭐ 坑 C：凭证 helper 选择弹窗（选 manager）

若弹出 `Select a credential helper`（`<no helper>` / `manager` / `wincred`）：

| 选项 | 判定 |
|---|---|
| **`manager`** | ✅ **选它**（GCM，支持浏览器 OAuth / 2FA / token 刷新） |
| `wincred` | ❌ 只存「用户名+密码」，**不支持 OAuth**；GitHub 2021 起已禁用密码推送 ⇒ 必然失败 |
| `<no helper>` | ❌ 不存储 ⇒ 每次都要重输 |

⚠️ 该弹窗可能来自 **PortableGit 的系统级 `etc/gitconfig`**
（`[credential] helper = helper-selector`），**不是用户自己配的** ——
用 `git config --show-origin --get-all credential.helper` 查来源再下结论。
勾选框 **`Always use this from now on`** 建议**先不勾**（先跑通再固化）。

### 推送后必须回头验的 5 项（**远端侧**，不是本地）

```bash
git ls-remote --heads origin          # ① 远端 ref 是否等于本地 HEAD
```
```bash
# ② 远端文件数：只数 blob，别把 tree 目录项算进去
curl -s "https://api.github.com/repos/<u>/<r>/git/trees/main?recursive=1" \
  | grep -oE '"type": *"[a-z]+"' | sort | uniq -c
#   期望 blob 数 == 本地 `git ls-tree -r HEAD | wc -l`（本项目 179/179，tree 42/42）

# ③ 远端**数据类文件必须为 0**（这是「语料私有」的最终验收）
curl -s ".../git/trees/main?recursive=1" | grep -oE '"path": "[^"]*"' \
  | grep -E '\.(jsonl|sse|csv|tsv|xlsx?|parquet|db|sqlite)"'
#   必须为空

# ④ 远端提交身份 + 消息零实名（逐条读 API，不信本地）
curl -s "https://api.github.com/repos/<u>/<r>/commits?per_page=100"

# ⑤ remote URL 里不得含 token
grep -iE "token|ghp_|password|@github" .git/config   # 须无命中
```

### ⭐ 坑 D：**终端乱码 ≠ 数据损坏**（险些误判）

`git log` 输出中文在 Windows 终端可能显示为 `琛ュ厖銆屽惎鐢...`。
**不要凭终端观感判定「提交信息坏了」**，取 **raw bytes** 解码验证：
```python
raw = subprocess.run(['git','log','-1','--format=%B'],capture_output=True).stdout
raw.decode('utf-8')        # 成功 ⇒ 仓库内数据正常，只是终端显示编码问题
```
⭐ 同族：**观察者的显示层**与**被观察的数据层**是两回事。

### ⭐ 坑 E：推送是**不可撤**的，删了也在

`git push` 之后，**提交对象永久留存**于 GitHub（提交列表 / REST API / 任何人 `git log`）。
本地重写历史**只改本地**，撤不回远端。⇒ 本技能前面所有「推之前」的核查，
**必须在首次 push 之前**做完，不能想着「先推上去再改」。

## ⭐ 已推送后的补救：force-push **不够**，要**删仓库重建**（2026-09-24 实测）

### 先说结论（违反直觉，务必记住）

**`git push --force` 之后，旧提交在 GitHub 上仍然完全可访问** ——
不是理论，是实测：
```
GET /repos/<u>/<r>/commits/<旧SHA>              → HTTP 200（不是 404）
raw.githubusercontent.com/<u>/<r>/<旧SHA>/README.md → HTTP 200，能读到内容
```
原因：**GitHub 的 force-push 只改 ref；旧对象要等服务端 gc，时间不确定**。
⇒ **「连历史一起清」靠 force-push 做不到即时生效。**

### 唯一能立刻生效的做法：删仓库 → 同名重建 → 重推

| | force-push | 删 + 重建 |
|---|---|---|
| 旧提交 API | HTTP 200（仍可达） | **`409 Git Repository is empty.`** |
| 旧内容 raw | 能读到 | **HTTP 404** ✓ |
| 生效时间 | 不确定（等 GitHub gc） | **立即** |

代价极低的前提：**仓库刚建、star/fork/watch 均为 0**。
⇒ **决策点其实是「发布前就问一句」**：若预期可能要清历史，
**先推一个临时仓库私有验证，再建正式仓库**，比事后重建便宜。

### 执行顺序（本地必须先就绪，再动远端）

```bash
# ① 本地：清洗历史 + 备份（见下节脚本）
# ② 本地：确认对象库干净（**关键，见坑 F**）
git reflog expire --expire=now --expire-unreachable=now --all
git gc --prune=now
# ③ 远端：GitHub Settings → Danger Zone → Delete this repository（需输入全名确认）
# ④ 远端：**同名**重建（⚠️ 必须同名 ⇒ remote URL 不变，无需改配置）
#       三个开关全关（Add README / .gitignore / License）
# ⑤ 验证旧对象已死（**注意 409 的正确解读，见下**）
# ⑥ git push -u origin main    ← 输出 `* [new branch]` 即证明推的是全新空仓库
```

⚠️ **重建后的配置不用改**：remote URL 同名不变；本地仓库级 `user.name/email`、
`core.hooksPath` 都是**本地**配置，不受远端影响；提交身份**已内嵌在提交对象里**。

### ⭐ 坑 F：清洗后若再 `fetch`，**本地对象库会被旧对象重新污染**

实测：为修 `--force-with-lease` 的 `stale info` 跑了 `git fetch origin`，
而当时**远端还是旧提交** ⇒ **旧对象被重新拉回本地对象库**
⇒ 本地扫描又出现 **273 处旧串**（reflog 可见 `... : fetch origin: forced-update`）。

⇒ **判据：清洗/重写历史之后，任何一次 `fetch`/`pull` 都要重新跑
`reflog expire` + `gc --prune=now`，并重新做对象级扫描。**
⇒ 正确顺序：**先把远端切成干净的，再 fetch**；否则 fetch 就是在往回搬垃圾。

### ⭐ 坑 G：HTTP 状态码判据必须**读出 message**，不能只判「是不是 404」

本项目踩到：检查旧提交是否失效时只判 `404`，而实际返回 **`409`** ⇒
脚本报「!! 仍可达」**误判**。实际 409 的 message 是：
```json
{"message": "Git Repository is empty.", "status": "409"}
```
⇒ **409 = 仓库为空 ⇒ 旧对象不存在**（即目标达成）。

**正确判据**（读 message，而非只读 code）：
```bash
curl -s ".../commits/<sha>" | grep -o '"message": *"[^"]*"'
#   "Git Repository is empty."  ⇒ 旧对象已死 ✓
#   "Not Found"                 ⇒ 旧对象已死 ✓（另一种表现）
#   正常返回 commit JSON         ⇒ !! 仍可达
```

### ⭐ 推送后核验的**最佳手法**：真实 clone 一份再扫描

⚠️ 不要「逐个文件 curl raw」——179 个文件逐个请求，实测**被 SIGTERM 打断**。
```bash
cd /tmp && git clone --depth 1 https://github.com/<u>/<r>.git _verify
cd _verify
git grep -I -F -l -e "<旧串1>" -e "<旧串2>" HEAD     # 须 0
git ls-tree -r HEAD | wc -l                          # 须 == 本地文件数
bash scripts/<门禁>.sh                               # 在**真实远端内容**上跑门禁
rm -rf /tmp/_verify
```
优点：**一次 clone 拿到全部内容**，且验证的是**真实远端状态**；
再配合「本地 HEAD == 远端 HEAD」的 SHA 相等（密码学保证内容逐字节一致）。

### 历史清洗脚本的实现要点（`filter-branch --tree-filter`）

| 要点 | 说明 |
|---|---|
| 用 `--tree-filter` 而非 `--env-filter` | 要改**文件内容**（tree），不是只改元数据 |
| **字节级替换**（`rb`/`wb`） | `.gitattributes` 若是 `* -text`（字节冻结），走文本层会被 EOL 归一化 |
| ⚠️ **必须 `git -c core.quotepath=false`** | 否则中文路径输出为八进制转义 ⇒ `git show <rev>:<路径>` 取不到 ⇒ **静默跳过 ⇒ 假阴性**（实测基线 58 而真值 79） |
| ⚠️ `quotepath` **只能按需加** | 若在通用 `run()` 里无条件拼 `["git","-c",...] + args` ⇒ 变成 `git -c ... git status` ⇒ `'git' is not a git command` |
| ⚠️ 必须补 **gc 清理** | `filter-branch` 只改 ref；旧对象被 `refs/original`+reflog 保护 ⇒ 对象级自证必挂（实测报 83 个残留 blob） |
| ⚠️ `filter-branch --all` 会连 **`refs/remotes/origin/*` 一起重写** | 导致本地 `origin/main` 失真 ⇒ `--force-with-lease` 报 `stale info`。**这是保护，不是故障**：先 `git fetch` 校正再推 |
| ⚠️ 替换表**必须与构建脚本一致** | 否则下次重建产出与历史不同的文本（本项目：构建脚本写 `_staging`、清洗脚本误写 `_stages`，靠机器比对才发现） |

**必做自证**（缺一不可）：
1. 每个提交逐提交扫描 ⇒ 全 0；
2. 文件数不变；
3. **未被替换的文件字节 SHA 不变**（防 EOL 归一化）+ 被替换数 == 基线命中数；
   ⚠️ `git grep <rev>` 输出带 `HEAD:` 前缀，**必须先剥掉**，否则 `path not in hits` 恒为真 ⇒ 假失败；
4. **对象库级**扫描（`--batch-all-objects --batch` 取 raw 字节）⇒ 全 0；
5. 新串命中 > 0（证明替换真的生效，不是空跑）。

### 仓库改名可以后做（不必为取名卡住）

实测：公开层里**通常不含硬编码仓库名**（本项目 `git clone` 命中 **0** 文件）。
⇒ GitHub 改名后 **issue/wiki/star/follower 自动重定向**，
且 `clone`/`fetch`/`push` 打旧地址**仍正常工作**，本地只需
`git remote set-url origin NEW_URL`。
⚠️ **唯一硬约束**：**以后不要再用回旧名字** —— 一旦重名，重定向立即失效。
⚠️ GitHub **不重定向 Actions**（有 workflow 时要注意）。
⇒ **取名不必阻塞发布**，先推、后改，成本约 1 分钟。

⚠️ 还有一个**更轻的公开路径**备选：只公开**自洽性最高、断链面最小**的子集
（如纯工具链目录），而不是整个代码层。适配成本低得多。

## 历史清洗的**备份目录**怎么安全处置（2026-09-24 实测）

清洗/身份重写这类操作会留下多个前态备份（`_pub-bak-before-*`）。
它们在工作区之外、从未上传，**但恒含旧串或旧身份** ⇒ 是「本地侧最后一处敏感沉淀」。

### 判敏感度：必须**内容 + 元数据**两栏（见坑 13 反例）

```bash
for d in _pub-bak-before-*; do
  echo "=== $d ==="
  echo "[元数据]"; git --git-dir="$d/.git" log --format='%an|%ae|%cn|%ce' --all | sort -u
  echo "[内容]"; for s in "<真名>" "<手机号>" "<邮箱>"; do
      echo "  $s → $(cd "$d" && git grep -l "$s" $(git rev-list --all) 2>/dev/null | sed 's/^[^:]*://' | sort -u | wc -l) 文件"
  done
done
```
⭐ 典型形态：**内容 0 命中，但元数据就是真名+手机号**（我本次就是这样）。

### 删之前：四项安全前置（缺一不可）

| # | 检查 | 命令 / 判据 | 风险若跳过 |
|---|---|---|---|
| 1 | 路径断言 | `os.path.normpath(p) == EXPECT` | 变量展开异常 ⇒ **误删** |
| 2 | 是独立仓库而非 worktree 指针 | `.git` 是**目录**（不是文件） | 若是指针文件，删它不影响主库但也删不掉真对象 |
| 3 | **无 `objects/info/alternates`** | `cat "$d/.git/objects/info/alternates"` | 有 alternates ⇒ **对象被他人共享**，删了会**破坏其他仓库** |
| 4 | 无外部引用 | `grep -l "<目录名>" --include=*.py --include=*.sh --include=*.md -r .` + 查主库 `.git/config` / `worktrees` / `.gitmodules` | 有脚本依赖 ⇒ 后续运行崩 |

### ⭐ 关键判据：**对象集合比对** —— 判断「删它会不会丢内容」

```bash
for d in A B; do git --git-dir="$d/.git" rev-list --objects --all | awk '{print $1}' | sort -u > /tmp/o_$d.txt; done
comm -23 /tmp/o_A.txt /tmp/o_B.txt      # 仅存在于 A（=待删）而不在 B（=保留）的对象
```

本次实测：待删目录 250 个对象中**仅 3 个**不在保留的回滚点里 ——
**恰好是它自己的 3 个 commit 对象**，也就是**含实名的那 3 个**。
⇒ **删它 = 只销毁实名元数据，零内容损失**。这个数字让「删」从「有风险」变成「明确安全」。

⚠️ 若差集里出现大量 **blob/tree**（不是 commit）⇒ 说明它**独有内容** ⇒ 删前必须先拷出或另做归档。

### 删除手法

- **不要**在 Bash 里用 `rm -rf "$VAR"` 裸删（本机安全策略会拦「无法解析命令根」，且变量异常风险高）。
- 用 **Python `shutil.rmtree`**，把「路径断言 + 存在性断言 + 删除 + 删后复核」压**同一进程**：

```python
p = "<绝对路径>"; EXPECT = os.path.normpath(p)
if os.path.normpath(p) != EXPECT: sys.exit("ASSERT FAILED")
if not os.path.isdir(os.path.join(p, ".git")): sys.exit("ABORT: not the expected repo")
shutil.rmtree(p)
if os.path.exists(p): sys.exit("FAILED: still exists")   # 删后必复核
```

### 删后必做

1. 保留的回滚点**二次核验**：`rev-list --count HEAD` / `cat-file --batch-all-objects` 数对象 / `grep -c missing` 应为 0 / 工作树 `status --porcelain` 为空。
2. 剩余备份**逐个体检**（内容+元数据）确认零敏感。
3. 回写交付文档（裁定 + 安全前置 + 判据修正 + 删后复核）。

⭐ **纪律**：**扫描/盘点阶段只出报告，不删任何东西**；等裁定后再动，且动之前把上面的前置跑完。
