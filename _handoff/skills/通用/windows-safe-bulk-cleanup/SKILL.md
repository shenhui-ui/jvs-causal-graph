# Windows 安全批量清理（移入回收站）

> 适用：用户说「清理」「清理一下」「腾空间」，或需要把一批文件/目录移入回收站。
> ⚠️ **单字「清理」是模糊指令** —— 先判定、再出清单、再逐组确认，**不要猜着删**。

## 0. 五步流程（顺序不可换）

| 步 | 动作 | 关键纪律 |
|---|---|---|
| 1 | **只读判定**：哪些真的能删 | 机械判据，不靠印象（见 §1） |
| 2 | **出清单**：全量路径 + 体量 + 分类 | 清单落到文件，供人工逐条看 |
| 3 | **逐组确认** | 用户选哪组删哪组；**未选的一行不动** |
| 4 | **执行**：移入回收站 | 硬前置断言 + 每批 10 项 + 逐批核验 + 失败即停（§2） |
| 5 | **核验**：源消失 + 仓库未受影响 | 双仓库 HEAD / 工作区变更数（§3） |

## 1. 第 1 步：只读判定「哪些真的能删」

**判据**：条目名是否出现在 **① 目标仓库的已入库文本文件** 或 **② 同目录下现存脚本** 里。

- ⚠️ **必须承认判据的方向性**：用**子串匹配**时，
  `零命中 ⇒ 必然无引用`（**保守可靠**）；而「有命中」**含假阳性**
  （实测：`probe/` 命中 `_d3_probe/`）⇒ 只作「待人工看」的标记，
  **不得当作「有依赖」的证据**。
- 分类输出三档：`KEEP`（活件：构建输入 / 工具 / overlay）/ `REF`（有命中）/ `FREE`（零命中）。
- ⚠️ **`KEEP` 必须人工列白名单**，不能靠自动判据 —— 自动判据认不出「这是构建输入」。

### ⚠️ 性能教训（两条，各跑到 10 分钟未完）
1. **不要用 `git grep -o -F -f <上千条模式>`** —— 模式太多会卡死。
2. **不要为了找引用去读整个数据目录的 `.json`/`.txt`** —— 数据目录太大。
⇒ 改为「**一遍 Python 遍历 + 单条编译正则**（只读 ≤5 MB 的文本类入库文件）」+
「同目录侧**只看脚本**」。实测：1069 个条目 × 18607 个文件 ⇒ **4 分 16 秒**。

## 2. 第 4 步：执行（移入回收站）

### 2.1 宿主限制：PowerShell 可能两条路都被封
本环境安全策略**拒绝**：
- `Add-Type` —— *"compiles and loads .NET code at runtime"* ⇒
  `[Microsoft.VisualBasic.FileIO.FileSystem]` 不可用；
- `New-Object -ComObject` —— *"COM object instantiation can run arbitrary code"* ⇒
  `Shell.Application` 的 `NameSpace(10).MoveHere` 不可用。

⇒ **改用 Win32 `SHFileOperationW` + `FOF_ALLOWUNDO`**（Python `ctypes`，无需 .NET / COM）：

```python
FO_DELETE, FOF_ALLOWUNDO = 0x0003, 0x0040     # FOF_ALLOWUNDO = 送回收站
FOF_NOCONFIRMATION, FOF_SILENT, FOF_NOERRORUI = 0x0010, 0x0004, 0x0400
# 结构体 SHFILEOPSTRUCTW；pFrom = '\0'.join(paths) + '\0\0'（双 NUL 结尾）
# fFlags = FOF_ALLOWUNDO | FOF_NOCONFIRMATION | FOF_SILENT | FOF_NOERRORUI
rc = ctypes.windll.shell32.SHFileOperationW(ctypes.byref(op))
```

⚠️ **`argtypes` / `restype` 要显式声明**（`POINTER(SHFILEOPSTRUCTW)` / `c_int`）。

### 2.2 ⭐⭐ 三条实测机制事实（不知道就会做错判据）

| # | 事实 | 后果 |
|---|---|---|
| 1 | **返回码不可信** —— 成功入回收站却返回 `rc=2`（`ERROR_FILE_NOT_FOUND`） | **判据不能用 rc** |
| 2 | **目录进回收站会「展开成多条」** —— 提交 10 项 ⇒ 回收站 `$I` **+344** | **判据不能用 `Δ$I == 项数`** |
| 3 | **目录需要「两遍」** —— 第一遍只回收其中的**文件**，留下**空目录壳** | 每批**必须重试一次** |

### 2.3 ✅ 可靠判据：回收站 `$I` 条目数增量
```
C:\$Recycle.Bin\<SID>\$I*     ← 每个入回收站的对象对应一条 $I
```
- **标定**（必做）：先丢 **1 个探针文件**，确认 `$I` **+1** ⇒ 机制可用（且证明**不是永久删除**）。
- 判定：**主判据 = 源路径全部消失**；**次判据 = `Δ$I >= 1`**（证明确实进了回收站）。
- ⚠️ 某些 SID 子目录**拒绝访问**（`WinError 5`）⇒ 遍历时逐个 `try`，跳过不可读者。
- ⚠️ 回收站满时会**自动清最旧** ⇒ `Δ$I` 可能偏小，故只作次判据。

### 2.4 安全纪律（缺一不可）
1. **硬前置断言**：每条路径 `normpath` 后**父目录必须恰为预期根目录**（顶层单段）
   ⇒ 杜绝「误删上级目录 / 通配符扩散」。断言不过 ⇒ **不做任何删除**。
2. **每批 10 项**；**逐批双重核验**（源消失 ∧ `$I` 增长）；**任一不符立即停止**。
3. **回收站，不永久删**（`FOF_ALLOWUNDO`）—— 可恢复。
4. **全过程留痕**：逐批结果写日志；清单文件与日志**保留**（是审计证据）。
5. **先做无害干跑**：造一个探针文件走完整流程，确认「源消失 + `$I` +1」再上真清单。

## 3. 第 5 步：核验（不只验「删干净了」）
- 清单 **N/N 已消失**；
- 目录/文件计数与体量**前后对照**（证明删的是预期的量）；
- **保留组逐项 `test -e`**（活件不能被误删）；
- ⚠️ **相关的版本库必须复验**：`HEAD` 未变、`git status --porcelain` 为 0
  —— 「删的是工作区之外的文件」不等于「仓库没受影响」，要**实测**。

## 4. 收尾
通用收尾序列见 `_handoff/DEFINITION-OF-DONE.md`（相对 JVS 仓库根）。本技能专属项：

- ⚠️ **若改动落在「会被发布」的路径上**（如公开层的 `_handoff/`），
  收尾必须把「构建 → 核验 → 推送」放在**最后一步**（详见技能 `repo-public-private-split`）。
- **判定脚本 + 清单 + 日志要留下**（下次清理可复用判据与格式）。

## 5. 边界
- **不删用户未确认的组**；`REF` 组即使体量大也**必须逐项核过**再动。
- **不动系统目录 / 不递归清空上级目录**；不在「家目录根」上做通配删除。
- 单字「清理」**不等于**授权删除 —— 授权只在「用户选定具体组」之后成立。
