## 铁律

**未完成阶段一（根因调查）之前，不得提出修复。** 只治症状 = 失败。

## 什么时候用

任何技术问题：脚本报错、行为异常、性能问题、门禁/构建失败、集成问题。

**尤其**在这些时刻：

- 时间压力下
- 「就一个快速修复」看起来很明显时
- 已经试过多个修复时
- 上一个修复没生效时
- 你并不完全理解问题时

**不要**因为「问题很简单」「很急」「对方催得紧」就跳过 —— 系统性调试比反复试错**更快**。

## ⚠️ 本项目最贵的一类：不报错、只出错

本项目已有大量「**静默过期**」前例：断言「状态」而非「事实」的文本，
**变了不报错，只持续输出错结论**。

⇒ 诊断这类缺陷时：

- **「没有报错」不是证据**；`rc=0` 不是证据；被忽略的 `WARN` 也不是证据
- 必须找到**观测值 vs 期望值**的具体差异，并**说明用什么口径测的「变」**
- **口径各有盲区**：尺寸、mtime、计数、`grep -c` 各自会漏 ——
  实测：只改时间戳、字节数**恰好相同**的产物，会让「尺寸变化」判据**恒报无变化**
- 判据能真跑就**真跑**，不要硬编码结论
  （**永久为真的告警会训练人忽略 WARN** —— 本项目已因此废弃过一条门禁硬编码告警）

## 四阶段（每阶段完成才能进入下一阶段）

### 阶段一：根因调查

1. **逐字读错误信息** —— 不要跳过；栈要读完；记下行号 / 路径 / 错误码
2. **稳定复现** —— 能可靠触发吗？确切步骤？每次都发生吗？
   **不能复现就去收集更多数据，别猜**
3. **查最近改动** —— `git log` / `git diff` / 新增依赖 / 配置变化 / 环境差异
   ⚠️ 本环境**不要用切换分支的方式看旧版本**（会触发丢文件事故）；
   用 `git show <sha>:<path>` 直接读历史内容
4. **多组件系统：先在每层边界加仪器**

   ```
   对每个组件边界：记录进入的数据、流出的数据、环境/配置传递、该层状态
   跑一次，得到「在哪一层断掉」的证据，再去查那一层
   ```

   （本项目实例：`桥 → 子进程 → git` 三层；断点在「子进程环境未注入 `PATHEXT`」，
   而不在桥本身 —— 不逐层加仪器就会去改错的地方）

5. **追数据流** —— 坏值从哪来？谁带着坏值调用了它？一路向上追到源头。
   **在源头修，不在症状修**

### 阶段二：模式分析

1. **找能跑通的同类** —— 同一库里相似的正常实现是什么？
2. **对照参考实现要读完** —— 不要跳读
3. **列出所有差异**，多小都要列 —— 不要假定「这个不可能有影响」
4. **搞清依赖** —— 还需要什么组件 / 设置 / 配置 / 环境？它假定了什么？

### 阶段三：假设与验证

1. **一次一个假设** —— 写清楚：「我认为根因是 X，因为 Y」
2. **最小验证** —— 只改一个变量，不要一次修多个
3. **验证后再继续** —— 成了 → 阶段四；没成 → **提新假设**，
   **不要在原假设上叠修复**
4. **不知道就说不知道**，不要装作知道

### 阶段四：实施

1. **先造一个能复现的检查件**

   ⚠️ **本项目改写点**：上游要求「先写一个失败的**自动化测试**」。
   本项目**通常没有测试框架** ⇒ 改为：
   **写一个只读的复现脚本，打印「期望值 / 实际值 / 判据口径」三样**，
   并在修复**之前**先跑一次、把差异记下来。有测试框架时仍优先自动化测试。

   ⚠️ 复现脚本放**工作区之外**（如 `C:\Users\<user>\_staging\tools\`），
   既符合本项目「工具放工作区外」的铁律，也避免污染 `git status`

2. **只做一处修复** —— 治已确认的根因；**不要顺手重构**、不要夹带别的改进
3. **验证修复** —— 复现件现在过了吗？**有没有把别的地方弄坏**？问题真的解决了吗？
   声明成功前必须有**本次新跑**的证据（不是「上次跑过」、不是「应该没问题」）
4. **修复无效就停**

   - 数一下：已经试了几个修复？
   - < 3 个：带新信息**回到阶段一**重新分析
   - **≥ 3 个：停下来质疑架构**，不要试第 4 个

5. **3 个以上修复都失败 ⇒ 质疑架构**

   症状：每个修复都在**别处**暴露新的共享状态 / 耦合；修复需要「大重构」；
   每个修复都在别处造出新症状。

   ⇒ 停下来问：这个设计本身成立吗？我们是不是在靠惯性硬撑？该重构还是继续治症状？
   **先和人讨论再动手。** （这不是「假设失败」，是「**架构错了**」。）

## 四条本项目实测纪律（上游没有）

### ① 出现 FAIL 先怀疑检查串

本项目已**四次**踩「检查串本身写错」：
凭印象写检查串 ⇒ 报 FAIL 而文本其实正确；
说明文字里含检查串 ⇒ **恒真通过**。

- 检查串**必须从文件里抄** —— 先 `grep -o` / `sed -n '<行号>p'` 打印真实行，再照抄
- 一律用 `grep -F`，**不用正则**
- ⚠️ **`grep -F` 下 `^` 是字面量**（固定串搜索**不解析锚点**）
  ⇒ 要按行首判定就用 `grep` / `grep -E`，或干脆去掉锚点只搜独特子串
- 判「行是否存在」按**行首**（`ln.startswith(...)`），不要用 `in`
- **命中 0 ≠ 编辑丢了** —— 先查是不是自己的引号 / 转义写错；
  `sed -n '<行号>p'` 打印真实行再判断

### ② 校验必须独立于被校验逻辑，且要自证

五种已实测失效形态：

| 形态 | 机制 |
|---|---|
| **子串假阳性** | 说明文字本身含检查串 ⇒ 恒真 ⇒ 报「通过」而正文没插进去 |
| **字段名错配恒真** | `o.get("size")` 而字段其实是 `s` ⇒ `None == None` |
| **守卫子串误判** | `if "X" not in s0` 被说明文字满足 ⇒ **跳过插入** |
| **检查串本身写错** | 凭印象写 ⇒ 报 FAIL 而文本正确 |
| **口径看不见「等长内容变更」** | 尺寸 / mtime / 计数各有盲区 |

⇒ 加**自证式校验**（直接数磁盘事实，不复用台账数字）；
期望值找**独立第二来源**对账；校验用**集合差**（新增 / 消失），**`消失` 必须为 0**。

### ③ 「换个版本 / 重装一下就好了」必须有离线对照实测

版本类结论极易由**源码阅读**得出。**源码阅读只能提出假设，实测才是证据。**

做法：取官方便携版解到**工作区之外** → 校验完整性（字节数 + SHA256 与官方值比对）
→ 把**同一份环境**分别喂给新旧两个可执行文件 → **逐项对照** → 无差异就**明确写「无效」**。

- ❌ 不要先装再试（安装是全局副作用）
- ✅ 结论写成「**无效 + 证据**」，否则后人会再试一遍

（实例：PS 7.6.6 与 5.1 在 `PATHEXT` 缺失时行为**逐字节一致**、且慢约 37% ⇒ 升级无效。）

### ④ 结果「全 0 / 全不相符」先怀疑比较口径

与 ① 是镜像：① 管「报了 FAIL 但文本其实对」，④ 管「**看起来全部相符 / 全部不相符**」。

**本项目实测（2026-09-21，代价一整轮的错误结论）**：把 Windows 绝对路径**写进 `python -c "…"`**，
反斜杠会被 shell 层**改写成正斜杠** ⇒ `pp.startswith(旧根)` **静默全假**，
据此得出「旧根 0 条」（真相是 1,165/1,165 全是旧根）。同一次还踩到两个变体：

- **假通过**：`os.path.exists("C:/Users/…")` 在 Windows 上**为真**（正斜杠等价）
  ⇒ 前一句「旧根存在: True」**看起来完全正常**，把口径已被改写这件事盖住了。
- **交集近乎空跑**：两侧分隔符不同（索引用 `\`、`git ls-tree` 用 `/`）
  ⇒ 集合交只剩 9 条，**尺寸校验等于没跑**，却报「不符 0 条」。

判据：

- 比较前**先打印两侧的 `repr()`**，肉眼确认分隔符 / 大小写 / 前后缀一致
- 断言前**自证口径规模**：交集条数异常小 ⇒ 口径错了（不是数据对了）
- 跨 shell 传参的字符串**不要用字面量反斜杠** —— 用 `chr(92)` / `os.sep` 拼，
  或干脆**把探针写成脚本文件**再跑
- 「全 0」「全不相符」「全部一致」这类**极端齐整的结果本身就是红旗**

## 红旗 —— 出现就停下，回到阶段一

- 「先快速修一下，之后再查」
- 「试试改 X 看行不行」
- 「一次多改几处，一起跑」
- 「跳过复现，我手工看一眼就行」
- 「大概是 X，我先修它」
- 「我还没完全理解，但这样可能管用」
- 「再多试一次修复」（已经试过 2 个以上时）
- 还没追数据流就先列修复方案
- 每个修复都在**别处**冒出新问题
- 「结果全是 0 / 全部相符」直接当成结论（先查比较口径，见纪律 ④）

## 常见借口对照表

| 借口 | 现实 |
|---|---|
| 「问题很简单，不用流程」 | 简单问题也有根因；简单问题上流程很快 |
| 「很急，没时间走流程」 | 系统性调试比反复试错快 |
| 「先试这个，之后再查」 | 第一个修复会定下模式，一开始就做对 |
| 「等修好了再补复现件」 | 没复现件的修复留不住；先证明它失败 |
| 「一次多修几处省时间」 | 无法归因，还会引入新缺陷 |
| 「参考太长，我按理解改」 | 部分理解必然出缺陷；读完再改 |
| 「我看到问题了，我直接修」 | 看到症状 ≠ 理解根因 |
| 「再多试一次」（已失败 2+ 次） | 3+ 次失败 = 架构问题，质疑模式，别再来一次 |

## 速查

| 阶段 | 关键动作 | 成功判据 |
|---|---|---|
| 1 根因 | 读错误、复现、查改动、逐层加仪器、追数据流 | 说清 **是什么** 与 **为什么** |
| 2 模式 | 找同类正常实现、逐项对照 | 差异清单 |
| 3 假设 | 单假设、最小验证 | 确认，或换新假设 |
| 4 实施 | 造复现件、单点修复、验证 | 缺陷消失且无新破坏，且有**本次**证据 |

## 当流程得出「没有根因」

若系统调查后确认问题是环境性、时序性、外部性：

1. 流程已走完
2. 记录你查过什么
3. 实施合适的处置（重试 / 超时 / 错误提示）
4. 加监控，便于下次调查

**但：95% 的「没有根因」其实是调查不完整。**
