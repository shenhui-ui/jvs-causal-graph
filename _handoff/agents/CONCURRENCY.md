# JVS 多会话并发提交 —— 优先级仲裁机制

> **一句话**：多个会话同时往同一仓库提交时，**不按提交时间先到先得**，
> 而按 `_handoff/agents/PRIORITY.json` 里**预先设定的优先级列表**仲裁；
> 冲突时**高优先级获胜**，低优先级触碰既有高优先级内容**会被拒绝并转人工**。
>
> **真值源**：`_handoff/agents/PRIORITY.json`（仅项目方可改，红线 7）。
> **实现**：`scripts/jvs-arbitrate.py`（全程 plumbing，不碰工作区 / index / HEAD）。
> **建立日期**：2026-09-28。**起因**：本仓实测到两个真实的并发失效模式（见 §3）。
>
> **⭐ 姊妹章 §8「任务级并行」** —— 本文 §0–§7 解决「**两个提交撞上了谁赢**」；
> §8 解决更前一步的问题：「**哪两个任务一开始就不该同时跑**」。
> 先按 §8 分组，再用本文仲裁；两者互补，不可互替。

---

## 0. 为什么需要它

本仓会出现**两个及以上会话同时操作同一个仓库**（实测：2026-09-28 一天内至少 3 个会话
交替推进 `main`）。既有流程（`GIT-POLICY.md` §四）只规定「各自开分支 → 门禁 → 合入」，
**没有规定两个会话同时要合并时谁先、谁赢**。

默认行为（按时间）会带来两类事故：

| 失效模式 | 后果 | 本轮实测 |
|---|---|---|
| **stale-tree 合并** | 后合并者的分支树基于**旧 main** ⇒ 合并树用分支树 ⇒ **静默回退先合并者的全部改动** | 已踩，见 §3.1 |
| **共享 index 污染** | 两个会话共用 `.git/index` ⇒ 甲 `git write-tree` 把**乙的半成品**一并快照 | 已踩，见 §3.2 |

⇒ 结论：**「按时间」在本仓不只是不公平，而是会丢数据。** 必须改成**按优先级列表仲裁**。

## 1. 优先级如何设定（你要改的就是这个文件）

`_handoff/agents/PRIORITY.json`：

```json
{
  "sessions": {
    "gate-signoff":     { "priority": 60, "desc": "验收/签字落档（红线 7，最高）" },
    "daily-dev":        { "priority": 50, "desc": "日常开发（主线推进）" },
    "handoff-reminder": { "priority": 30, "desc": "定时交接提醒（自动任务）" },
    "index-refresh":    { "priority": 20, "desc": "索引层刷新（多为生成物，已豁免）" },
    "ad-hoc": { "priority": 10, "desc": "临时/未声明会话的回落身份" }
  },
  "unmarked_priority": 40
}
```

**三条要点**：

1. **数字大者胜**。冲突时高优先级一方覆盖低优先级一方。
2. **会话身份由提交信息 trailer 承载**（只承载身份，**不承载权力** ——
   提交信息里写什么优先级一律忽略，防止自抬身价）：
   ```
   fix(x): 说明

   JVS-Session: daily-dev
   ```
   未署名 ⇒ 按 `ad-hoc`(10) 处理。
3. **`unmarked_priority`（40）= main 上「无署名内容」的基准优先级**。
   ≥40 的会话可以覆盖 main 上的既有无署名内容；**<40 的会**碰了就会**被拒绝**。
   ⇒ 这是「对并发保守还是激进」的总旋钮：调高更保守，调低放行更多自动覆盖。

### 调整流程（治理动作，走分支）

```bash
# ① 从 main 建分支（扁平名）
git update-ref refs/heads/chore-priority-adjust "$(git rev-parse main)"
git symbolic-ref HEAD refs/heads/chore-priority-adjust   # 或用 plumbing 全程不碰 HEAD
# ② 改 _handoff/agents/PRIORITY.json
# ③ 门禁 → 提交 → 合入（同其它改动）
```

> ⚠️ **本文件是治理件**：优先级即权力分配，属项目方裁定范畴（红线 7）。
> AI 可提议、可起草，**不擅自改既有会话的优先级数值**。

## 2. 用法

```bash
PY="C:/Users/<user>/.workbuddy-ai/binaries/python/versions/3.13.12/python.exe"

# 只探测（默认，不改任何 ref）—— 先看谁会被合、谁会被拒
"$PY" -B scripts/jvs-arbitrate.py --dry-run

# 真的推进 main（内部用 CAS，main 被并发推走则拒绝）
"$PY" -B scripts/jvs-arbitrate.py --apply

# 负向自证：6 个夹具场景，证明判据「能拒绝」
"$PY" -B scripts/jvs-arbitrate.py --selfcheck
```

**安全性质**：

- `--dry-run` 是**默认**，不加 `--apply` 绝不改 ref；
- 全程**不碰**工作区、`.git/index`、`.git/HEAD` ⇒ 可与其它会话**同时运行**；
- 推进 main 用 `git update-ref refs/heads/main <new> <old>` 的 **CAS 语义**
  （第三个参数是期望旧值）⇒ main 被并发推走时**自动放弃**，不覆盖；
- 有**任一被拒绝**的候选 ⇒ **整体不推进 main**（不带半成品入主线）。

## 3. 两个实测失效模式（这是本机制的由来）

### 3.1 stale-tree 合并（**最危险，会静默丢改动**）

**错误做法**（本项目既有文档 `GIT-POLICY.md` §四 / 技能里写的那种）：

```bash
TREE=$(git rev-parse "$BRANCH^{tree}")     # ← 分支自己的树
NEW=$(git commit-tree "$TREE" -p main -p "$BRANCH")
```

**为什么错**：该写法只在「**main 是分支祖先**」时正确（此时合并结果树 = 分支树）。
一旦 main 被**并发推进**，`$BRANCH^{tree}` **不含** main 上的新改动 ⇒
合并提交把那些新改动**静默回退**。本项目 2026-09-28 实测踩到：
一次合并把并发会话刚提交的 `memory/2026-09-28.md`（−53 行）与
`jvs-index-layer-maintenance/SKILL.md`（−21 行）**抹掉**。

**正确做法**（`jvs-arbitrate.py` 已采用）：

```bash
TREE=$(git merge-tree --write-tree main "$BRANCH") || echo "有冲突"
NEW=$(git commit-tree "$TREE" -p main -p "$BRANCH")
```

`git merge-tree --write-tree`（git ≥2.38，本机 2.55）做**真正的三方合并**，
返回合并结果树；且**不读写工作区、index、HEAD**（官方明示），天然适配并发。

### 3.2 共享 index 污染

`git add` 是**全仓共享**的（`.git/index` 只有一个）。
两个会话同时操作时，甲的 `git write-tree` 会把**乙已 `git add` 但尚未提交的半成品**
一并快照进甲的提交。本轮实测：本应 10 个文件的提交变成了 17 个。

**解法**：本批提交用**临时索引**，互不干扰：

```bash
export GIT_INDEX_FILE=/path/outside/repo/_tmp_idx
rm -f "$GIT_INDEX_FILE"
git read-tree HEAD                    # 以 HEAD 为基底载入临时索引
git add -- <只 add 本批文件>
T=$(git write-tree)                   # 只含本批
git commit-tree "$T" -p main -F msg.txt
unset GIT_INDEX_FILE
rm -f "$GIT_INDEX_FILE"
```

⇒ 结论：**在并发仓库里，凡 `git add` 后 `write-tree` 前可能被他人插入 `git add`，
就必须改走临时索引。**

## 4. 生成物豁免（不参与仲裁）

以下路径的冲突**不仲裁**，一律保留 ours 并列入「待重生成」：

- `_index/`（整个目录）
- `_handoff/PENDING.md`
- `_handoff/scripts/SCRIPTS.md`

**理由**：它们是**生成物**（真值源是 `_migrate/*.py`）。
对生成物做人工/自动仲裁 = 制造「生成物与生成器分叉」的真错。
正确姿势是**合并后重跑六步生成器**（见技能 `jvs-index-layer-maintenance`）。

配置位置：`PRIORITY.json` 的 `generated_prefixes` / `generated_files`。

## 5. 与既有流程的衔接

| 环节 | 既有做法 | 本机制补充 |
|---|---|---|
| 开分支 | `update-ref` + `symbolic-ref`（**禁用** `git switch`/`checkout`，因 SIGTERM） | 不变 |
| 提交 | `git add` + `git commit` | ⚠️ 并发时改**临时索引**（§3.2） |
| 合并 | `commit-tree "$BRANCH^{tree}"` + CAS `update-ref` | ⚠️ 树改自 **`merge-tree --write-tree`**（§3.1） |
| **多会话同时合并** | **无规定** | ✅ 本机制：`jvs-arbitrate.py` 按优先级仲裁 |
| 门禁 | `git-gate.sh` + `check_env.sh` | 不变（合并前仍须全绿） |
| 生成物 | 合并后跑六步 | 不变 + 豁免项入「待重生成」清单 |

> **不替代**：本机制只解决「**谁赢**」。**门禁仍然独立** ——
> 仲裁器不跑门禁，被合入的内容仍须在合并前由提交方自证门禁全绿。

## 6. 已知边界与不做的事

1. **不自动解语义冲突**：非生成物的真冲突，只在「优先级明确可分」时自动选边；
   低优先级触碰高优先级内容**一律拒绝**，交人工裁定（红线 7：不作独立语义裁决）。
2. **不看提交信息里的优先级**：身份（trailer）来自提交信息，**权力（数值）来自仓库外配置**。
3. **不替代 code review**：优先级高 ≠ 内容对。
4. **业界无先例**：调研（2026-09-28）显示 GitHub merge queue / bors / Zuul / Mergify
   **全部是「队列排序 + 冲突即拒绝/重试/人工」**，**没有**「冲突胜者由自定义优先级决定」的
   开源实现 ⇒ 本机制的仲裁策略层是**自研**，底层用的是 git 原生件
   （`merge-tree -X ours` + 临时索引 + CAS `update-ref`）。
5. **`-X ours` 必须留证**：它会**静默消除冲突**（rc 从 1 变 0）。
   故仲裁器**先跑一次不带 `-X` 的 `merge-tree` 取冲突清单并记录**，再决定是否消解 ——
   否则「发生过冲突」这一事实会丢失。

## 8. ⭐ 任务级并行（多 agent / 子代理）—— **什么能同时跑**

> **与上文的层次关系**：§0–§7 是**提交级**仲裁（两个提交撞上了谁赢）；
> 本章是**任务级**编排（哪两个任务根本不该同时跑）。**先分组，再仲裁** —— 分组减少冲突面，
> 仲裁兜住剩下的真冲突。**本章不替代 §1–§7。**

### 8.1 四条硬约束（判「能不能并行」的根因）

| # | 约束 | 后果 | 出处 |
|---|---|---|---|
| **C1** | **子代理共享同一个工作区**（同一目录、同一 `.git`） | 两个 agent 改**同一文件** ⇒ 环境回滚 + 互相覆盖 | 红线 3 |
| **C2** | **提交全部落 `main`** | 并发提交须走 `jvs-arbitrate.py`；**同一路径冲突必被拒** | 红线 27/28、本文 §3 |
| **C3** | **LLM 判分端点是端点级限流**（`token.sensenova.cn`） | 全局**同时只能有 1 个 LLM 任务** | 红线 §〇 |
| **C4** | **生成物**（`_index/*`、`_handoff/PENDING.md`、`_handoff/scripts/SCRIPTS.md`）仲裁豁免 | 必须**最后统一重生成**，**不可并行改** | 本文 §4 |

⇒ 推论：**「用不同 agent 并行」只对「写集不相交 **且** 不同时用 LLM」的任务安全。**

### 8.2 分组判据（对任意两个候选任务，依次问三句）

1. **写集相交吗？** 列出各自会写的**具体路径**（不是「大概改文档」）；有交集 ⇒ **不可并行**（C1）。
2. **都用 LLM 吗？** 都用 ⇒ **不可并行**（C3）。注意「只读任务」若内部调 LLM 取数，**仍算 LLM 任务**。
3. **谁是生成物？** 若一方改**生成器**、另一方改**生成物** ⇒ **生成物那一方必须最后跑**（C4）。

三问全过才可并行；否则**串行**，或改用**只读 agent**。

### 8.3 只读 agent 永远可以并行

`Explore` / `Plan` 类**只读** agent 不改文件、不提交 ⇒ 对 C1/C2 **影响为零**，可任意并发
（**仅受 C3 约束**）。

### 8.4 实测分组（2026-09-29 盘点，作为范例）

| 组 | 任务 | 写集 | 用 LLM | 可并行 |
|---|---|---|---|---|
| **A1** | P2-2 220 条「可疑度 `sus`」口径重定 | 仅工作区外报告 | ❌ | ✅ |
| **A2** | P2-4 123 条非阻塞提示归类 | 仅工作区外报告 | ❌ | ✅ |
| **B** | 关闭 P1-2 过期条目（改 `status_map.py` → 重生成） | `_migrate/status_map.py` + 生成物 | ❌ | ✅（与 A1/A2 写集不相交） |
| — | **P1-4 → P1-3**（改判分器 → 建自证件） | **同一判分器** | ✅✅ | ❌ **必须串行** |

**为什么 P1-4/P1-3 不能并行**（双重理由，缺一即已足够）：
① 两者都调 LLM ⇒ 撞 C3；
② P1-3 的自证件要**建在改后的判分器上**，先建再改 ⇒ 自证基线立刻漂掉（**红线 25 同族**：
把「工具没变」当成了「结论可比」）。

⇒ **建议并发度 ≤ 3，且其中至多 1 个用 LLM。**

### 8.5 与本文其它章的关系（三句话）

1. 并行分组**不替代**仲裁 —— 真冲突仍由 `jvs-arbitrate.py` 裁决（§1–§3）。
2. 写型任务提交时仍须走**临时索引**（§3.2）+ **CAS `update-ref`**（§2）。
3. 生成物一律**最后统一重生成**（§4），**不得**由某个并行分支单独产出。

### 8.6 ⚠️ 跨会话共享文件的写集纪律（2026-09-29 实测，三条）

#### ① 禁用宽泛 `git add -A` / `git add .`

- **实测**：某会话宽泛 add 之后，共享 index 里躺着**另一个会话的过期副本** ——
  `_handoff/agents/CONCURRENCY.md`（**1 增 / 59 删**，pre-§8 版）、
  `.workbuddy-ai/memory/2026-09-29.md`（**0 增 / 26 删**，缺一轮小节）。
- **可复用判据**：**纯删除、零新增** ⇒ 是**过期副本**，不是对方的新编辑；
  只有出现**新增**时才需要合并双方内容。
- **后果**：对方若按 index 提交（`git commit`），会**静默回退**对方已落库的 **85 行**，
  且 **git 不报任何错**。这是 §3「共享 index 污染」的**姊妹形态** ——
  污染是**夹带**别人的半成品，这里是**回退**别人的成品。
- **正解**：**显式列路径** add；写型任务一律走 §3.2 临时索引（`GIT_INDEX_FILE` 指向工作区外）。

#### ② 共享文件的「轮次」编号**不是全局唯一**

- **实测**：`memory/2026-09-29.md` 现存 **「轮次 5」×2、「轮次 6」×2** ——
  两会话**各自从 1 起编号**，互不知情（`sess_c7a5bcf9` 的 5 = 遗留件清理 + 并发约束表；
  `sess_3f5ab809` 的 5 = A1、6 = P1-4→P1-3 与 A2）。
- **约定**：引用必须带**会话标识**，写作 `轮次 5〔sess_c7a5bcf9〕`。
  **只加标识，不重排既有编号**（重排会打断既有引用）。
- **会话标识从哪来**：本仓**没有**现成的「会话实例 id」字段 ——
  `PRIORITY.json` 的 `sessions` 是**角色**（`daily-dev` 等）而非实例，**多个会话可共用同一角色**
  （本次实测即 `sess_c7a5bcf9` 与 `sess_3f5ab809` 都署名 `daily-dev`）⇒
  实例级标识取宿主 `CODEBUDDY_SESSION_ID` 前 8 位，写作 `sess_<8 位>`。

#### ③ 提交必须带 `JVS-Session` 署名（§1 的既有要求；本次自查发现漏签）

- **依据**：`scripts/jvs-arbitrate.py:37` `SESSION_TRAILER = "JVS-Session"`；
  `priority_of()` 对未署名提交返回 `unmarked_priority`（= **40**）。
- **已登记漏签**：`5f8658c`、`66453f2`、`f12e9b0`、`21cc67e`（本会话前四个提交）
  ⇒ 一律按 **40** 对待。对照：`sess_3f5ab809` 的 `18d5f04` / `bd2fbd0` **均已署名 `daily-dev`（50）**。
- **处置**：**不改写历史**（用 `commit-tree` 重建提交信息会改 SHA、打断既有引用）
  ⇒ 以「**后续提交一律带署名** + 本条登记」收敛。**新会话请照此自查**。

#### ④ 门禁 `[9]` 是「全仓当前 HEAD」的断言 —— 跨会话须先归因，再谈修复

- **判据**：`scripts/git-gate.sh:253` 取 `git rev-list --parents -n 1 HEAD | wc -w`，要求 `== 3`
  （双父合并）。它**只看末提交** ⇒ **任何会话直提 `main` 都会点亮它**。
- **实测（2026-09-29）**：本会话两笔单父提交（`21cc67e`、`2a5d1d4`）使 `[9]` 变红，
  而**评测线会话当时是绿的** ⇒ 归因必须看 `git log -1 --format=%p main` 的**父数与提交者**，
  **不能只看红绿**。
- **两种情形不可混**：
  - ✅ **自纠**：把**自己**的单父提交用 `commit-tree` 重建为双父（**tree 哈希不变** ⇒ 内容零变化）。
    这是还原「本应走分支 + `--no-ff`」的**应有形态**，手法见技能 `jvs-index-layer-maintenance`。
  - ⛔ **替他方补造**：为**别人的**单父提交补一个 merge —— 那是让守卫「看起来绿」，**不是修复**。
    正确做法是**如实报告**（评测线会话 2026-09-29 轮次 8 持此立场，本会话认同）。
