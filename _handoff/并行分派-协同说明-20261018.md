生成物的冲突**不仲裁**（一律保留 ours + 列入「待重生成」）—— 因为

⚠️ **两条已实测的坑**（技能原文，务必先读）：
1. **改完生成器源、跑生成器之前，必须逐项核验编辑存活** ——

   手法：对每条改动的关键串 `grep -cF`，输出必须全是 **1**。
   若跑完生成器才发现被回滚 ⇒ 产物里的尺寸字段是旧值 ⇒ **整轮六步必须重跑**。
2. **`classify.py` 必须跑两次**（第 ⑤ 步不可省）—— 否则 `功能分类总表.md` 里记的是**旧尺寸**。

## 4. C2 合入：仲裁调用方式（**必须带 `--refs`**）

### 4.1 为什么必须带

`scripts/jvs-arbitrate.py` 默认扫 **全部** `refs/heads/*`（L486 `for-each-ref`）。
本仓有 **23 个分支**（含 22 个历史遗留），其中**真未并入 main 的有 1 个**：

| 分支 | commit | 日期 | 仲裁器判定 |
|---|---|---|---|
| `docs-p1-closeout-20261007` | `39598d7` | 10-07 | ⛔ **拒绝**（与 `_migrate/status_map.py` 冲突，`p=40 ≤ 基准 40`） |

⇒ 若不限定 refs，仲裁器会**把历史遗留分支一并当候选**，
输出里混入无关拒绝项 ⇒ 干扰对三组新任务的判断。

### 4.2 正确调用

```bash
PY="C:/Users/<user>/.workbuddy-ai/binaries/python/versions/3.13.12/python.exe"

# 只处置指定分支（先 dry-run 看谁被合、谁被拒）
"$PY" -B scripts/jvs-arbitrate.py --refs <A组分支>,<B组分支>,<C组分支> --dry-run

# 确认无误再推进 main
"$PY" -B scripts/jvs-arbitrate.py --refs <A组分支>,<B组分支>,<C组分支> --apply
```

**安全性质**（已实测）：`--dry-run` 是**默认**；全程**不碰**工作区 / `.git/index` / `.git/HEAD`
⇒ **可与其它会话同时运行**；推进 main 用 `update-ref` 的 **CAS 语义** ⇒ main 被并发推走时**自动放弃**。

### 4.3 关于那个被拒的遗留分支（**只登记，不处置**）

`docs-p1-closeout-20261007`（`39598d7`）**不是**本轮三组的产物，是 **10-07 的遗留分支**。
实测它与 main 的差异方向是 **`401 deletions`**（20 文件 / +28 / −401）、
`status_map.py` 为 **1 增 22 删**，且其独有「+」行是 **10-07 已被订正过的旧表述**
（「注：寻址工具本体已由成品桥解决」—— 该说法在 `main` 上已于 `01671a7` 加删除线订正）。

⇒ **它的内容已被 main 覆盖并超越**（属 §3.1 stale-tree 形态：沿用旧树会静默回退 main 的新改动）。
**处置**：保留分支不动、登记在此。
⚠️ **不擅自删分支、不做语义裁决**（红线 7）。
