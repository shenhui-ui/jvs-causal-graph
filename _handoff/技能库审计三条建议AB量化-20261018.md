## 3. 建议②：`repo-refactor-perf-survey` × `script-family-merge-verification`

### 3.1 现状（A）

两条 description（frontmatter 原文）：

- **repo-refactor**（133 字）：`在一个大型…仓库上，做「代码重构 + 性能优化」候选的只读盘点，并产出方案文档。当出现「代码重构」「性能优化」「重复代码太多」「仓库太大/太慢」「全树扫描很慢」「哪些脚本可以合并」「盘点技术债」且**用户只要方案不写代码**时使用。`
- **script-family**（254 字）：`把「同源脚本族」合并成「单脚本 + 子命令」并做机械等价性验证（A/B）。当出现「这些脚本重复度很高，能不能合并」「命名族收敛」「多份快照合成一份」「合并后怎么证明行为没变」「A/B 验证脚本族」「合并完输出对不上」「给脚本加缓存/记忆化后结论会不会变」时使用。…`

**问题**：`「这些脚本重复度很高，能不能合并」` 是**评估语气**，却逐字写在 script-family（执行方）的触发语里；repo-refactor 的互斥条件「用户只要方案不写代码」在句末，权重低。于是两条评估查询 Q2/Q3 都被机械路由到 script-family。

### 3.2 三种 B 态

- **B1（审计字面）**：repo 把「用户只要方案、不写代码」提前；script 补「已决定要合并（不是评估要不要合并）」，但**保留**「这些脚本重复度很高，能不能合并」这个触发语。
- **B4（修正，建议）**：在 B1 基础上：
  1. repo 的触发语**显式收编**评估语气：`包括还在评估「这些脚本重复度很高，能不能合并」「哪些脚本可以合并」`；
  2. script 的触发语改为 `「同源脚本族已决定合并」`，**删除**「这些脚本重复度很高，能不能合并」；
  3. script 的互斥条件改为 `合并决定已作出（尚未决定时不要用本技能）`，**不再写**「不是评估要不要合并」——因为这句话本身会吸引评估查询；
  4. 两边各加一句反向指路（repo→script 执行；script→repo 评估/只要方案）。
